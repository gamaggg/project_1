# FishZone — журнал изменений

Формат: дата (сессии) не фиксируется автоматически — при переносе в реальный проект дописывайте дату коммита. Каждая запись = один запрос пользователя и что было сделано.

## Инициализация проекта
- Собран MVP мобильного приложения для береговой рыбалки в Батуми по исходному ТЗ (Strava-style, не игра).
- Единый файл `fishzone-app.html` (HTML/CSS/JS, без сборки), рендерится как мобильный экран 390×844.
- Экраны: Карта, Территории, Камера (фиксация улова), Подтверждение улова, Активность, Профиль.
- Реальная карта на Leaflet + OpenStreetMap тайлы.

## UI-полировка
- Единый шрифт (Manrope) на всё приложение, включая GPS-чип на камере (раньше был отдельный monospace).
- Плавные переходы между экранами (кроссфейд + подъём) вместо резкого display:none/flex.
- Углублены тени, добавлены градиенты на кнопках, тактильный отклик (scale на нажатии) почти на всех интерактивных элементах.
- Добавлен минимальный брендинг-лого на экране карты.

## Баг: тайлы карты с водяным знаком «API KEY REQUIRED»
- Причина: CARTO закрыл бесплатный доступ к своим базовым тайлам.
- Исправление: переход на стандартные тайлы OpenStreetMap (без ключа) + CSS-фильтр (grayscale/contrast) для приглушённого «премиального» вида вместо туристической пестроты OSM по умолчанию.

## Баг: территории на карте не совпадали с береговой линией
- Несколько итераций проблемы:
  1. Первая версия — повёрнутые квадраты по 2 опорным точкам берега → диагональ резала город.
  2. Убрали поворот (axis-aligned квадраты через divIcon) — устранило часть багов, но перестало «облегать» изгиб берега.
  3. Вернули поворот через две смещённые кривые (земля/море) + нарезку на полосы — сложная геометрия, часть багов с самопересечением полигонов.
  4. По просьбе пользователя — сектора стали шестиугольниками (сотами), шаг 300 м, каждый сектор ориентируется по касательной ЛОКАЛЬНО (не по одной глобальной линии).
  5. Обнаружено: направление менялось только в 6 точках стыка исходных опорных точек → между ними ряд был прямым. Добавили сглаживание сплайном (Catmull-Rom) — не прижилось при дальнейшей правке.
  6. **Финальное решение**: убрали сплайн и любые «глобальные линии» вообще. Ввели `SECTOR_POINTS` — явный список `{ id, lat, lng }`, по одной точке на сектор. Ориентация и размер каждого шестиугольника считаются от соседних точек в списке (направление на предыдущую/следующую точку). Это даёт полный ручной контроль без скрытой математики.
- Отдельная проблема: часть опорных координат указывала на объекты в глубине города (например, «Центральный парк Батуми»), а не на набережную → линия срезала через кварталы. Пересчитано через проверенные прибрежные ориентиры (Iveria Beach, Alphabet Tower, Radisson Blu, парк Batumi Boulevard, Batumi Beach, озеро Ардагани, южный кластер New Boulevard), найденные через Google Places.

## Баг: карточка сектора на карте перекрывалась нижним меню
- Карусель карточек (`map-sheet-container`) была позиционирована `bottom:12px`, залезала под `bottomnav`.
- Исправление: `bottom:94px` (высота меню + отступ).
- Побочный баг: при подъёме карточек случайно занизили `z-index` карусели ниже, чем внутренние z-index панелей Leaflet (тайлы/маркеры) → карточки визуально «исчезли» под картой. Возвращён `z-index:700`.

## Баг: кнопка камеры перекрывалась нижним меню
- При открытии полноэкранной камеры `bottomnav` теперь скрывается (`display:none`), возвращается при выходе из экрана камеры.

## Функция: свайп карточки сектора → карта летит к нему
- Карусель карточек через нативный горизонтальный скролл (`scroll-snap`).
- При свайпе (через `scroll`-listener с debounce) карта делает `flyTo` на выбранный сектор.
- Баг: `zoomend` (срабатывающий из-за `flyTo`) был подписан на полную перерисовку карусели → карусель сбрасывалась на первую карточку → карта возвращалась обратно к «моей территории». Исправление: перерисовка квадратов на зуме отделена от перерисовки карусели; карусель теперь обновляется только там, где это действительно нужно (при первой загрузке и после подтверждения улова).

## Замена логики секторов: гекс-сетка друга по реальным данным OSM

Пользователь принёс независимо написанный инструмент друга (`fishing-hex.zip`) — генератор гексагональной сетки 600м по воде из OpenStreetMap. Заменили им ручной список ориентиров `SECTOR_POINTS` (~24 точки, только центр Батуми, только море, координаты подбирались вручную по Google Places).

Что сделано:
- Инструмент скопирован в `tools/fishing-hex/` (`fetch_osm.sh`, `build_hex.mjs`, `assemble.mjs`, `tiles.py`, `README.md`, `package.json` + `hex.geojson`/`water.geojson` — уже прогнанные автором данные для bbox Сарпи–Чакви).
- Добавлен `tools/fishing-hex/extract_sectors.mjs` (новый файл, не было у друга) — фильтрует `hex.geojson` до реальных (`core:true`) сот, конвертирует координаты `[lon,lat]→[lat,lng]`, считает центр каждой соты. Node в этой среде был недоступен — прогнан один раз эквивалентным Python-скриптом, результат (`sectors.json`) идентичен тому, что дал бы `node extract_sectors.mjs`.
- `fishzone-app.html`: `SECTOR_POINTS` + вся ручная геометрия (`hexCornersForPoint`, `lerp`, `metersOffset`, `metersDelta`) удалены. Вместо них — вшитый `const HEX_SECTORS` (703 сектора: море 61, река 303, ручей 320, озеро 19) и `territories = HEX_SECTORS.map(...)`.
- Стартовые «моя»/«чужие» территории (`B1127`/`B1126`/`B1079`) подобраны как ближайшие морские соты к тем же трём ориентирам набережной, что были в старой версии (Дельфинарий/Marriott/порт) — сохранили узнаваемость демо-сценария и персонажей «Алексей»/«Марина».
- Попутно исправлено расхождение документации и кода: `t.name`/`t.type` (выдуманные названия секторов) фактически ещё выводились в нескольких шаблонах, хотя решение их убрать было задокументировано раньше. Убраны окончательно; «Тип» на карточке территории и в списках теперь показывает настоящий тип воды сектора (`KIND_LABEL[t.kind]`: Море/Река/Ручей/Озеро) вместо выдуманного текста.
- Все `onclick="...(${t.id})"` без кавычек починены на `'${t.id}'` — id теперь строка (`"B0144"`), не число.
- Карта: `preferCanvas:true` (замер — перерисовка всех 703 полигонов ≈5мс), `fitBounds` считается по вершинам `territories` (весь охват, а не старые точки), id-подписи секторов вынесены в отдельный слой и показываются только при `zoom >= 14` — на дальнем зуме 703 подписи разом превращались в нечитаемое месиво текста; шестиугольники со статусом остаются видны на любом зуме.
- Тексты интерфейса: «Побережье Батуми · N участков» → «Море, реки и озёра Аджарии · N участков», «Шаг ≈300 м» → «≈600 м» (реальная ширина соты инструмента).
- Проверено вручную через локальный http-сервер (файл открытый как `file://` рендерился статическим снепшотом без выполнения JS) — карта, карусель, список территорий (703 карточки), полный цикл камера→подтверждение→успех, лента активности, профиль и достижения отработали без ошибок в консоли; `renderTerritoriesList()` ≈9мс, `renderMapSheet()` ≈54мс на 703 элемента.
- Решение по охвату (весь берег Аджарии + все 4 типа воды, а не только море в центре Батуми) — явный выбор пользователя, зафиксирован в DECISIONS.md вместе с открытым вопросом о переименовании/репозиционировании продукта.

## Миграция в веб-сервис: Next.js + Supabase + Vercel

Пользователь решил делать не прототип, а настоящий веб-сервис — многопользовательский, с реальными аккаунтами вместо одного демо-юзера. Стек (Next.js + Supabase + Vercel), объём переноса (дизайн 1:1, минус рамка телефона) и момент подключения авторизации (сразу, email+пароль) — согласованы явными вопросами пользователю, зафиксированы в DECISIONS.md.

**Окружение**: в среде разработки не оказалось Node.js/npm вообще (ни системно, ни через nvm/Homebrew — тоже не было). Скачан официальный Node 24 LTS (arm64) с nodejs.org в `.tools/node/` внутри репозитория (gitignored) — без sudo, без изменения системных путей.

**Scaffold** (`web/`): `create-next-app` (App Router, TypeScript, ESLint, без Tailwind — переносили существующие CSS-токены дословно). Пакеты: `@supabase/supabase-js`, `@supabase/ssr`, `leaflet` (без `react-leaflet` — Leaflet рулится императивно, как в прототипе), `@tanstack/react-query`.

**Next.js 16 (новее тренировочных данных модели)**: `web/AGENTS.md` (сам файл кладёт `next dev`) явно предупредил свериться с `node_modules/next/dist/docs/` перед тем как писать код. Ключевое отличие — `middleware.ts` переименован в `proxy.ts` (`export function proxy` вместо `export function middleware`), механика та же. Использован `proxy.ts` сразу, без набивания шишек.

**База данных** (Supabase проект `yhgdcdkfkerzuhnzjzrz`, уже был подготовлен в сессии, схема была пустой): через MCP `apply_migration`/`execute_sql` созданы `profiles`, `territories` (тонкая — id/kind/lat/lng/owner_id, без геометрии), `catches`, `activity_log`, вью `territories_with_stats` (агрегация catch_count/last_catch_at), RLS (публичное чтение везде, запись только через RPC), RPC `confirm_catch` (SECURITY DEFINER, атомарно: улов → смена владельца → лента, с блокировкой строки территории от гонки при параллельном захвате), триггер `handle_new_user` (создаёт `profiles` при регистрации). Просеяны все 703 территории из `tools/fishing-hex/sectors.json` — **все свободны**, никаких demo-владельцев (в отличие от прототипа с захардкоженными `B1127`/`B1126`/`B1079` — фиктивные люди неуместны при настоящих аккаунтах).

`get_advisors` после первого прохода нашёл 2 security warning (обе SECURITY DEFINER-функции были случайно исполняемы ролью `anon`, включая `handle_new_user`, который вообще не должен быть вызываем напрямую) — поправлено отдельной миграцией (`revoke`/`grant` только нужным ролям), после чего остался один ожидаемый warning (сам факт того, что `confirm_catch` доступна `authenticated` — так и задумано).

**Приложение**: 7 экранов перенесены как клиентские React-компоненты внутри одного app-shell (`FishZoneApp.tsx`, стейт-машина экранов — аналог `goTo()`/`currentScreen` из прототипа, не отдельные Next.js-роуты — см. DECISIONS.md). Карта (`LeafletMap.tsx`) — прямой перенос `initMap`/`drawTerritories` с тем же `preferCanvas:true` и зум-гейтингом подписей. Данные — через `@tanstack/react-query` хуки (`lib/supabase/queries.ts`): геометрия секторов фетчится статикой из `public/data/sectors.json` и мёржится на клиенте с владением из `territories_with_stats`. `/auth` — форма входа/регистрации email+пароль, вне app-shell. Карта/территории/активность доступны без входа; запись (улов/захват) редиректит на `/auth`, если нет сессии.

**Баг, найденный и починенный в этой же сессии**: `lib/supabase/client.ts` изначально создавал новый Supabase-клиент на каждый вызов `createClient()` — из-за этого `AuthProvider` (подписан на один экземпляр) не узнавал о входе, выполненном через другой экземпляр (форма на `/auth`), пока страница не перезагружалась полностью. Первый сквозной тест («поймать рыбу» сразу после регистрации) провалился именно на этом — `startCatchFlow` считал пользователя неавторизованным. Починено переводом `createClient()` на модуль-левel синглтон.

**Проверено вручную** через `next dev` (порт 3300, добавлен как конфигурация `fishzone-web` в `.claude/launch.json`) с реальным Supabase: регистрация → (подтверждение email через прямой SQL, т.к. тестовое письмо шло на несуществующий адрес) → вход → карта (703 сектора, публичный список/фильтры) → открыть территорию → камера → подтверждение улова → RPC `confirm_catch` → сектор стал «моя территория», записи появились в `catches`/`activity_log`, профиль/достижения/лента обновились — все проверено прямыми SQL-запросами к БД, не только по UI. Тестовый аккаунт и его данные удалены после проверки (`delete from auth.users` — каскадом почистило всё, включая владение территорией).

**Не сделано в этом заходе** (см. «Открытые вопросы» в DECISIONS.md): деплой на Vercel (MCP-коннектор не авторизован, нужен явный шаг пользователя), Realtime-подписки (пока refetch-on-focus через react-query), файловые миграции `web/supabase/` (схема живёт в истории миграций Supabase, не в репозитории).

## Деплой на Vercel

MCP-коннектор Vercel не заработал ни разу за сессию — каждый вызов (`list_teams`, `create_git_project`, `get_deployment`) отдавал `403 Not authorized... re-authenticate to this scope`, независимо от переданного teamId (пробовал `personal`, `gamag`, реальный `team_...` id из тела ошибки). Штатного способа переподключить именно этот коннектор не нашлось. Весь деплой пользователь прошёл сам через веб-интерфейс Vercel по пошаговым инструкциям в чате, я диагностировал по присланным скриншотам и проверял результат через Browser-инструмент (публичные `*.vercel.app` URL не требуют моей авторизации в Vercel).

Первая попытка — проект `project-1`, который Vercel, похоже, создал сам через auto-detect сразу после пуша в GitHub (карточка «New repository detected»). У него на всех доменах (включая уникальный URL самого деплоя, не только кастомный алиас) стабильно был `404 NOT_FOUND` на уровне edge-сети — при этом сборка была зелёной, лог показывал корректный роут `/`, а в Runtime Logs не появлялось вообще ни одной записи (запросы не доходили до функции). Ни правка Root Directory (`web`), ни отключение Deployment Protection (`Require Log In`), ни повторные Redeploy (в т.ч. без билд-кэша) не помогли.

Решение — не чинить, а пересоздать: удалили `project-1` (Settings → Advanced → Delete Project) и импортировали репозиторий заново через обычный флоу Import, задав Root Directory и env-переменные (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) сразу на экране импорта. Новый проект (`web`) заработал с первого деплоя.

**Продакшен: https://web-flame-mu-44.vercel.app** — проверено вживую (карта, 703 сектора из реальной БД, без ошибок в консоли).

## Баг: карта на проде без гексагонов и обрезана

Пользователь открыл продакшен-URL в своём браузере — карта частично не показывалась, гексагонов не было вообще, только куски тайлов. Воспроизвёл в Browser-инструменте на локальном деве (баг был не только на проде — он был во всём переносе с самого начала, просто не проверялся в настоящем браузере вне превью-панели).

Причина — банальная: при переносе карты из `fishzone-app.html` (где `leaflet.min.css` подключался через `<link>` в `<head>`) забыл добавить эквивалент в Next.js-версию. Без стилей Leaflet у canvas-слоя с полигонами нет `position:absolute` (наследуется из `leaflet.css`, других источников для этого правила нет) — он рендерился как обычный `<canvas>` браузера по умолчанию (`display:inline; position:static`), поэтому visually улетал за пределы видимой области карты. Тайлы при этом выглядели более-менее нормально, потому что их позиционирование Leaflet делает через инлайновые `transform`, не только через CSS — из-за этого баг был не сразу очевиден на глаз (карта вроде рисовалась, просто без секторов и слегка криво).

Исправление: `import 'leaflet/dist/leaflet.css'` в начало `LeafletMap.tsx` (единственное место, где карта монтируется). Заодно на всякий случай добавлен `ResizeObserver` на контейнер карты, вызывающий `map.invalidateSize()` при изменении размера — не по этому багу, а как общая защита от рассинхронизации размера контейнера/карты в будущем (шрифты `next/font` могут дозагружаться и сдвигать вёрстку уже после инициализации Leaflet).

## Форма входа встроена в профиль вместо отдельного экрана /auth

## Геолокация, форма улова, справочник видов на 36 рыб

По запросу пользователя — реалистичный поток фиксации улова вместо случайной генерации. Первое изменение с переноса в веб-сервис, которое трогает схему БД — прошло через `EnterPlanMode`.

**БД** (миграции `0005`/`0006` через Supabase MCP): новая таблица `species` (key/name/category, 36 строк — 23 морских + 13 пресноводных, публичное чтение). `catches.species`: enum `catch_species` → текстовый FK на `species.key` (гибче — не нужна миграция на каждый новый вид). `catches.length_cm`/`weight_kg`/`method`/`bait` → nullable (обязателен только вид). `confirm_catch` пересоздана с новой сигнатурой (`p_species text`, остальные параметры `default null`). `get_advisors` — тот же единственный ожидаемый warning, что и раньше.

**Форма улова**: `ConfirmScreen.tsx` переписан из экрана-обзора случайно сгенерированных данных в настоящую форму — переключатель «Морская/Пресноводная» (дефолт от `territory.kind`), `<select>` вида рыбы (обязателен, список из `useSpecies()`, отфильтрован по категории), необязательные размер/вес/способ/наживка. `FishZoneApp`: `takePhoto()` больше не генерирует случайные данные, `handlePlus()` (новый) — геолокация → территория → камера, `submitCatch()` принимает данные формы вместо готового `pendingCatch`.

**Достижения**: «Коллекционер видов» пересчитана — раньше «поймать все 3 (из 3)», теперь фиксированный таргет 5 разных морских видов (с 23 видами «поймать всё» — нереалистичная планка). `personalRecord()` учитывает только уловы с указанным размером (раз размер теперь необязателен).

## Настоящая камера, обязательное фото, интро-экран

По запросу пользователя (скриншот с реальной геолокацией на его телефоне): убрать GPS-чип с экрана камеры и заменить симулированную камеру на настоящую (`getUserMedia`). Первый черновик плана предлагал мягкие фолбэки (пропуск фото при отказе, незаблокированный сабмит при неудачной загрузке) — пользователь их отклонил в рецензии плана, план переписан под «фото обязательно всегда» (см. DECISIONS.md).

**БД** (миграция `catch_photos`): `catches.photo_url` — `text not null` (добавлена через safe default-и-drop, т.к. `ADD COLUMN NOT NULL` без дефолта падает на непустой таблице). Storage-бакет `catch-photos` (публичное чтение, запись только `authenticated` в свою папку `{userId}/...`). `confirm_catch` пересоздана: `p_photo_url text` — обязательный параметр (без дефолта, перед остальными опциональными — Postgres требует такой порядок).

**Камера** (`CameraScreen.tsx`, переписан): стейт-машина `intro→requesting→live→denied`. `intro` — объяснение + кнопка «Разрешить доступ к камере»; клик → настоящий `getUserMedia({video:{facingMode:'environment'}})`; успех → `<video>` с потоком + затвор; отказ/ошибка → `denied` — сообщение и только кнопка «Запросить доступ снова» (без обхода). Затвор рисует кадр в offscreen `<canvas>` (даунскейл до 1280px), сразу останавливает поток, кодирует JPEG (`toBlob`, качество 0.85). GPS-чип убран из UI целиком (геолокация как логика осталась, просто не показывается).

**Загрузка и форма** (`FishZoneApp.tsx`, `ConfirmScreen.tsx`, `lib/supabase/storage.ts` — новый): кадр сразу переключает на `screen-confirm` и запускает загрузку в фоне (`uploadCatchPhoto`), пока пользователь заполняет форму на том же экране — превью фото и поля вида рыбы/размера/веса/способа/наживки показываются вместе, не разными шагами. Поверх фото — статус: спиннер при загрузке, сообщение об ошибке + кнопка «Повторить попытку» (перезаливает тот же `Blob`) при неудаче. Кнопка «Подтвердить улов» задизейблена, пока не выбран вид **и** фото не загружено успешно — отправить улов без фото невозможно ни в UI, ни на уровне RPC/БД.

**Баг, найденный и исправленный при сквозной проверке**: `srcObject` присваивался `<video>` в обработчике клика сразу после `getUserMedia`, но элемент `<video>` рендерится в разметке только при `state==='live'` — в момент присвоения он ещё не существовал, поток молча терялся, экран оставался чёрным. Исправлено: `useEffect` по смене `state` подключает сохранённый в `streamRef` поток к `videoRef` уже после монтирования `<video>`.

**Второй баг, найденный при сквозной проверке**: `CameraScreen` — один и тот же React-компонент на всю сессию (экраны не размонтируются, только переключается CSS-класс `.active`), поэтому второй заход в камеру (новый улов или возврат кнопкой «назад» с экрана подтверждения) заставал компонент в состоянии `live` с уже остановленным потоком от предыдущего кадра — застывший чёрный экран вместо новой попытки. Исправлено: `FishZoneApp` держит счётчик `cameraSessionId`, инкрементирует его в каждом месте, откуда открывается камера, и передаёт как `key={cameraSessionId}` — форсирует полный ремаунт компонента с чистым состоянием `intro`.

Проверено вручную на локальном деве: `navigator.mediaDevices.getUserMedia` подменён на canvas-based `MediaStream` (`canvas.captureStream()`, рисующий видимый текст «MOCK CAM») — пройден полный путь интро→доступ→живое видео→кадр→фон-загрузка→форма→сабмит→БД (`photo_url` заполнен реальной ссылкой на Storage, файл открывается напрямую и показывает снятый кадр) → территория и достижения обновились, фото появилось в карточках уловов (`TerritoryScreen`/`ProfileScreen`) вместо градиента-плейсхолдера. Отдельно проверены оба защитных пути: отказ доступа → экран `denied` → «Запросить доступ снова» → повторный вызов `getUserMedia` (успешный) → живое видео; и неудачная загрузка (подменённый `fetch`, первый POST в Storage возвращает 500) → сообщение об ошибке + кнопка «Повторить попытку», сабмит задизейблен → повтор → загрузка проходит, сабмит разблокирован. Не проверено на реальном телефоне/камере (только эмуляцией) — см. открытый вопрос в DECISIONS.md.

## Метка геолокации на карте, «+» — единственный путь к камере

По запросу пользователя, уточняющему логику геолокации: при определении местоположения на карте должна появляться метка, а если человек не стоит ни на одном секторе — явное сообщение об этом, а не тихий фолбэк на что-то другое.

**`lib/geolocation.ts`**: `findMyTerritory()` разделена на `getCurrentCoords()` (координаты или `null`) и `nearestTerritory(lat, lng, territories)` (чистая функция поиска ближайшего сектора в радиусе 400м) — координаты теперь нужны сами по себе, для маркера, а не только для расчёта совпадения.

**`LeafletMap.tsx`**: новый метод хендла `showUserLocation(lat, lng)` — ставит/двигает маркер реальной позиции (синяя точка с CSS-пульсацией), не завязан на перерисовку полигонов секторов. Проброшен через `MapScreen.tsx` тем же паттерном, что уже был у `flyToTerritory`.

**`FishZoneApp.handlePlus()`** переписан: координаты получены → маркер ставится на карту всегда, затем ищется сектор → нашли — камера открывается, как раньше; не нашли — новое модальное окно «Ты не на территории» (`.modal-overlay`/`.modal-card`, новый паттерн в `globals.css`) вместо старого фолбэка на ранее вручную открытую территорию. Технический отказ геолокации (нет доступа/таймаут) — просто тост с ошибкой, без похода к какой-либо территории.

**Убрана ручная точка входа в камеру**: пользователь прямо указал, что вручную можно только посмотреть сектор, но не сфотографировать улов. `TerritoryScreen.tsx` лишился кнопки «Поймать и занять/переоформить территорию» и пропа `onStartCatchFlow`; `FishZoneApp.startCatchFlow()` удалена — «+» (геолокация) остался единственным путём к камере. Заодно поправлена вводящая в заблуждение подпись кнопки на карточке карты (`MapScreen`: «Занять территорию» → «Подробнее о секторе» — она и раньше вела только на экран просмотра).

Проверено вручную на локальном деве (подмена `getCurrentPosition`): координаты в 636м от ближайшего сектора → маркер появился, модалка «Ты не на территории» показана, камера не открылась; координаты ровно в центре сектора B0144 → маркер появился там же, карта долетела до сектора и сразу открылась камера. Также обнаружено при проверке (не баг, полезная находка): продакшен уже используется реальными людьми — в БД настоящие уловы под настоящими email из предыдущего деплоя камеры, тестирование велось на отдельном свежем тестовом аккаунте, чтобы их не задеть.

## Начальный зум карты, кнопки +/− и «моё местоположение»

По запросу пользователя: при заходе карта была слишком отдалена (`fitBounds` по всем 703 секторам всего побережья Аджарии), плюс не было кнопок ручного управления зумом/местоположением (`zoomControl:false` изначально, под кастомную карусель).

**`LeafletMap.tsx`**: начальный вид вместо `map.fitBounds(bounds, {padding:[36,36]})` — `map.getBoundsZoom(bounds, false, L.point(36,36))` (тот же зум, что вычислил бы `fitBounds`) плюс `Math.log2(3)` уровней (в Leaflet каждый уровень зума удваивает масштаб, значит `+log2(3)` — это ровно тройное приближение), тот же центр через `bounds.getCenter()`. `LeafletMapHandle` пополнился `zoomIn()`/`zoomOut()` (обёртки над встроенными `map.zoomIn()`/`map.zoomOut()`) и `flyToLocation(lat, lng)` (как `flyToTerritory`, но по сырым координатам, не по id сектора).

**`MapScreen.tsx`**: три круглые кнопки справа от карты (`.map-controls`, вертикально по центру, между легендой и каруселью снизу) — приблизить/отдалить (сгруппированы в одну таблетку) и отдельно «моё местоположение» (иконка прицела). Кнопка геолокации не связана с потоком улова/«+» — просто `getCurrentCoords()` → ставит маркер (`showUserLocation`) и перелетает туда (`flyToLocation`), без проверки попадания в сектор и без камеры; при отказе/ошибке молча ничего не делает (та же семантика «никогда не бросает», что и у `getCurrentCoords`).

Проверено на локальном деве (подмена `getCurrentPosition`): открытие карты — сразу видны отдельные секторы, а не всё побережье целиком; «+» на кнопках зума явно приближает/отдаляет; кнопка местоположения ставит маркер и перелетает к нему.

**Персонализированная лента**: `useActivity()` без сессии — как раньше, публичная нефильтрованная; с сессией — только своё, подписки (но **не ретроактивно**, только начиная с момента подписки — уточнено пользователем после того, как первая версия без такого ограничения показала подписанному аккаунту в проверке пустую ленту вопреки ожиданиям), и «кто-то забрал твою территорию» (`previous_owner_id`). Фильтр по автору/владению — сервер, до `.limit(100)`; фильтр по времени подписки — клиент (PostgREST не выражает разный порог на разных авторов одним запросом).

**Баг, найденный и исправленный при проверке**: добавление `previous_owner_id` дало `activity_log` два FK на `profiles`, из-за чего старый select `profiles(display_name)` стал неоднозначным для PostgREST (300 «ambiguous relationship»). `ActivityScreen` не проверяет `isError`, поэтому упавший запрос тихо превращался в пустую ленту, а не в заметную ошибку — нашли только по факту, что лента была пуста там, где заведомо не должна была быть. Исправлено указанием конкретного FK: `profiles!activity_log_user_id_fkey(display_name)`.

Проверено на локальном деве двумя тестовыми аккаунтами: смена имени/аватара сохраняется и отражается сразу; подписка/отписка меняет счётчик подписчиков и кнопку; улов ДО подписки не показывается в ленте подписчика, улов ПОСЛЕ — показывается; лайтбокс открывается/закрывается корректно на всех трёх экранах. Тестовые аккаунты и их данные удалены после проверки (каскадом через `auth.users`, без сирот в `catches`/`activity_log`/`follows`).
