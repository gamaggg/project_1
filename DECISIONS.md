# FishZone — журнал технических решений

Здесь фиксируется **почему** сделано так, а не иначе — чтобы не переоткрывать одни и те же вопросы заново.

---

**Решение: один HTML-файл, без сборки/фреймворка**
Причина: это MVP/прототип для демонстрации и итеративной правки в чате. Сборка (React/Vite/etc.) добавляет накладные расходы без пользы на этой стадии. Если проект перейдёт в реальную разработку — потребуется миграция на нормальный стек (см. открытый вопрос ниже).

**Решение: Leaflet + OpenStreetMap вместо Google Maps / Mapbox**
Причина: не требует API-ключа и оплаты, достаточно для MVP. Минус: тайлы OSM по умолчанию визуально «пёстрые» — компенсировано CSS-фильтром (`grayscale/contrast`).

**Решение: сектора — явный список точек (`SECTOR_POINTS`), а не процедурная генерация вдоль линии берега**
Было перепробовано несколько процедурных подходов (сплайн через опорные точки берега + арк-length нарезка, две смещённые кривые земля/море). Все они работали математически корректно, но ошибка в **исходных координатах** (не в самой генерации) приводила к тому, что сектора уходили в город — и было тяжело понять, в геометрии баг или в данных. Явный список `{id, lat, lng}` на каждый сектор убирает эту неоднозначность: если сектор не на месте — правится ровно одна пара чисел, без побочных эффектов на соседей. Ориентация/размер по-прежнему считаются автоматически (по соседним точкам), так что вручную указывать угол поворота не нужно.
> **Заменено** (см. «Решение: сектора генерируются из реальных данных OSM» ниже) — `SECTOR_POINTS` и вся эта ручная подгонка координат удалены из кода. Оставлено здесь как история: те же уроки (не полагаться на одну глобальную линию/сплайн, ошибка в данных выглядит как баг геометрии) стояли за выбором подхода, которым эта проблема решена окончательно.

**Решение: ориентация сектора = направление от предыдущей точки к следующей (не отдельная «касательная берега»)**
Причина: убирает необходимость в отдельной модели береговой линии (второй источник правды). Каждый сектор буквально «смотрит» на своих соседей по списку — если список точек соответствует реальному изгибу берега, ряд секторов будет ему соответствовать.

**Решение: сектора — шестиугольники (соты), а не квадраты**
По явному запросу: соты плотнее стыкуются друг с другом без зазоров на изгибах, чем квадраты/прямоугольники, повёрнутые под фиксированным углом.

**Решение: перерисовка полигонов (`drawTerritories`) отделена от перерисовки карусели карточек (`renderMapSheet`)**
Было: `drawTerritories()` в конце вызывал `renderMapSheet()`, а `drawTerritories` был подписан на событие `zoomend`. `flyTo()` (при свайпе карточки) triggers `zoomend` → карусель каждый раз пересобиралась и сбрасывала скролл на первую карточку → это триггерило повторный `flyTo` на неё же → визуально «карта дёргается назад». Разделение вызовов устранило зацикливание. **Вывод на будущее**: не завязывать перерисовку геометрии карты и перерисовку независимого UI-компонента (карусели) на одно и то же событие без явной необходимости.

**Решение: сектора идентифицируются только числом (`id`), без названий/типов**
По явному запросу пользователя — упростили модель, убрали `name`/`type` из данных и из всех экранов, где они показывались (карточка сектора, карусель, подтверждение улова, успех, лента активности, профиль).
> **Уточнение**: на практике `name`/`type` были убраны из `SECTOR_POINTS`/`territories` не полностью — несколько шаблонов (карточка территории, карусель, подтверждение улова, лента активности, профиль) продолжали выводить `t.name`/`t.type` вплоть до перехода на `HEX_SECTORS` (см. ниже), то есть DOCS.md какое-то время не отражал реальный код. Это исправлено заодно с переходом на новые данные: `name` выведен окончательно, `type` в UI показывает `KIND_LABEL[t.kind]` (реальный тип воды из OSM — Море/Река/Ручей/Озеро), это не выдуманное название и не противоречит духу этого решения.

**Решение: полигоны через Leaflet `L.polygon` (SVG), а не CSS-div с `border-radius`**
Причина: как только сектора перестали быть простыми квадратами (шестиугольники, произвольная ориентация), CSS-div с фиксированным border-radius больше не подходит — SVG-полигон единственный вариант для точной формы/поворота на реальных геокоординатах.

**Решение: без localStorage/сохранения между сессиями**
В среде артефактов Claude localStorage не поддерживается технически. Для реального продукта — see «Открытые вопросы».

## Интеграция инструмента друга (tools/fishing-hex): гекс-сетка по реальным данным OSM

**Решение: сектора генерируются из реальных данных OpenStreetMap (`tools/fishing-hex`), а не из ручного списка ориентиров**
Причина: знакомый прислал независимо написанный инструмент — берёт реальную геометрию воды из OSM через Overpass API и режет её на честную гексагональную сетку 600м, оставляя только соты, которые физически касаются воды. Это снимает саму проблему, из-за которой раньше пришлось перейти на ручной `SECTOR_POINTS`: координаты воды теперь берутся из первоисточника (OSM), а не подбираются вручную по Google Places, поэтому сектора не могут «уйти в город» по ошибке ввода. Детали инструмента и как его перегенерировать — DOCS.md, раздел «tools/fishing-hex».

**Решение: полный охват побережья Аджарии (Сарпи–Чакви) и все 4 типа воды (море/река/ручей/озеро), а не только центр Батуми и только море**
Явный выбор пользователя (двумя вопросами) при интеграции: инструмент поддерживает такой охват «из коробки» (61 морская сота + 303 река + 320 ручьёв + 19 озёр = 703), решили не резать вручную обратно до масштаба старой версии (~24 точки в центре Батуми, только море).
Открытый вопрос из-за этого — см. ниже: приложение задумывалось и называется как «береговая морская рыбалка», а по факту стало «рыбалка у любой воды в Аджарии».

**Решение: id секторов — формат сетки инструмента (`"B0144"`), а не сквозной ручной номер**
id больше не придумывается вручную, а приходит из `build_hex.mjs` (порядковый номер в гекс-сетке инструмента). Из-за смены числа на строку пришлось поправить все места, где id подставлялся в `onclick`-атрибуты без кавычек (`onclick="openTerritory(${t.id})"` для строки — синтаксическая ошибка в разметке) — везде добавлены кавычки вокруг `${t.id}`.

**Решение: стартовые «моя»/«чужие» территории — явный список из 3 id (`B1127`/`B1126`/`B1079`)**
В сетке 703 сектора, вручную придумывать статус каждому смысла нет, но для узнаваемости демо-сценария (Пирс у Дельфинария / Marriott / порт, персонажи «Алексей»/«Марина») эти три id подобраны как ближайшие морские (`kind:'sea'`) соты к тем же трём координатам, что были у старых `SECTOR_POINTS` id 21/18/23. **Хрупкость**: если пересобрать `hex.geojson` с другим BBOX или `WIDTH_M`, эти конкретные id могут не существовать в новой сетке — seed молча пропустит недостающие (все сектора останутся `free`), понадобится заново найти ближайшие соты к тем же ориентирам (как сделано один раз в этой сессии — см. `tools/fishing-hex/extract_sectors.mjs` для формата данных, поиск ближайшего делался разовым скриптом, не сохранён в репозитории).

**Решение: id-подписи секторов на карте показываются только при `zoom >= 14`, полигоны — всегда**
При 703 секторах на весь берег все подписи разом на далёком зуме (когда виден весь berег целиком) визуально сливаются в нечитаемое месиво текста — проверено вживую при интеграции. Статус-цвет сектора (мой/чужой/свободный) — самая важная информация на дальнем зуме — остаётся виден всегда; подписи включаются только когда пользователь уже приблизился к конкретному участку и они читаемы.

**Решение: `preferCanvas:true` на карте Leaflet**
С ростом числа секторов до 703 рисовать каждый шестиугольник отдельным SVG-узлом (поведение Leaflet по умолчанию) стало бы граничным по производительности; canvas-рендер держит все полигоны на одном холсте. Замер в этой сессии: `drawTerritories()` для всех 703 секторов ≈5мс на canvas — с запасом.

## Миграция в веб-сервис: Next.js + Supabase + Vercel

Пользователь решил делать не прототип, а настоящий веб-сервис — многопользовательский, с реальными аккаунтами. Ниже — решения, зафиксированные при переходе (все — явный выбор пользователя через вопросы в чате, не решены за него).

**Решение: стек — Next.js + Supabase (Postgres/Auth) + Vercel**
Причина: в сессии уже были подключены MCP-инструменты обоих сервисов — прямой намёк на связку, и она же самая быстрая для этого масштаба (React-фреймворк с бэкендом на одном языке, БД+Auth из коробки, деплой в один клик). Другие стеки не оценивались.

**Решение: `web/` — соседняя папка в том же репозитории (монорепо), `fishzone-app.html`/`tools/fishing-hex/` не трогаются**
Причина: `tools/fishing-hex` — общий источник геометрии для обоих поколений (прототип и веб-сервис), логично держать их рядом. Прототип оставлен как есть — исторический референс дизайна, из которого `web/` был перенесён, не удалён и не обновляется дальше.

**Решение: дизайн/экраны переносятся 1:1, кроме фейковой рамки телефона/статус-бара — их убрали**
`.device`/`.statusbar`/`.notch` в прототипе существовали только для превью в браузере на десктопе (эмуляция экрана iPhone 390×844). В реальном вебе, открытом на настоящем телефоне, это стало бы вторым статус-баром поверх настоящего — решили убрать, заменив на честную адаптивную вёрстку (`.app-shell{max-width:480px;margin:0 auto}` — full-bleed на мобильном, по центру на десктопе). Все цвета/радиусы/тени/шрифт/компонентные классы (`.card`, `.btn-primary`, `.badge-*`, и т.д.) перенесены из `fishzone-app.html` практически дословно — см. `web/app/globals.css`.

**Решение: авторизация сразу и по-настоящему — Supabase Auth, email+пароль**
Причина: территории должны принадлежать реальным людям, не одному демо-юзеру — иначе «веб-сервис» не отличался бы от прототипа по сути. Email+пароль выбран для v1 вместо magic link/OAuth — не требует настройки внешних OAuth-приложений или зависимости от доставки писем для самого входа (регистрация всё равно требует подтверждения email — это дефолт Supabase, не отдельная настройка, см. DOCS.md).

**Решение: карта/территории/лента активности публичны без входа; вход нужен только для записи (улов/захват территории)**
Strava-style: смотреть чужие уловы и карту может кто угодно, вход — только когда хочешь сам что-то сделать. Реализовано через RLS `select using (true)` на всех таблицах + проверку сессии в `FishZoneApp.startCatchFlow` (редирект на `/auth`, а не тихий no-op).

**Решение: все 703 территории стартуют свободными — никаких demo-аккаунтов вместо старых `B1127`/`B1126`/`B1079`**
Причина: раз территории теперь принадлежат настоящим людям, подсовывать фиктивных «Алексея»/«Марину» как реальные аккаунты — обман; создавать реальные тестовые аккаунты только ради демо-заполненности карты тоже не имеет смысла для только что запущенного сервиса. Карта просто пустая (все свободны), пока реальные пользователи её не заполнят.

**Решение: геометрия секторов — статический JSON-ассет (`web/public/data/sectors.json`), не строки в Postgres**
Причина: 6 вершин × 703 сектора никогда не меняются в рантайме и не нужны для RLS/агрегаций — гонять их через БД на каждый запрос бессмысленно. В Postgres — только «тонкая» `territories` (id/kind/lat/lng/owner_id) для целостности FK (`catches`/`activity_log` ссылаются на неё) и владения. См. DOCS.md, раздел «База данных».

**Решение: `catch_count`/`last_catch_at` — вью с агрегацией (`territories_with_stats`), не денормализованные колонки**
Причина: 703 территории — агрегация по `catches` дешёвая при любом разумном трафике; денормализация потребовала бы триггеров и создала риск рассинхронизации ради экономии, которая тут не нужна.

**Решение: запись только через RPC (`confirm_catch`), не прямые INSERT/UPDATE от клиента**
Причина: `confirmCatch()` в прототипе атомарно делает три вещи (улов, смена владельца, запись в ленту) — RPC с `SECURITY DEFINER` и `select … for update` на строке территории повторяет то же самое атомарно и безопасно при параллельном заходе двух пользователей на одну свободную территорию (кто первый — тот и получил). Прямые insert/update-политики клиентам не выданы: без RPC создать улов без реального `auth.uid()` или подделать владение нельзя.

**Решение: единый клиентский app-shell со стейт-машиной экранов, а не отдельные Next.js-роуты на каждый экран**
Причина: переходы-кроссфейды между 7 экранами и эфемерный `pendingCatch` (камера→подтверждение) проще и надёжнее перенести как React-стейт в одном компоненте (`FishZoneApp.tsx`), как это было устроено в прототипе (`goTo()`/`currentScreen`), чем резать на роуты — ни один экран сейчас не должен быть шаримой ссылкой, а настоящая навигация браузера рисковала бы потерять `pendingCatch` между камерой и подтверждением.
> **Уточнение**: изначально `/auth` был единственным отдельным роутом вне shell — позже убран целиком (см. «Форма входа встроена в профиль» ниже), теперь весь app-shell — один роут (`/`), без исключений.

**Решение: Realtime-подписки Supabase — не в v1, обновление на фокусе вкладки (`@tanstack/react-query`, `refetchOnWindowFocus`)**
Причина: проще для первой версии; переход на Realtime позже — локальное добавление (инвалидация query на `postgres_changes`), не переписывание архитектуры данных.

**Решение: `lib/supabase/client.ts` — синглтон, не фабрика нового клиента на каждый вызов**
Наступили на грабли в этой же сессии: с фабрикой (`createBrowserClient()` при каждом `createClient()`) форма входа создавала СВОЙ экземпляр Supabase-клиента, отдельный от того, на который подписан `AuthProvider` — `onAuthStateChange` срабатывает только на экземпляре, который сам выполнил вход/выход, поэтому после логина `AuthProvider` не узнавал о новой сессии без полной перезагрузки страницы (первый прогон end-to-end теста «поймать рыбу» упал именно на этом — `startCatchFlow` считал пользователя неавторизованным сразу после успешного входа). Починено модуль-левел синглтоном. **Вывод на будущее**: Supabase-клиент в браузере должен быть один на вкладку, если где-то в приложении есть больше одного места, которое его создаёт и на него подписывается.

**Решение: Next.js 16 — используем `proxy.ts` вместо `middleware.ts`**
В установленной версии (16.3.4, новее тренировочных данных модели — увидели явное предупреждение в `web/AGENTS.md`, которое Next.js сам кладёт в свежий проект) файл-конвенция `middleware.ts`/`export function middleware` переименована в `proxy.ts`/`export function proxy`; механика (cookies, matcher, `NextResponse`) не изменилась. Узнали из `node_modules/next/dist/docs/` перед тем как писать код, а не через ошибку компиляции постфактум.

**Решение: Node.js скачан локально в `.tools/node/` (не установлен системно, не через nvm/Homebrew — их тоже не было)**
В среде разработки не оказалось вообще никакого JS-тулчейна (ни `node`, ни `npm`, ни менеджера версий, ни Homebrew). Вместо системной установки (нет sudo/доступа к системным путям от инструмента) — скачан официальный tar.gz с nodejs.org (v24 LTS, «Krypton», arm64) и распакован в `.tools/node/` внутри репозитория, добавлен в корневой `.gitignore`. Все npm/node-команды в этой и будущих сессиях требуют `export PATH=".../.tools/node/bin:$PATH"` перед запуском — шелл-стейт инструмента не персистится между вызовами, окружение задаётся заново каждый раз (это не изменение системы пользователя, никакие системные файлы/PATH не тронуты за пределами репозитория).

**Решение: первый Vercel-проект удалён и создан заново через обычный Import, а не починен на месте**
При первом подключении (через MCP `create_git_project`, упавший на 403 из-за нерабочей авторизации коннектора) в аккаунте пользователя откуда-то появился проект `project-1`, автоматически привязанный к `gamaggg/project_1` — по всей видимости, сработал стандартный auto-detect Vercel для только что запушенного репозитория, независимо от наших действий. У этого проекта на всех проверенных доменах (включая собственный уникальный URL конкретного деплоя, не только кастомный алиас) стабильно был 404 `NOT_FOUND` на уровне Vercel edge — при этом сборка была полностью успешной (логи показывали корректный роут `/`), а в Runtime Logs не было вообще ни одного request-лога, то есть запросы не доходили до функции вообще, останавливаясь на маршрутизации домена. Ни смена Root Directory, ни отключение Deployment Protection, ни повторные Redeploy (в т.ч. без билд-кэша) это не поправили. Решили не разбираться дальше в природе поломки — удалили проект (Settings → Advanced → Delete Project) и создали новый через обычный флоу Import (карточка «New repository detected» → Root Directory/env переменные выставлены сразу при импорте). Новый проект заработал с первого деплоя. **Вывод на будущее**: если у только что созданного/auto-detected Vercel-проекта домен стабильно 404-ит на пустых Runtime Logs при зелёной сборке — это, похоже, дешевле починить пересозданием проекта через Import, чем разбираться, в каком именно внутреннем состоянии Vercel он застрял.

**Решение: деплой в итоге сделан руками пользователя через веб-интерфейс Vercel, не через MCP**
MCP-коннектор Vercel был доступен по имени инструментов, но каждый вызов (`list_teams`, `create_git_project`, `get_deployment`, …) отдавал `403 Not authorized: ... re-authenticate to this scope` независимо от того, какой teamId передавался (`personal`, `gamag`, реальный `team_...` id из тела ошибки) — то есть сам токен коннектора был нерабочим, а не просто неверно указан scope. Штатных инструментов «переподключить коннектор»/получить ссылку авторизации в рамках этой сессии не нашлось (`suggest_connectors`/`list_connectors` не видели Vercel как переключаемый коннектор вообще — судя по всему, это отдельная интеграция уровня Claude Code/аккаунта, не обычный MCP-коннектор). Пользователь прошёл весь путь (создание env-переменных, Root Directory, Deployment Protection, удаление и пересоздание проекта) вручную по скриншотам, я только читал логи/статусы через Browser-инструмент (у которого доступ к самим *.vercel.app URL не требует авторизации Vercel API) и давал следующий шаг.

**Решение: Confirm email временно выключен в Supabase Auth**
При первой же попытке пользователя зарегистрироваться на проде словили `email rate limit exceeded` — дефолтный (не настроенный отдельно) email-сервис Supabase имеет очень маленький лимит писем, аккаунт при этом не создаётся вообще (падает до записи в БД, подтверждать через SQL было нечего, в отличие от более раннего теста в этой же сессии). Чтобы не блокировать тестирование, выключили Confirm email (Dashboard → Authentication → Sign In / Providers) — регистрация теперь сразу даёт активную сессию. **Это временно**: без подтверждения email любой человек может зарегистрироваться на чужой email без проверки владения им — приемлемо, пока сервис не публичный, но перед реальным запуском нужно либо вернуть подтверждение вместе со своим SMTP-провайдером (снимет лимит), либо осознанно решить, что подтверждение почты вообще не нужно для этого продукта.

**Решение: форма входа встроена в screen-profile, отдельного роута `/auth` больше нет**
По прямому запросу пользователя после первого раунда тестирования на проде: раньше «+» без сессии редиректил на `/auth`, а вкладка «Профиль» без входа показывала пустую заглушку (плейсхолдеры вместо имени/статистики) — два разных места для одного и того же «нужен вход», нелогично. Теперь `AuthForm.tsx` (вынесена из бывшего `app/auth/page.tsx` в переиспользуемый компонент, без `router.push`) рендерится прямо в `ProfileScreen`, когда `user` пуст — и «+», и сама вкладка «Профиль» ведут в одно и то же место. Успешный вход/регистрация ничего никуда не редиректит: `AuthProvider` реактивно обновляет `user`, `ProfileScreen` сам переключается с формы на настоящий профиль. По той же причине «Выйти» сразу возвращает форму входа на этом же экране — это просто следствие того, что рендер экрана целиком зависит от `user`, а не отдельное поведение кнопки.
`app/auth/` (папка) удалена; `.auth-wrap` (CSS для полноэкранной раскладки формы) убран как мёртвый, `.auth-card` получил `margin:0 auto` для центрирования внутри `.screen-inner`.

## Геолокация, форма улова, расширенный справочник видов

По прямому запросу пользователя: реалистичный поток «встал на секторе → «+» → сразу камера → фото → форма (вид рыбы обязателен, остальное по желанию) → подтвердить», плюс расширение списка рыб с 3 до 36 (с разделением на морских/пресноводных). Первое изменение с момента переноса в веб-сервис, которое трогает схему БД — сделано через план (`EnterPlanMode`), не итеративно.

**Решение: список видов — то, что пользователь прислал текстом, а не то, что распознал голосовой ввод**
Первая попытка (голосом) дала нечёткий список с нераспознанными названиями («Zubar», «Testava») — переспросил, пользователь прислал точный список текстом: 23 морских (Ставрида, Барабуля, Кефаль, Морской бычок, Морская собачка, Сарган, Луфарь, Морской карась, Скорпена, Смарида, Горбыль, Каменный окунь, Пеламида, Морской дракон, Звездочёт, Скат, Катран, Чёрноморская сельдь, Мармир, Зубарь, Морской петух, Радужная форель, Черноморская форель) + 13 пресноводных (Речная форель, Кумжа, Голавль, Усач, Сазан, Карп, Карась, Щука, Судак, Окунь, Сом, Амур, Толстолобик). Старый enum (`stavrida`/`skorpena`/`laskir`) заменён целиком — `laskir` в новый список не попал (пользователь не включил), `stavrida`/`skorpena` сохранили те же ключи по смыслу.

**Решение: справочник видов — таблица `species` в БД, а не хардкод в TS**
36 записей с категорией (`marine`/`freshwater`) — это уже не маленький фиксированный список вроде `METHODS`/`BAITS` (которые остались в TS как были), а полноценный справочник, который может расшириться позже без передеплоя фронтенда. `catches.species` стал текстовым FK на `species.key` (раньше был Postgres enum `catch_species` — enum пришлось бы менять миграцией `ALTER TYPE ... ADD VALUE` на каждое добавление вида, что и негибко, и нельзя откатить в одной транзакции; текстовый FK такого ограничения не имеет).

**Решение: категория вида по умолчанию — от типа территории (`kind`), но переключаема**
`sea` → сразу «Морская», `river`/`stream`/`lake` → «Пресноводная» (`categoryForKind()`). Меньше кликов в типичном случае (рыбак почти всегда ловит то, что водится в этом типе воды), но не жёстко — вдруг он поймал что-то нетипичное или геолокация ошиблась с сектором.

**Решение: геолокация запрашивается только по нажатию «+», не автоматически на карте**
Карта публична и не требует входа (более раннее решение) — запрашивать разрешение на геолокацию у анонимного посетителя, который просто листает карту, было бы навязчиво и не нужно для этого действия. «+» уже требует вход, так что момент запроса геолокации совпадает с моментом, когда она реально нужна. Порог «человек на этой соте» — 400м от центра (сота 600м шириной, запас на неточность GPS); `getCurrentPosition` разовый на каждое нажатие, не фоновый `watchPosition` (проще, не жжёт батарею фона, свежие координаты важнее в момент фиксации улова, чем постоянное слежение).

**Решение: при неудачной геолокации — fallback на вручную открытую территорию, потом тост с ошибкой**
Не блокирует поток совсем: если геолокация отказала/недоступна/слишком далеко от всех секторов, но пользователь до этого сам открыл территорию (карта/список) — используем её. Только если вообще ничего не выбрано — тост «выбери территорию на карте».

**Решение: карта долетает до найденной по геолокации территории сразу, ещё до открытия камеры**
`MapScreen` стал `forwardRef`, прокидывает `flyToTerritory` от внутреннего `LeafletMap` наверх в `FishZoneApp` — тот же паттерн, что уже применялся для карусели (`LeafletMap`→`MapView`). Карта не размонтируется при переходе на другие экраны (только визуально скрыта через `.screen`), поэтому `flyTo` можно вызвать, даже когда в этот момент показана камера — когда пользователь потом вернётся на карту, она уже там.

**Решение: размер/вес/способ/наживка — необязательные (в форме и в БД), обязателен только вид рыбы**
Соответствует тому, как реально фиксируют улов на бегу — не всегда есть время/желание взвешивать и измерять рыбу. `catches.length_cm`/`weight_kg`/`method`/`bait` переведены в nullable (`alter column ... drop not null`), RPC `confirm_catch` — параметры с `default null`. Клиент передаёт `null`, но сгенерированные TS-типы для RPC-аргументов ожидают `undefined` для необязательных полей — на вызове `?? undefined` (иначе TS-ошибка `null` не назначается в `T | undefined`).

**Решение: «Коллекционер видов» пересчитан под новый список — 5 морских видов вместо «поймать все»**
Старая ачивка требовала поймать все 3 (из 3) видов — со старым списком это было «поймать вообще всё». С 23 морскими видами требовать «все» — нереалистичная планка для геймификационной вехи; вместо этого — фиксированный таргет (5 разных морских видов), учитываются только `category:'marine'` уловы (пресноводные виды не считаются — ачивка описана именно как «рыба Чёрного моря»).

**Решение: `personalRecord()` учитывает только уловы с указанным размером**
Раз размер необязателен, `reduce` по всем уловам (включая без размера) был бы некорректен — фильтруем на `lengthCm !== null` перед сравнением; если ни разу не указали размер — рекорда нет вообще (секция «Личный рекорд» на профиле не показывается), а не берётся случайный/нулевой улов.

## Настоящая камера, обязательное фото, интро-экран

Пользователь увидел живую геолокацию на своём телефоне (реальные координаты в скриншоте) и запросил: убрать GPS-чип с экрана камеры (логика сопоставления координата↔сектор остаётся, просто не показывается) и заменить симулированную камеру на настоящую (`getUserMedia`), с интро-экраном перед запросом доступа. Первый черновик плана предложил «мягкие» фолбэки (пропустить фото при отказе камеры, не блокировать сабмит при неудачной загрузке) — пользователь их явно отклонил в рецензии плана; ниже — решения после правки.

**Решение: фото обязательно на уровне данных, не только UI — `catches.photo_url` NOT NULL, RPC-параметр без дефолта**
Пользователь прямым текстом: «без загрузки фото улов засчитывать нельзя». Раньше это было бы просто необязательным полем формы — теперь это структурное ограничение: без успешно загруженного в Storage фото запрос к `confirm_catch` физически невозможен (обязательный `p_photo_url`, кнопка сабмита задизейблена без него). Нет пути «отправить улов без фото» ни в UI, ни в БД.

**Решение: при отказе/ошибке камеры — только повтор запроса, никакого «продолжить без фото»**
Пользователь явно отклонил вариант с пропуском фото. `CameraScreen` в состоянии `denied` показывает объяснение и единственную кнопку «Запросить доступ снова» (тот же `getUserMedia`-вызов, что у интро) — выйти можно только назад на карту (×), не мимо камеры.

**Решение: загрузка фото в Storage стартует сразу после кадра, не при отправке формы**
Пользователь: «сразу после того как пользователь фоткает, показывается экран с превью фото и полями формы» — то есть превью и форма на одном экране сразу, а не как отдельный шаг. Раз пользователь в это время всё равно заполняет форму (вид рыбы и т.д.), логично параллелить загрузку с вводом, а не заставлять ждать после нажатия «Подтвердить». `FishZoneApp.handleCapture(blob)` переключает на `screen-confirm` и одновременно запускает `uploadCatchPhoto` — статус (`uploading`/`success`/`error`) живёт в `FishZoneApp`, не в `ConfirmScreen`, потому что должен пережить сам факт того, что `ConfirmScreen` — это просто рендер текущего состояния формы, а не источник правды про загрузку.

**Решение: неудачная загрузка — сообщение + «Повторить попытку» поверх фото, не возврат к камере**
Пользователь: «пишем о том, что загрузка не удалась, и кнопка повторить». Повтор переиспользует уже снятый `Blob` (`capturedPhoto` хранится в `FishZoneApp` до сабмита/возврата) — не нужно переснимать фото заново, только перезалить тот же файл. Кнопка «Подтвердить улов» остаётся задизейблена всё это время (`photoStatus !== 'success'`).

**Решение: `srcObject` подключается к `<video>` через `useEffect`, а не сразу в обработчике клика**
Наступили на грабли при первой ручной проверке: `<video>` рендерится в JSX только при `state==='live'`, поэтому в момент, когда промис `getUserMedia` резолвится (ещё в состоянии `requesting`), `videoRef.current` — `null` (элемента ещё нет в DOM), присвоение `videoRef.current.srcObject = stream` в обработчике клика молча не срабатывает (поток получен, но экран остаётся чёрным). Исправлено: обработчик только сохраняет `stream` в `streamRef` и переключает состояние; отдельный `useEffect`, срабатывающий по смене `state`, подключает `streamRef.current` к `videoRef.current` уже после того, как `<video>` смонтирован. **Вывод на будущее**: если элемент рендерится условно по стейту, любой сайд-эффект, которому нужен ref на этот элемент, должен идти через `useEffect` от того же стейта, а не синхронно в обработчике, который этот стейт только устанавливает.

**Решение: `CameraScreen` получает `key={cameraSessionId}` (счётчик) от `FishZoneApp`, а не полагается на внутренний сброс состояния**
Экраны в этом приложении не размонтируются при переключении (см. более раннее решение про единый app-shell со стейт-машиной) — виден только CSS-класс `.active`. Значит `CameraScreen` — один и тот же React-инстанс на все заходы в камеру за сессию. Без явного сброса второй заход (новый улов после первого, или возврат из `ConfirmScreen` кнопкой назад) заставал бы компонент в состоянии `live` от прошлого раза, но с уже остановленным (`track.stop()` вызван после кадра) потоком — застывший чёрный кадр вместо новой попытки снять фото. Обнаружено и исправлено в этой же сессии при сквозной проверке (см. CHANGELOG.md). `FishZoneApp` инкрементирует `cameraSessionId` в каждом месте, откуда открывается камера (`startCatchFlow`, оба выхода `handlePlus`, `backToCamera` — кнопка «назад» с экрана подтверждения) и передаёт его как `key` — React полностью размонтирует/пересоздаёт `CameraScreen` (со свежим `state:'intro'`), вместо попытки вручную дозачищать внутренний стейт компонента снаружи.

**Решение: кадр — офскрин `<canvas>` с даунскейлом до 1280px, JPEG 0.85, поток останавливается сразу после `drawImage`**
1280px по ширине — достаточно для отображения в карточках/превью, не раздувает Storage/трафик мобильного пользователя на берегу. Поток останавливается синхронно сразу после отрисовки кадра в canvas (`stopStream()` до асинхронного `canvas.toBlob`) — индикатор камеры на телефоне гаснет как можно раньше, кодирование JPEG может идти и без активного потока.

## Метка геолокации на карте, «+» — единственный путь к камере

По прямому запросу пользователя, уточняющему суть геолокации: при определении местоположения на карте должна появляться метка (где именно находится человек), и результат должен быть однозначным — либо сектор найден и после фото он автоматически засчитывается, либо человек не на воде, и это явно сообщается, а не тихо подменяется чем-то другим.

**Решение: маркер позиции ставится на карту при любом успешном `getCurrentPosition`, независимо от того, попадает ли точка в сектор**
Раньше `handlePlus()` использовал координаты только для расчёта ближайшего сектора и никак их не визуализировал. Теперь `LeafletMapHandle` получил `showUserLocation(lat, lng)` — синяя точка с пульсацией, ставится сразу после получения координат, до проверки на попадание в сектор. Это отдельный маркер вне `markersLayer` (который целиком перерисовывается при смене владения секторами) — не должен пропадать/мигать от перерисовок полигонов.

**Решение: если координаты получены, но ни один сектор не найден в радиусе 400 м — модальное окно, а не тихий фолбэк**
Раньше (см. более раннее решение про геолокацию) при неудаче — и техническом отказе, и промахе мимо всех секторов — код одинаково пытался подставить `activeTerritoryId` (ранее вручную открытую территорию) как фолбэк, а при его отсутствии — тост с подсказкой выбрать сектор на карте. Пользователь явно разделил эти два случая: если геолокация технически не сработала (отказ/таймаут) — просто тост с ошибкой; если координаты получены, но человек не стоит ни на одном секторе (например, в центре города) — отдельное блокирующее модальное окно «Ты не на территории», объясняющее, что зафиксировать улов не получится. `.modal-overlay`/`.modal-card` — новый переиспользуемый паттерн в `globals.css` (`position:absolute` внутри `.app-shell`, а не `fixed` на весь viewport — иначе на десктопе перекрыло бы всё окно браузера, а не только карточку приложения).

**Решение: `TerritoryScreen` (ручной выбор сектора) — только просмотр, кнопки «поймать»/«занять» больше нет**
Пользователь прямым текстом: «вручную можно только смотреть подробнее о секторе, нельзя вручную выбрать сектор и сфоткать улов». Раньше клик по кнопке на экране территории (`onStartCatchFlow`) открывал камеру напрямую для этого сектора, в обход геолокации — это был единственный путь начать улов без «+». Убран целиком: `startCatchFlow` в `FishZoneApp` удалена (не осталось вызывающих), `TerritoryScreen` больше не принимает `onStartCatchFlow`. Теперь камера открывается **только** через `handlePlus()` — единая точка входа, без исключений. Заодно поправлены подписи кнопок, которые обещали действие вручную (`MapScreen`: «Занять территорию» → «Подробнее о секторе» — карточка карусели и раньше только открывала `TerritoryScreen`, не претендовала на большее, но текст вводил в заблуждение).

**Решение: `nearestTerritory(lat, lng, territories)` вынесена из `findMyTerritory` как чистая функция, отдельно от получения координат**
Раньше `findMyTerritory()` делала всё за один вызов (координаты → сразу ближайший сектор или `null`), чего было достаточно, пока результат координат никак не показывался. Теперь маркер на карте должен появиться независимо от результата поиска сектора — понадобились координаты как отдельное значение до, а не только внутри, вычисления совпадения. `lib/geolocation.ts`: `getCurrentCoords()` (получение точки, никогда не бросает) + `nearestTerritory()` (чистая функция расстояния, тестируема без браузерных API).

## Убраны сектора над «микро-ручьями» (порог длины водотока)

Пользователь прислал скриншот с продакшена: кластер соседних `stream`-секторов над лесистым/горным участком без видимой воды на тайле — технически касаются OSM-линии `waterway=stream`, но по факту незначительные ручьи/канавы, не места для рыбалки. Попросил убрать подобные.

**Решение: фильтр по суммарной длине связного водотока (порог 800м), не по отдельному OSM-way и не по тегу**
У 587 линий-ручьёв в bbox почти нет метаданных о размере — именованы только 8. Единственный доступный сигнал — геометрическая длина. Но считать по отдельному OSM-`way` нельзя: мапперы часто режут один и тот же физический ручей на много мелких сегментов (пересечения дорог, административные границы и т.п.) — наивная длина одного фрагмента ничего не говорит о размере настоящего ручья. Решение: склеить связанные `waterway`-way (кроме `river`) в целые водотоки union-find'ом по общим id узлов OSM, считать суммарную длину каждого водотока, и уже её сравнивать с порогом (`STREAM_MIN_LENGTH_M = 800` в `build_hex.mjs`). River-сегменты в склейку не включаются намеренно: иначе крошечный приток, впадающий в большую реку через общий узел, унаследовал бы длину всей реки, и порог перестал бы что-либо отличать.

**Порог подобран экспериментально, не теоретически**: прогнали симуляцию на реальных данных при разных порогах (100–1000м) и посмотрели, что реально удаляется. 400м — безопасно (не задевает ни одной уже занятой территории), но не убирает ни одного сектора со скриншота пользователя. 800м — убирает ровно те сектора со скриншота (6 из 8) и ещё 39 похожих по всему bbox (итого 45 из 703, все `kind:'stream'`, 320→275); выбран пользователем явно, после того как ему показали оба варианта с count'ами.

**Решение: сектор `B1313` (единственный из 45 с реальным уловом) удалён вместе с остальными, не защищён отдельно**
Изначально предполагалась защита уже занятых секторов от удаления геометрическим фильтром (чтобы не терять реальные данные пользователей). Пользователь уточнил текстом: улов на `B1313` — тест его друга, никакой ценности как реальные данные не несёт, защищать не нужно. Перед удалением строки `territories` вручную почищены зависимые `activity_log` (id 13, 14) и `catches` (id 7) — иначе упал бы FK. Фото в Storage осталось сиротой (прямой `delete` в `storage.objects` заблокирован Supabase, `storage.protect_delete()`) — не мешает, как и два похожих осиротевших файла из более ранней сессии тестирования камеры.

**Вывод на будущее** (см. также обновлённый раздел в DOCS.md «tools/fishing-hex»): теперь, когда территориями реально владеют живые пользователи, регенерация сетки — больше не безобидная операция «переисполнить один скрипт». Перед удалением любого id из `sectors.json`/`territories` нужно проверять, нет ли на нём реальных `catches`/`owner_id`, и осознанно решать (сохранить/расчистить), а не полагаться на автоматическое исчезновение строки, как было до запуска в прод.

## Полноразмерное фото, аватар/имя, публичные профили и подписки, персонализированная лента

Четыре связанных запроса пользователя за один заход: лайтбокс для фото уловов, редактирование имени/аватара (без email), публичные страницы других рыбаков с подпиской, и лента активности, показывающая либо только своё (+ уведомления о потере территории), либо ещё и подписки.

**Решение: `followers_count` (статичная колонка-заглушка) заменена на вью `profiles_with_stats`, не превращена в триггер-поддерживаемый счётчик**
Тот же паттерн, что уже был выбран для `territories_with_stats` (см. решение выше в этом файле) — агрегация `count(*) from follows` дешева при разумном числе подписчиков, триггер на каждый `insert`/`delete` в `follows` добавил бы риск рассинхронизации ради экономии, которая не нужна на этом масштабе. Старая колонка `profiles.followers_count` удалена полностью (не переименована/не оставлена как deprecated) — она была буквально всегда 0, ничего не хранила, оставлять её рядом с работающим счётчиком было бы просто мёртвым полем.

**Решение: подписка/отписка — прямой `insert`/`delete` в `follows` с клиента, без RPC**
В отличие от `confirm_catch` (три таблицы, атомарность, блокировка строки от гонки), подписка — одна строка в одной таблице под RLS «можешь писать только свою». Оборачивать в `SECURITY DEFINER` RPC ради этого — не по делу; политики `insert ... with check (auth.uid() = follower_id)` / `delete ... using (auth.uid() = follower_id)` полностью достаточны.

**Решение: подписка не ретроактивна — в ленте только то, что подписанный сделал ПОСЛЕ подписки**
Первая реализация фильтровала `activity_log` только по `user_id in (подписки)`, без учёта времени — при проверке (два тестовых аккаунта, улов сделан ДО подписки) пользователь уточнил текстом: ожидание — уведомления только на новые уловы после подписки, не ретроактивная загрузка всей истории подписанного. Так и для реальных соцсетей интуитивнее: подписка — это «показывай мне, что будет дальше», не «вывали всю историю разом». Технически: `follows.created_at` сравнивается построчно с `activity_log.created_at` для каждого автора — PostgREST не может выразить разный порог для разных `user_id` в одном фильтре, поэтому это отдельный проход на клиенте поверх уже полученных (и уже суженных сервером до «моё + подписки + отняли территорию») строк, не полный клиентский фильтр с нуля — так не теряется защита от вытеснения топ-100 глобальной активностью.

**Решение: «увели территорию» — новая колонка `activity_log.previous_owner_id`, не вью с window-функцией**
Нужно было понять, что данный `'claim'` — это территория, которая раньше принадлежала текущему пользователю. Рассматривался вариант с `LAG()` по истории `claim`-строк на территорию (посчитать «предыдущего владельца» постфактум из истории). Отклонён: `confirm_catch` RPC уже вычисляет `v_prev_owner` в момент захвата (нужен для решения, писать ли `'claim'` вообще) — сохранить уже известное значение в новую колонку на порядок проще и надёжнее, чем восстанавливать его позже оконной функцией по всей таблице. Побочный эффект, на который наступили при первой реализации: у `activity_log` теперь два FK на `profiles` (`user_id`, `previous_owner_id`) — старый select с `profiles(display_name)` стал неоднозначным для PostgREST (300 «ambiguous relationship»), пришлось явно указать `profiles!activity_log_user_id_fkey(display_name)`. Ловушка была тем незаметнее, что `ActivityScreen` не проверяет `isError` — ошибка запроса тихо превращалась в пустую ленту («Пока нет активности»), а не в видимую ошибку; сам факт бага нашёлся только потому, что лента была ПУСТОЙ там, где заведомо не должна была быть.

**Решение: имя/аватар — модалка на экране профиля, не отдельный роут/экран**
Тот же принцип, что уже применён для входа (встроен в `screen-profile`, не отдельная `/auth`) — маленькая, самодостаточная форма не заслуживает собственного места в стейт-машине экранов `FishZoneApp`. Аватар грузится сразу по выбору файла (без промежуточного шага подтверждения) — решение сразу применяется (`useUpdateProfile({avatarUrl})`), как и с фото улова, ждать нажатия отдельной кнопки незачем.

**Решение: email — `<input disabled>` с явной подписью, а не просто отсутствующее поле**
По запросу пользователя («нельзя менять почту»). RLS и так не позволяет менять `auth.users.email` через `profiles` (это разные таблицы), так что можно было бы просто не показывать email в форме вообще — но явное «Email нельзя изменить» рядом с видимым (но неактивным) значением понятнее, чем молчаливое отсутствие поля, которое выглядело бы как недоделанная форма.

**Решение: список территорий/уловов чужого профиля — фильтрация уже загрученных данных, не новые запросы (кроме уловов)**
`FishZoneApp` уже держит в памяти полный массив `territories` (не про сектор — про ВСЕ 658, с `ownerId`) для карты; чужие территории — просто `territories.filter(t => t.ownerId === viewedUserId)`, без похода в БД. Уловы так не переиспользовать (нет глобального списка «все уловы всех» в памяти) — `useCatchesByUser(userId)` стал параметризованной версией того, что раньше было только `useMyCatches()` (теперь однострочная обёртка над ней).

**Решение: точки входа на чужой профиль — имя в ленте активности и владелец в карточке территории, отдельного поиска/каталога рыбаков нет**
Пользователь попросил «заходить на страницы других рыбаков», не «искать рыбаков» — этого достаточно для органического обнаружения (увидел чужой улов в ленте или на территории — зашёл к автору), отдельный экран поиска/каталога никто не просил, и создавать его сейчас — угадывать нереализованное требование.

## Позиционирование модалок, навигационный стек, бейдж непрочитанных уведомлений

Пользователь прислал скриншот бага на реальном десктопном Chrome (фото улова открывалось «оторванным», прибитым к верху экрана, а не там, где был проскроллен экран) и попросил три вещи: починить это, сделать так, чтобы кнопка «назад» всегда вела на реальный экран, с которого пришли, и добавить бейдж непрочитанных уведомлений с точками на новых записях и кнопкой «Прочитать все».

**Решение: `PhotoLightbox`/`EditProfileModal` рендерятся на уровне `FishZoneApp`, а не внутри экрана, который их открыл**
Диагностировано вживую через `getBoundingClientRect()` в браузере: `top` оторванного оверлея точно совпадал по модулю с `scrollTop` скроллящегося `.screen`, внутри которого он был смонтирован — то есть корень проблемы не в CSS-правиле самого оверлея, а в том, что `position:absolute; inset:0` внутри containing block, который сам является `overflow-y:auto`-контейнером, отсчитывает `0` от верха *контента* этого контейнера, а не от видимой области. Тот же паттерн уже был правильно реализован для модалки «Ты не на территории» (рендерится в `FishZoneApp`, не внутри `MapScreen`) — просто не был соблюдён единообразно для более поздних `PhotoLightbox` и `EditProfileModal`, добавленных в прошлый заход. Решение — не точечный CSS-фикс (`position:fixed` внутри `.screen` тоже сработал бы, но это костыль на конкретный случай), а перенос обоих компонентов на уровень `FishZoneApp` как единое архитектурное правило для всех full-screen оверлеев в приложении (см. DOCS.md, «Позиционирование модалок»).

**Решение: `stack: StackEntry[]` вместо плоского `currentScreen`, для корректной кнопки «назад»**
Раньше «назад» на `TerritoryScreen`/`UserProfileScreen` вело на один захардкоженный экран (например, всегда на `screen-activity`), независимо от того, откуда реально пришёл пользователь — работало только для единственного тогда существовавшего пути входа. С ростом числа точек входа на территорию/профиль (карта, список, лента, чужой профиль, свой профиль) это стало явно неверным. Стек с параметризованными записями (`{screen:'screen-territory', territoryId}` и т.п.) хранит весь путь и восстанавливает не только тип экрана, но и его данные при каждом `pop()` — единственный способ корректно развернуть цепочку вида «территория → профиль владельца → другая его территория → назад → назад».

**Решение (сопутствующее, не запрошено напрямую): `catchTerritoryId` отделён от `viewingTerritoryId`**
Обнаружено при реализации стека: старое единое поле `activeTerritoryId` обслуживало одновременно и поток фиксации улова (геолокация «+» → камера → подтверждение), и вручную просматриваемую `TerritoryScreen` — а поскольку нижнее меню с кнопкой «+» остаётся видимым поверх экрана территории, геолокация могла молча подменить это поле, пока пользователь листал чужой сектор, ломая то, куда должна вести кнопка «назад». Разделено на два независимых поля — не потому что попросили, а потому что корректная реализация стека для «назад» этого требовала: без разделения стек восстанавливал бы `territoryId` из своей записи, но рендер всё равно мог бы показать не ту территорию, если `activeTerritoryId` успел смениться между push и pop.

**Решение: бейдж/точки непрочитанного — `localStorage`, не колонка/таблица в БД**
Статус «прочитано» здесь — чисто UI-удобство уровня одного устройства/браузера (как непрочитанные в большинстве почтовых клиентов), не данные, которым нужна собственная запись в БД, синхронизация между устройствами одного пользователя или видимость другим пользователям. Хранить это в Postgres означало бы писать при каждом открытии вкладки «Активность» ради чисто косметического состояния — оверинжиниринг для того, что и так прекрасно живёт в `localStorage` рядом с самим приложением.

**Решение: при первом визите на устройство — точка отсчёта «сейчас», а не «ничего не прочитано»**
Если бы отсутствие сохранённого `lastReadAt` трактовалось как «ничего никогда не читал», то у любого пользователя с существующей историей уловов/подписок бейдж при первом же открытии на новом устройстве (или после очистки браузера) показал бы гору «непрочитанных» записей, которые на самом деле давно случились и не новость. Вместо этого первый визит сразу пишет в `localStorage` текущий момент как базовую точку — непрочитанными считаются только записи, появившиеся уже после этого.

## Уведомление о подписке, жалобы на фото + админ-модерация, админ-улов на любой сектор, био профиля

Четыре запроса за один заход: уведомление в ленте при новой подписке, кнопка «Пожаловаться на фото» на занятой территории с фиксированными причинами и админ-очередью модерации, право одного конкретного аккаунта (`m.alimetov@mail.ru`) добавлять улов на любой сектор без привязки к геолокации, и описание профиля («био»).

**Решение: «подписался на тебя» — синтетическая запись на клиенте из `follows`, не строка в `activity_log`**
Хранить это в `activity_log` потребовало бы делать `territory_id` nullable (у подписки нет территории) ради единственного нового вида записи, плюс завести триггер на `insert` в `follows`, дублирующий то, что и так делает клиентский `useSetFollowing()`. Вместо этого `useActivity()` при наличии сессии отдельно тянет последние строки `follows` (`followee_id = я`) и подмешивает их в общий список, пересортированный по времени — та же идея, что уже применялась для персонализации ленты (клиентский пост-обработка поверх серверной выборки), не новый архитектурный паттерн.

**Решение: `ActivityEntry.id` — строка с префиксом источника (`log:123` / `follow:<uid>`), не сырой bigint**
Как только появился второй источник данных для одного списка (`activity_log` и `follows`), встал риск коллизии id между ними (bigint `activity_log.id` и uuid `follower_id` — разные пространства, но раньше тип был `number`, что технически не позволило бы `follow`-записи иметь строковый id вообще). Простая типизация «с префиксом» устраняет и коллизию, и несовместимость типов разом, не заводя отдельного параллельного набора «непрочитанных подписок» в `lib/activityRead.ts`.

**Решение: admin — колонка `profiles.is_admin`, захардкоженная под конкретный email в `handle_new_user()`, а не отдельная таблица ролей**
На один известный аккаунт (`m.alimetov@mail.ru`, уже существующий реальный пользователь «Magamed») городить таблицу `roles`/`admins` с полноценным RBAC — оверинжиниринг; булева колонка ровно отвечает на единственный вопрос, который приложению сейчас нужен («может ли этот профиль модерировать»). `handle_new_user()` проверяет `new.email = 'm.alimetov@mail.ru'` при каждой новой регистрации — не только текущий (уже существующий и обновлённый вручную через `update`) аккаунт, но и гипотетическое пересоздание того же email в будущем сразу получит права, без повторного ручного вмешательства.

**Решение: `is_admin` публично читаем через `profiles_with_stats`, а не скрыт**
Сам факт «этот профиль — админ» не даёт никаких прав через клиентское чтение — все реальные действия (`admin_delete_catch`, `admin_dismiss_report`) перепроверяют `is_admin` внутри `SECURITY DEFINER` функции по `auth.uid()`, не доверяя тому, что прислал клиент. Прятать колонку не даёт защиты (её всё равно легко проверить, просто попытавшись выполнить админское действие), а публичность упрощает код (`useIsAdmin()` — просто поле уже загруженного профиля, не отдельный защищённый эндпоинт).

**Решение: жалобы — отдельная таблица `catch_reports` с фиксированными причинами в TS, не enum в БД**
4 причины ровно как `METHODS`/`BAITS` — короткий список для `<select>`, не растущий каталог вроде `species`, так что не нужна отдельная таблица-справочник; но и `check`-constraint на `reason` не заведён (по той же причине, по которой его нет и на `catches.method`/`catches.bait` — см. решение выше в этом файле про способ/наживку) — это не enum уровня БД, а подсказки клиента, менять список — это правка одного файла, не миграция.

**Решение: «Удалить улов» пересчитывает владельца территории из оставшихся уловов, а не просто освобождает сектор**
Первая мысль — раз улов был поддельный, всегда снимать владение с territories. Но если поддельный улов перехватил территорию поверх чужого РЕАЛЬНОГО более раннего улова (обычный сценарий модели «последний улов побеждает», см. `confirm_catch`), после удаления фейка сектор должен вернуться прежнему владельцу, а не встать свободным — иначе модерация сама создаёт вторичный баг (без вины отобранная территория). `admin_delete_catch` явно смотрит, есть ли ещё уловы на этот `territory_id` после удаления, и либо переносит владение на автора самого нового оставшегося, либо (если не осталось ни одного) освобождает сектор.

**Решение: `admin_delete_catch` полагается на уже существующий `on delete cascade` (`activity_log.catch_id` → `catches.id`, `catch_reports.catch_id` → `catches.id`), не на ручную последовательность DELETE**
`activity_log.catch_id` каскадно удалялся и раньше (проверено через `pg_constraint` перед тем, как писать функцию) — в отличие от более ранней ручной чистки сирот при удалении сектора `B1313` (см. CHANGELOG), здесь достаточно одного `delete from catches`, обе зависимые таблицы почистятся сами. `catch_reports.catch_id` заведён с тем же `on delete cascade` намеренно — жалоба существует, чтобы админ принял решение; после решения (улов удалён) сама жалоба не несёт дальнейшей ценности как отдельная запись.

**Решение: «Отклонить» — отдельная RPC `admin_dismiss_report`, хотя пользователь явно просил только «удалить улов»**
Без способа закрыть необоснованную жалобу без действия над уловом очередь модерации была бы тупиковой — каждая жалоба либо приводит к удалению чужого (возможно, настоящего) улова, либо вечно висит в списке. Это не запрошенная пользователем функция сама по себе, а необходимое следствие того, что у очереди вообще есть кнопки, а не только один нож.

**Решение: обход геолокации для админа — только клиентский UI-путь в камеру, без изменений в `confirm_catch`/RLS**
Проверено перед реализацией: RPC `confirm_catch` никогда не принимала и не проверяла координаты — «сектор должен быть рядом» всегда было проверкой на клиенте (`handlePlus()` → `nearestTerritory()`), не на сервере. Значит для «админ может добавить улов куда угодно» не нужно ослаблять никакую серверную защиту — только дать админу кнопку, которая пропускает вызов геолокации и сразу открывает камеру для выбранного вручную сектора (`TerritoryScreen` → `FishZoneApp.startAdminCatch`), используя тот же самый камера→форма→RPC пайплайн, что и обычный улов.

**Решение: био — `text` без ограничения на уровне БД, `maxLength=280` только в UI**
Как и с именем (`maxLength=40` в `EditProfileModal`, тоже не задан в БД) — ограничение длины здесь чисто UX-декоративное (не даёт разрастись карточке профиля), а не требование целостности данных, так что constraint на колонке был бы лишним.

## Бейдж на «Жалобы на фото», уведомление об удалении улова + предупреждение о блокировке, блокировка пользователя, редизайн модалки «не на территории», Батуми вместо Аджарии

Пять доп. правок сразу после предыдущего блока (уведомление о подписке / жалобы+модерация / админ-улов / био).

**Решение: уведомление «улов удалён» — обычная строка `activity_log` с новым `kind:'moderation'`, а не отдельная таблица**
В отличие от «подписался на тебя» (синтетическая запись, собранная на клиенте из `follows` — там `activity_log` не подходил из-за `territory_id not null`), здесь территория остаётся существовать (удаляется только улов) — значит `activity_log` подходит без каких-либо компромиссов, просто с `catch_id: null` и новым видом `kind`. Единственная цена — расширить `CHECK`-constraint (`activity_log_kind_check`) до третьего значения; заводить для этого отдельную таблицу «системных уведомлений» было бы дублированием того, что `activity_log` уже умеет (персонализация по `user_id`, сортировка по времени, бейдж непрочитанного — всё бесплатно достаётся от существующего механизма).

**Решение: `admin_delete_catch` вставляет уведомление владельцу до, а не вместо, удаления улова**
Порядок в теле функции: сперва `select ... into v_owner_id from catches`, потом `delete`, потом `insert` уведомления. Это не могло быть в обратном порядке — после `delete` строка `catches` с нужным `user_id` уже не существует (хотя технически `v_owner_id` уже сохранён в переменную до удаления, так что порядок `insert`/`delete` между собой не важен — важно, что `select` идёт первым).

**Решение: текст предупреждения о блокировке — фиксированная строка в компоненте, не отдельное поле в БД**
Пользователь попросил конкретную формулировку («при повторных нарушениях аккаунт будет заблокирован») без вариативности по причине жалобы — хранить её в БД как будто это динамический контент означало бы придумывать несуществующее требование (разные тексты для разных причин никто не просил).

**Решение: `is_blocked` — блокирует только `confirm_catch`, не аутентификацию и не просмотр**
Полноценный бан на уровне Supabase Auth (`auth.admin.updateUserById` с `ban_duration`) требует service-role ключ — недоступен из клиентской `SECURITY DEFINER`-функции на анон-ключе (это управление самим Auth-сервисом, а не строкой в `public`-схеме, RLS/`SECURITY DEFINER` тут бессильны). Вместо полного бана — точечный отказ ровно в том месте, которое злоупотребление использует (создание нового улова/захват территории поддельным фото). Пользователь по-прежнему может войти и посмотреть свой профиль — это осознанно уже, а не «недоделанная» блокировка: цель — остановить конкретное злоупотребление, а не наказать доступом.

**Решение: `admin_set_blocked` — два явных guard'а (нельзя заблокировать себя, нельзя заблокировать другого админа), не полагаемся на дисциплину UI**
UI и так не даёт кликнуть «Заблокировать» на своём профиле (`openUserProfile` уводит на свой же редактируемый экран вместо чужого) — но проверка внутри `SECURITY DEFINER` функции нужна независимо от UI, потому что RPC — реальная граница доступа, а не сам факт существования кнопки. Guard на «другого админа» — защита от случайной или недобросовестной эскалации между несколькими админами; проверено вживую прямым вызовом RPC (в обход UI) — оба случая корректно отклоняются с понятным сообщением, состояние БД не меняется.

**Решение: `is_blocked` публично читаема, бейдж «Заблокирован» виден всем посетителям профиля**
Тот же аргумент, что уже применялся к `is_admin`: публичность булевого статуса не даёт никаких дополнительных прав через клиент (реальный эффект — только в `confirm_catch`, на сервере), а скрытие бейджа от обычных пользователей только запутало бы их («почему у этого рыбака перестали появляться уловы»), не добавив никакой защиты.

**Решение: `useReports()` получил `enabled: isAdmin`**
Побочная, но напрашивающаяся правка при добавлении бейджа на кнопку «Жалобы на фото»: `AdminReportsScreen` всегда смонтирован (как любой экран в этом app-shell), поэтому `useReports()` раньше уходил в сеть на каждую загрузку для абсолютно любого посетителя — RLS просто возвращал пустой список, не ошибку, так что это была не поломка, а лишний ненужный запрос. `enabled: isAdmin` убирает его для всех, кроме админа, и заодно даёт `ProfileScreen` переиспользовать тот же кэш (`queryKey:['reports']`) для счётчика бейджа без дополнительного запроса.

**Решение: модалка «Ты не на территории» — короче текст + новая иконка, без изменения логики показа**
Чисто презентационная правка по прямой просьбе пользователя («сделай короче описание, добавь иконку, чтобы выглядело интереснее») — использован тот же `.modal-overlay`/`.modal-card` паттерн, что и у остальных модалок в приложении, добавлен только один новый переиспользуемый класс `.modal-icon` (круглый градиент, тот же приём, что у аватаров/плюс-кнопки).

**Решение: «Аджария» → «Батуми» — точечная замена текста в 5 местах, без переименования сущностей/схемы**
Прямая просьба пользователя, чисто косметическая: `sectors.json`/`territories`/охват геометрии (весь берег от Сарпи до Чакви, см. «Открытые вопросы» ниже) не переименовывались и не сужались — поменялся только видимый пользователю текст (заголовок вкладки, подписи, дефолтная локация профиля), а не то, что на самом деле покрывает карта.

## Публичный 5-значный ID пользователя + поиск по нему на вкладке «Территории»

Доп. запрос сразу после предыдущих двух блоков: короткий человекочитаемый ID вместо `uuid`, чтобы админ мог найти профиль по номеру, который пользователь может продиктовать/написать текстом (в отличие от `uuid`, который никто не станет вводить руками).

**Решение: `public_id` — `text`, не `int`, несмотря на то, что это число**
Требование явно включало ведущие нули (админскому аккаунту — `00000`). Целочисленный тип не хранит незначащие нули — `00042` считался бы как `42` и отображался бы без них при каждом чтении. `text` с проверкой на цифры при генерации и при вводе в поиске (клиент фильтрует нецифровые символы) даёт нужный формат без doп. форматирования на каждом чтении.

**Решение: генерация — цикл проверки уникальности в `handle_new_user()`, не последовательный счётчик**
Пользователь прямо попросил «рандомный» ID, не порядковый номер — последовательный счётчик было бы проще реализовать (не нужна проверка коллизий), но это не то, что просили, и вдобавок раскрывало бы примерное число зарегистрированных аккаунтов через сам ID. Цикл `loop … exit when not exists` — стандартный паттерн для «случайное значение с проверкой уникальности» в Postgres, коллизии на масштабе этого приложения (сотни-тысячи пользователей на пространство в 100 000 значений) практически не встретятся, а даже если встретятся — цикл просто попробует снова.

**Решение: существующим двум реальным профилям — не общий скрипт, а два точечных `update`**
На момент миграции в БД было ровно два реальных профиля (проверено `select` перед миграцией) — писать процедуру для «многих» пользователей было бы решением воображаемой, а не текущей задачи. Использован тот же `do $$ ... $$`-блок, что мог бы понадобиться и для большего числа строк (на случай, если между планированием и приложением миграции появятся новые регистрации), но без искусственного усложнения сверх необходимого.

**Решение: `public_id` показывается на профиле (свой + чужой), хотя пользователь явно попросил только генерацию и поиск**
Без этого поле поиска на вкладке «Территории» было бы неприменимо на практике — админу неоткуда узнать чей-либо ID, если он нигде не отображается. Это не самостоятельная функция, а необходимое условие работы уже запрошенной (строка 2 запроса) — размещено минимально (одна маленькая строка под локацией), не как отдельная выделенная секция профиля.

**Решение: поиск по ID — `useMutation`, не `useQuery`**
Это одноразовое действие по нажатию кнопки «Найти» (или Enter), а не значение, которое нужно держать в реактивном кэше react-query и переиспользовать между рендерами — `useMutation` (`mutateAsync`) точнее описывает происходящее («выполнить поиск и получить результат разово»), чем `useQuery` с искусственно управляемым `enabled`.

## Супер-админ, выдача/отзыв прав админа, журнал «Доступы» и «Последние действия»

Доп. запрос сразу после трёх предыдущих блоков: единственный текущий админ становится «супер-админом» с правом раздавать/забирать обычные права админа и видеть журнал действий всех админов.

**Решение: `is_super_admin` — отдельный флаг, не «уровень» поверх `is_admin`**
Простая булева колонка, а не enum ролей (`admin`/`super_admin`) — при ровно двух уровнях доступа, где верхний уровень уже подразумевает нижний (`is_super_admin=true` всегда идёт вместе с `is_admin=true`, выставляется в одном месте в `handle_new_user()`), enum добавил бы сравнения по строкам вместо простой проверки boolean без какой-либо гибкости, которая была бы использована. Та же логика, что уже применена к `is_admin`/`is_blocked` в этом проекте.

**Решение: `admin_set_admin` проверяет `is_super_admin` вызывающего, а не `is_admin`**
Прямое требование пользователя («учти что только супер админ может повышать пользователей до админа»). Это не тот случай, где два уровня прав естественно образуют иерархию для ЭТОГО конкретного действия — обычный админ, выданный супер-админом, не должен получать возможность плодить новых админов самостоятельно (иначе исходная гарантия «только я решаю, кто админ» ломается на втором шаге). Проверено вживую: прямой вызов RPC от обычного (не супер) админа отклоняется с `not authorized`.

**Решение: `details` в `admin_actions` — готовый текст, собранный в момент действия, не поля для пересборки при чтении**
Рассматривался вариант хранить только `action`/`target_user_id`/`territory_id` и собирать читаемый текст на клиенте по этим полям (JOIN'ом на лету). Отклонён: имя цели или вид пойманной рыбы на момент удаления улова — это факт того самого момента, который должен остаться в истории неизменным, даже если пользователь позже сменит имя или улов давно удалён (сам `catches`/`species`-join после `delete` уже невозможен). Готовый текст, вычисленный один раз внутри `SECURITY DEFINER`-функции (которая и так уже там же читает нужные имена для самого действия), проще и надёжнее, чем денормализованный snapshot полей + логика сборки текста, продублированная на клиенте.

**Решение: «Доступы» и «Последние действия» — один компонент (`AdminActionsScreen`) с разным фильтром, не два отдельных**
Обе разницы между экранами — заголовок и список `actionTypes` для `.in()` — не оправдывают дублирования разметки списка карточек (имя админа/детали/время), которая идентична для обеих. Тот же принцип, что уже применялся в проекте (например, `ReportPhotoModal`/`EditProfileModal` через общий `.modal-*` паттерн, а не копипаст вёрстки).

**Решение: кнопка «Выдать/забрать права админа» скрыта на профиле другого супер-админа (клиентская проверка задваивает серверный guard)**
Сейчас это единственный практический случай (один супер-админ), но проверка на клиенте не полагается на это допущение — если в будущем появится второй супер-админ, UI не будет показывать кнопку, которая всё равно была бы отклонена сервером; тот же принцип defense-in-depth, что уже применён к кнопке «Заблокировать» (тоже скрыта для чужих админов, хотя сервер и так отклонил бы).

## Открытые вопросы / не решено
- Приложение задумано и называется как «береговая морская рыбалка», а с переходом на инструмент друга фактически стало «рыбалка у любой воды (море/река/ручей/озеро) по всей Аджарии» — не решено, стоит ли переименовать/перепозиционировать продукт под новый охват, или в будущем сузить данные обратно до только моря / только части побережья (инструмент это поддерживает — правка `PRIORITY`/фильтра в `build_hex.mjs` и BBOX).
- 703 сектора отрисовываются и рендерятся в список/карусель без кластеризации или виртуализации (см. DOCS.md, «Известные ограничения») — пока быстро при демо-нагрузке, не проверено при реальном многопользовательском трафике.
- MCP-коннектор Vercel не заработал за всю сессию (постоянный 403, см. решение выше) — деплой сделан вручную через веб-интерфейс. Если он остаётся сломанным и в следующей сессии — не тратить время на повторные попытки `list_teams`/`create_git_project`, сразу вести пользователя по UI (Vercel Dashboard: Root Directory `web`, env-переменные `NEXT_PUBLIC_SUPABASE_*`, см. DOCS.md «Деплой»).
- Realtime не подключён (см. решение выше) — если многопользовательский сценарий окажется активным (несколько рыбаков одновременно смотрят карту), стоит переоценить, достаточно ли refetch-on-focus.
- `web/supabase/` как каталог файловых миграций не заведён — схема применена напрямую через Supabase MCP в разговоре (см. DOCS.md). Стоит выгрузить в файлы, если появится локальная разработка через Supabase CLI или понадобится история миграций в git.
- Confirm email выключен ради тестирования (см. решение выше) — перед публичным запуском вернуть подтверждение + подключить свой SMTP, либо осознанно решить оставить как есть.
- Названия видов рыб в ленте активности не склоняются падежно («поймал скорпена») — полноценное русское склонение 36 существительных не стали строить (нужен был бы словарь форм или библиотека морфологии), не критично для читаемости.
- Порог геолокации (400м) и выбор «разовый getCurrentPosition вместо watchPosition» не проверялись в реальных полевых условиях (только эмуляцией координат в браузере) — точность GPS на телефоне у воды, скорость получения фикса и поведение при плохом сигнале не протестированы.
- Настоящая камера (`getUserMedia`) проверена только эмуляцией `MediaStream` (canvas → `captureStream()`) — весь цикл интро→доступ→кадр→загрузка→БД пройден так, но не на реальном телефоне/браузере. Стоит попросить пользователя пройти поток на своём устройстве (он именно там впервые увидел GPS-координаты, есть под рукой) и проверить: реальное качество/ориентацию фото с задней камеры, поведение `facingMode:'environment'` на разных телефонах, и что происходит при повторном отказе после явного запрета доступа (браузер может не показывать системный диалог повторно — тогда кнопка «Запросить доступ снова» будет молча не срабатывать, у пользователя останется только подсказка проверить настройки сайта).
