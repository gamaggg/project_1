# FishZone — журнал технических решений

Здесь фиксируется **почему** сделано так, а не иначе — чтобы не переоткрывать одни и те же вопросы заново.

---

**Решение: один HTML-файл, без сборки/фреймворка**
Причина: это MVP/прототип для демонстрации и итеративной правки в чате. Сборка (React/Vite/etc.) добавляет накладные расходы без пользы на этой стадии. Если проект перейдёт в реальную разработку — потребуется миграция на нормальный стек (см. открытый вопрос ниже).

**Решение: Leaflet + OpenStreetMap вместо Google Maps / Mapbox**
Причина: не требует API-ключа и оплаты, достаточно для MVP. Минус: тайлы OSM по умолчанию визуально «пёстрые» — компенсировано CSS-фильтром (`grayscale/contrast`).

**Решение: сектора — явный список точек (`SECTOR_POINTS`), а не процедурная генерация вдоль линии берега**
Было перепробовано несколько процедурных подходов (сплайн через опорные точки берега + арк-length нарезка, две смещённые кривые земля/море). Все они работали математически корректно, но ошибка в **исходных координатах** (не в самой генерации) приводила к тому, что сектора уходили в город — и было тяжело понять, в геометрии баг или в данных. Явный список `{id, lat, lng}` на каждый сектор убирает эту неоднозначность: если сектор не на месте — правится ровно одна пара чисел, без побочных эффектов на соседей. Ориентация/размер по-прежнему считаются автоматически (по соседним точкам), так что вручную указывать угол поворота не нужно.
> **Заменено** (см. «Решение: сектора генерируются из реальных данных OSM» ниже) — `SECTOR_POINTS` и вся эта ручная подгонка координат удалены из кода. Оставлено здесь как история: те же уроки (не полагаться на одну глобальную линию/сплайн, ошибка в данных выглядит как баг геометрии) стояли за выбором подхода, которым эта проблема решена окончательно.

**Решение: ориентация сектора = направление от предыдущей точки к следующей (не отдельная «касательная берега»)**
Причина: убирает необходимость в отдельной модели береговой линии (второй источник правды). Каждый сектор буквально «смотрит» на своих соседей по списку — если список точек соответствует реальному изгибу берега, ряд секторов будет ему соответствовать.

**Решение: сектора — шестиугольники (соты), а не квадраты**
По явному запросу: соты плотнее стыкуются друг с другом без зазоров на изгибах, чем квадраты/прямоугольники, повёрнутые под фиксированным углом.

**Решение: перерисовка полигонов (`drawTerritories`) отделена от перерисовки карусели карточек (`renderMapSheet`)**
Было: `drawTerritories()` в конце вызывал `renderMapSheet()`, а `drawTerritories` был подписан на событие `zoomend`. `flyTo()` (при свайпе карточки) triggers `zoomend` → карусель каждый раз пересобиралась и сбрасывала скролл на первую карточку → это триггерило повторный `flyTo` на неё же → визуально «карта дёргается назад». Разделение вызовов устранило зацикливание. **Вывод на будущее**: не завязывать перерисовку геометрии карты и перерисовку независимого UI-компонента (карусели) на одно и то же событие без явной необходимости.

**Решение: сектора идентифицируются только числом (`id`), без названий/типов**
По явному запросу пользователя — упростили модель, убрали `name`/`type` из данных и из всех экранов, где они показывались (карточка сектора, карусель, подтверждение улова, успех, лента активности, профиль).
> **Уточнение**: на практике `name`/`type` были убраны из `SECTOR_POINTS`/`territories` не полностью — несколько шаблонов (карточка территории, карусель, подтверждение улова, лента активности, профиль) продолжали выводить `t.name`/`t.type` вплоть до перехода на `HEX_SECTORS` (см. ниже), то есть DOCS.md какое-то время не отражал реальный код. Это исправлено заодно с переходом на новые данные: `name` выведен окончательно, `type` в UI показывает `KIND_LABEL[t.kind]` (реальный тип воды из OSM — Море/Река/Ручей/Озеро), это не выдуманное название и не противоречит духу этого решения.

**Решение: полигоны через Leaflet `L.polygon` (SVG), а не CSS-div с `border-radius`**
Причина: как только сектора перестали быть простыми квадратами (шестиугольники, произвольная ориентация), CSS-div с фиксированным border-radius больше не подходит — SVG-полигон единственный вариант для точной формы/поворота на реальных геокоординатах.

**Решение: без localStorage/сохранения между сессиями**
В среде артефактов Claude localStorage не поддерживается технически. Для реального продукта — see «Открытые вопросы».

## Интеграция инструмента друга (tools/fishing-hex): гекс-сетка по реальным данным OSM

**Решение: сектора генерируются из реальных данных OpenStreetMap (`tools/fishing-hex`), а не из ручного списка ориентиров**
Причина: знакомый прислал независимо написанный инструмент — берёт реальную геометрию воды из OSM через Overpass API и режет её на честную гексагональную сетку 600м, оставляя только соты, которые физически касаются воды. Это снимает саму проблему, из-за которой раньше пришлось перейти на ручной `SECTOR_POINTS`: координаты воды теперь берутся из первоисточника (OSM), а не подбираются вручную по Google Places, поэтому сектора не могут «уйти в город» по ошибке ввода. Детали инструмента и как его перегенерировать — DOCS.md, раздел «tools/fishing-hex».

**Решение: полный охват побережья Аджарии (Сарпи–Чакви) и все 4 типа воды (море/река/ручей/озеро), а не только центр Батуми и только море**
Явный выбор пользователя (двумя вопросами) при интеграции: инструмент поддерживает такой охват «из коробки» (61 морская сота + 303 река + 320 ручьёв + 19 озёр = 703), решили не резать вручную обратно до масштаба старой версии (~24 точки в центре Батуми, только море).
Открытый вопрос из-за этого — см. ниже: приложение задумывалось и называется как «береговая морская рыбалка», а по факту стало «рыбалка у любой воды в Аджарии».

**Решение: id секторов — формат сетки инструмента (`"B0144"`), а не сквозной ручной номер**
id больше не придумывается вручную, а приходит из `build_hex.mjs` (порядковый номер в гекс-сетке инструмента). Из-за смены числа на строку пришлось поправить все места, где id подставлялся в `onclick`-атрибуты без кавычек (`onclick="openTerritory(${t.id})"` для строки — синтаксическая ошибка в разметке) — везде добавлены кавычки вокруг `${t.id}`.

**Решение: стартовые «моя»/«чужие» территории — явный список из 3 id (`B1127`/`B1126`/`B1079`)**
В сетке 703 сектора, вручную придумывать статус каждому смысла нет, но для узнаваемости демо-сценария (Пирс у Дельфинария / Marriott / порт, персонажи «Алексей»/«Марина») эти три id подобраны как ближайшие морские (`kind:'sea'`) соты к тем же трём координатам, что были у старых `SECTOR_POINTS` id 21/18/23. **Хрупкость**: если пересобрать `hex.geojson` с другим BBOX или `WIDTH_M`, эти конкретные id могут не существовать в новой сетке — seed молча пропустит недостающие (все сектора останутся `free`), понадобится заново найти ближайшие соты к тем же ориентирам (как сделано один раз в этой сессии — см. `tools/fishing-hex/extract_sectors.mjs` для формата данных, поиск ближайшего делался разовым скриптом, не сохранён в репозитории).

**Решение: id-подписи секторов на карте показываются только при `zoom >= 14`, полигоны — всегда**
При 703 секторах на весь берег все подписи разом на далёком зуме (когда виден весь berег целиком) визуально сливаются в нечитаемое месиво текста — проверено вживую при интеграции. Статус-цвет сектора (мой/чужой/свободный) — самая важная информация на дальнем зуме — остаётся виден всегда; подписи включаются только когда пользователь уже приблизился к конкретному участку и они читаемы.

**Решение: `preferCanvas:true` на карте Leaflet**
С ростом числа секторов до 703 рисовать каждый шестиугольник отдельным SVG-узлом (поведение Leaflet по умолчанию) стало бы граничным по производительности; canvas-рендер держит все полигоны на одном холсте. Замер в этой сессии: `drawTerritories()` для всех 703 секторов ≈5мс на canvas — с запасом.

## Миграция в веб-сервис: Next.js + Supabase + Vercel

Пользователь решил делать не прототип, а настоящий веб-сервис — многопользовательский, с реальными аккаунтами. Ниже — решения, зафиксированные при переходе (все — явный выбор пользователя через вопросы в чате, не решены за него).

**Решение: стек — Next.js + Supabase (Postgres/Auth) + Vercel**
Причина: в сессии уже были подключены MCP-инструменты обоих сервисов — прямой намёк на связку, и она же самая быстрая для этого масштаба (React-фреймворк с бэкендом на одном языке, БД+Auth из коробки, деплой в один клик). Другие стеки не оценивались.

**Решение: `web/` — соседняя папка в том же репозитории (монорепо), `fishzone-app.html`/`tools/fishing-hex/` не трогаются**
Причина: `tools/fishing-hex` — общий источник геометрии для обоих поколений (прототип и веб-сервис), логично держать их рядом. Прототип оставлен как есть — исторический референс дизайна, из которого `web/` был перенесён, не удалён и не обновляется дальше.

**Решение: дизайн/экраны переносятся 1:1, кроме фейковой рамки телефона/статус-бара — их убрали**
`.device`/`.statusbar`/`.notch` в прототипе существовали только для превью в браузере на десктопе (эмуляция экрана iPhone 390×844). В реальном вебе, открытом на настоящем телефоне, это стало бы вторым статус-баром поверх настоящего — решили убрать, заменив на честную адаптивную вёрстку (`.app-shell{max-width:480px;margin:0 auto}` — full-bleed на мобильном, по центру на десктопе). Все цвета/радиусы/тени/шрифт/компонентные классы (`.card`, `.btn-primary`, `.badge-*`, и т.д.) перенесены из `fishzone-app.html` практически дословно — см. `web/app/globals.css`.

**Решение: авторизация сразу и по-настоящему — Supabase Auth, email+пароль**
Причина: территории должны принадлежать реальным людям, не одному демо-юзеру — иначе «веб-сервис» не отличался бы от прототипа по сути. Email+пароль выбран для v1 вместо magic link/OAuth — не требует настройки внешних OAuth-приложений или зависимости от доставки писем для самого входа (регистрация всё равно требует подтверждения email — это дефолт Supabase, не отдельная настройка, см. DOCS.md).

**Решение: карта/территории/лента активности публичны без входа; вход нужен только для записи (улов/захват территории)**
Strava-style: смотреть чужие уловы и карту может кто угодно, вход — только когда хочешь сам что-то сделать. Реализовано через RLS `select using (true)` на всех таблицах + проверку сессии в `FishZoneApp.startCatchFlow` (редирект на `/auth`, а не тихий no-op).

**Решение: все 703 территории стартуют свободными — никаких demo-аккаунтов вместо старых `B1127`/`B1126`/`B1079`**
Причина: раз территории теперь принадлежат настоящим людям, подсовывать фиктивных «Алексея»/«Марину» как реальные аккаунты — обман; создавать реальные тестовые аккаунты только ради демо-заполненности карты тоже не имеет смысла для только что запущенного сервиса. Карта просто пустая (все свободны), пока реальные пользователи её не заполнят.

**Решение: геометрия секторов — статический JSON-ассет (`web/public/data/sectors.json`), не строки в Postgres**
Причина: 6 вершин × 703 сектора никогда не меняются в рантайме и не нужны для RLS/агрегаций — гонять их через БД на каждый запрос бессмысленно. В Postgres — только «тонкая» `territories` (id/kind/lat/lng/owner_id) для целостности FK (`catches`/`activity_log` ссылаются на неё) и владения. См. DOCS.md, раздел «База данных».

**Решение: `catch_count`/`last_catch_at` — вью с агрегацией (`territories_with_stats`), не денормализованные колонки**
Причина: 703 территории — агрегация по `catches` дешёвая при любом разумном трафике; денормализация потребовала бы триггеров и создала риск рассинхронизации ради экономии, которая тут не нужна.

**Решение: запись только через RPC (`confirm_catch`), не прямые INSERT/UPDATE от клиента**
Причина: `confirmCatch()` в прототипе атомарно делает три вещи (улов, смена владельца, запись в ленту) — RPC с `SECURITY DEFINER` и `select … for update` на строке территории повторяет то же самое атомарно и безопасно при параллельном заходе двух пользователей на одну свободную территорию (кто первый — тот и получил). Прямые insert/update-политики клиентам не выданы: без RPC создать улов без реального `auth.uid()` или подделать владение нельзя.

**Решение: единый клиентский app-shell со стейт-машиной экранов, а не отдельные Next.js-роуты на каждый экран**
Причина: переходы-кроссфейды между 7 экранами и эфемерный `pendingCatch` (камера→подтверждение) проще и надёжнее перенести как React-стейт в одном компоненте (`FishZoneApp.tsx`), как это было устроено в прототипе (`goTo()`/`currentScreen`), чем резать на роуты — ни один экран сейчас не должен быть шаримой ссылкой, а настоящая навигация браузера рисковала бы потерять `pendingCatch` между камерой и подтверждением. Единственный отдельный роут — `/auth` (существует до входа, вне shell).

**Решение: Realtime-подписки Supabase — не в v1, обновление на фокусе вкладки (`@tanstack/react-query`, `refetchOnWindowFocus`)**
Причина: проще для первой версии; переход на Realtime позже — локальное добавление (инвалидация query на `postgres_changes`), не переписывание архитектуры данных.

**Решение: `lib/supabase/client.ts` — синглтон, не фабрика нового клиента на каждый вызов**
Наступили на грабли в этой же сессии: с фабрикой (`createBrowserClient()` при каждом `createClient()`) форма входа создавала СВОЙ экземпляр Supabase-клиента, отдельный от того, на который подписан `AuthProvider` — `onAuthStateChange` срабатывает только на экземпляре, который сам выполнил вход/выход, поэтому после логина `AuthProvider` не узнавал о новой сессии без полной перезагрузки страницы (первый прогон end-to-end теста «поймать рыбу» упал именно на этом — `startCatchFlow` считал пользователя неавторизованным сразу после успешного входа). Починено модуль-левел синглтоном. **Вывод на будущее**: Supabase-клиент в браузере должен быть один на вкладку, если где-то в приложении есть больше одного места, которое его создаёт и на него подписывается.

**Решение: Next.js 16 — используем `proxy.ts` вместо `middleware.ts`**
В установленной версии (16.3.4, новее тренировочных данных модели — увидели явное предупреждение в `web/AGENTS.md`, которое Next.js сам кладёт в свежий проект) файл-конвенция `middleware.ts`/`export function middleware` переименована в `proxy.ts`/`export function proxy`; механика (cookies, matcher, `NextResponse`) не изменилась. Узнали из `node_modules/next/dist/docs/` перед тем как писать код, а не через ошибку компиляции постфактум.

**Решение: Node.js скачан локально в `.tools/node/` (не установлен системно, не через nvm/Homebrew — их тоже не было)**
В среде разработки не оказалось вообще никакого JS-тулчейна (ни `node`, ни `npm`, ни менеджера версий, ни Homebrew). Вместо системной установки (нет sudo/доступа к системным путям от инструмента) — скачан официальный tar.gz с nodejs.org (v24 LTS, «Krypton», arm64) и распакован в `.tools/node/` внутри репозитория, добавлен в корневой `.gitignore`. Все npm/node-команды в этой и будущих сессиях требуют `export PATH=".../.tools/node/bin:$PATH"` перед запуском — шелл-стейт инструмента не персистится между вызовами, окружение задаётся заново каждый раз (это не изменение системы пользователя, никакие системные файлы/PATH не тронуты за пределами репозитория).

## Открытые вопросы / не решено
- Приложение задумано и называется как «береговая морская рыбалка», а с переходом на инструмент друга фактически стало «рыбалка у любой воды (море/река/ручей/озеро) по всей Аджарии» — не решено, стоит ли переименовать/перепозиционировать продукт под новый охват, или в будущем сузить данные обратно до только моря / только части побережья (инструмент это поддерживает — правка `PRIORITY`/фильтра в `build_hex.mjs` и BBOX).
- 703 сектора отрисовываются и рендерятся в список/карусель без кластеризации или виртуализации (см. DOCS.md, «Известные ограничения») — пока быстро при демо-нагрузке, не проверено при реальном многопользовательском трафике.
- Веб-сервис ещё не задеплоен на Vercel — MCP-коннектор Vercel не авторизован в этой сессии (`list_teams` вернул пусто), нужен явный шаг пользователя (перейти по ссылке авторизации через `get_access_to_vercel_url`), прежде чем деплоить.
- Realtime не подключён (см. решение выше) — если многопользовательский сценарий окажется активным (несколько рыбаков одновременно смотрят карту), стоит переоценить, достаточно ли refetch-on-focus.
- Графа подписок («Подписчики» в профиле, фильтр «Подписки» в ленте) не спроектирована — `followers_count` статичный плейсхолдер (0 у всех), фильтр «Подписки» в v1 скрыт из UI (решение из сессии интеграции гекс-сетки распространено и на веб-сервис).
