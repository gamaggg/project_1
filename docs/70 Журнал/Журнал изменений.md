# Журнал изменений

Формат: дата (сессии) не фиксируется автоматически — при переносе в реальный проект дописывайте дату коммита. Каждая запись = один запрос пользователя и что было сделано.

## Инициализация проекта
- Собран MVP мобильного приложения для береговой рыбалки в Батуми по исходному ТЗ (Strava-style, не игра).
- Единый файл `fishzone-app.html` (HTML/CSS/JS, без сборки), рендерится как мобильный экран 390×844.
- Экраны: Карта, Территории, Камера (фиксация улова), Подтверждение улова, Активность, Профиль.
- Реальная карта на Leaflet + OpenStreetMap тайлы.

## UI-полировка
- Единый шрифт (Manrope) на всё приложение, включая GPS-чип на камере (раньше был отдельный monospace).
- Плавные переходы между экранами (кроссфейд + подъём) вместо резкого display:none/flex.
- Углублены тени, добавлены градиенты на кнопках, тактильный отклик (scale на нажатии) почти на всех интерактивных элементах.
- Добавлен минимальный брендинг-лого на экране карты.

## Баг: тайлы карты с водяным знаком «API KEY REQUIRED»
- Причина: CARTO закрыл бесплатный доступ к своим базовым тайлам.
- Исправление: переход на стандартные тайлы OpenStreetMap (без ключа) + CSS-фильтр (grayscale/contrast) для приглушённого «премиального» вида вместо туристической пестроты OSM по умолчанию.

## Баг: территории на карте не совпадали с береговой линией
- Несколько итераций проблемы:
  1. Первая версия — повёрнутые квадраты по 2 опорным точкам берега → диагональ резала город.
  2. Убрали поворот (axis-aligned квадраты через divIcon) — устранило часть багов, но перестало «облегать» изгиб берега.
  3. Вернули поворот через две смещённые кривые (земля/море) + нарезку на полосы — сложная геометрия, часть багов с самопересечением полигонов.
  4. По просьбе пользователя — сектора стали шестиугольниками (сотами), шаг 300 м, каждый сектор ориентируется по касательной ЛОКАЛЬНО (не по одной глобальной линии).
  5. Обнаружено: направление менялось только в 6 точках стыка исходных опорных точек → между ними ряд был прямым. Добавили сглаживание сплайном (Catmull-Rom) — не прижилось при дальнейшей правке.
  6. **Финальное решение**: убрали сплайн и любые «глобальные линии» вообще. Ввели `SECTOR_POINTS` — явный список `{ id, lat, lng }`, по одной точке на сектор. Ориентация и размер каждого шестиугольника считаются от соседних точек в списке (направление на предыдущую/следующую точку). Это даёт полный ручной контроль без скрытой математики.
- Отдельная проблема: часть опорных координат указывала на объекты в глубине города (например, «Центральный парк Батуми»), а не на набережную → линия срезала через кварталы. Пересчитано через проверенные прибрежные ориентиры (Iveria Beach, Alphabet Tower, Radisson Blu, парк Batumi Boulevard, Batumi Beach, озеро Ардагани, южный кластер New Boulevard), найденные через Google Places.

## Баг: карточка сектора на карте перекрывалась нижним меню
- Карусель карточек (`map-sheet-container`) была позиционирована `bottom:12px`, залезала под `bottomnav`.
- Исправление: `bottom:94px` (высота меню + отступ).
- Побочный баг: при подъёме карточек случайно занизили `z-index` карусели ниже, чем внутренние z-index панелей Leaflet (тайлы/маркеры) → карточки визуально «исчезли» под картой. Возвращён `z-index:700`.

## Баг: кнопка камеры перекрывалась нижним меню
- При открытии полноэкранной камеры `bottomnav` теперь скрывается (`display:none`), возвращается при выходе из экрана камеры.

## Функция: свайп карточки сектора → карта летит к нему
- Карусель карточек через нативный горизонтальный скролл (`scroll-snap`).
- При свайпе (через `scroll`-listener с debounce) карта делает `flyTo` на выбранный сектор.
- Баг: `zoomend` (срабатывающий из-за `flyTo`) был подписан на полную перерисовку карусели → карусель сбрасывалась на первую карточку → карта возвращалась обратно к «моей территории». Исправление: перерисовка квадратов на зуме отделена от перерисовки карусели; карусель теперь обновляется только там, где это действительно нужно (при первой загрузке и после подтверждения улова).

- Убрана тень у карточек карты (по просьбе).

## Замена логики секторов: гекс-сетка друга по реальным данным OSM

Пользователь принёс независимо написанный инструмент друга (`fishing-hex.zip`) — генератор гексагональной сетки 600м по воде из OpenStreetMap. Заменили им ручной список ориентиров `SECTOR_POINTS` (~24 точки, только центр Батуми, только море, координаты подбирались вручную по Google Places).

Что сделано:
- Инструмент скопирован в `tools/fishing-hex/` (`fetch_osm.sh`, `build_hex.mjs`, `assemble.mjs`, `tiles.py`, `README.md`, `package.json` + `hex.geojson`/`water.geojson` — уже прогнанные автором данные для bbox Сарпи–Чакви).
- Добавлен `tools/fishing-hex/extract_sectors.mjs` (новый файл, не было у друга) — фильтрует `hex.geojson` до реальных (`core:true`) сот, конвертирует координаты `[lon,lat]→[lat,lng]`, считает центр каждой соты. Node в этой среде был недоступен — прогнан один раз эквивалентным Python-скриптом, результат (`sectors.json`) идентичен тому, что дал бы `node extract_sectors.mjs`.
- `fishzone-app.html`: `SECTOR_POINTS` + вся ручная геометрия (`hexCornersForPoint`, `lerp`, `metersOffset`, `metersDelta`) удалены. Вместо них — вшитый `const HEX_SECTORS` (703 сектора: море 61, река 303, ручей 320, озеро 19) и `territories = HEX_SECTORS.map(...)`.
- Стартовые «моя»/«чужие» территории (`B1127`/`B1126`/`B1079`) подобраны как ближайшие морские соты к тем же трём ориентирам набережной, что были в старой версии (Дельфинарий/Marriott/порт) — сохранили узнаваемость демо-сценария и персонажей «Алексей»/«Марина».
- Попутно исправлено расхождение документации и кода: `t.name`/`t.type` (выдуманные названия секторов) фактически ещё выводились в нескольких шаблонах, хотя решение их убрать было задокументировано раньше. Убраны окончательно; «Тип» на карточке территории и в списках теперь показывает настоящий тип воды сектора (`KIND_LABEL[t.kind]`: Море/Река/Ручей/Озеро) вместо выдуманного текста.
- Все `onclick="...(${t.id})"` без кавычек починены на `'${t.id}'` — id теперь строка (`"B0144"`), не число.
- Карта: `preferCanvas:true` (замер — перерисовка всех 703 полигонов ≈5мс), `fitBounds` считается по вершинам `territories` (весь охват, а не старые точки), id-подписи секторов вынесены в отдельный слой и показываются только при `zoom >= 14` — на дальнем зуме 703 подписи разом превращались в нечитаемое месиво текста; шестиугольники со статусом остаются видны на любом зуме.
- Тексты интерфейса: «Побережье Батуми · N участков» → «Море, реки и озёра Аджарии · N участков», «Шаг ≈300 м» → «≈600 м» (реальная ширина соты инструмента).
- Проверено вручную через локальный http-сервер (файл открытый как `file://` рендерился статическим снепшотом без выполнения JS) — карта, карусель, список территорий (703 карточки), полный цикл камера→подтверждение→успех, лента активности, профиль и достижения отработали без ошибок в консоли; `renderTerritoriesList()` ≈9мс, `renderMapSheet()` ≈54мс на 703 элемента.
- Решение по охвату (весь берег Аджарии + все 4 типа воды, а не только море в центре Батуми) — явный выбор пользователя, зафиксирован в [[Указатель решений|DECISIONS.md]] вместе с открытым вопросом о переименовании/репозиционировании продукта.

## Миграция в веб-сервис: Next.js + Supabase + Vercel

Пользователь решил делать не прототип, а настоящий веб-сервис — многопользовательский, с реальными аккаунтами вместо одного демо-юзера. Стек (Next.js + Supabase + Vercel), объём переноса (дизайн 1:1, минус рамка телефона) и момент подключения авторизации (сразу, email+пароль) — согласованы явными вопросами пользователю, зафиксированы в [[Указатель решений|DECISIONS.md]].

**Окружение**: в среде разработки не оказалось Node.js/npm вообще (ни системно, ни через nvm/Homebrew — тоже не было). Скачан официальный Node 24 LTS (arm64) с nodejs.org в `.tools/node/` внутри репозитория (gitignored) — без sudo, без изменения системных путей.

**Scaffold** (`web/`): `create-next-app` (App Router, TypeScript, ESLint, без Tailwind — переносили существующие CSS-токены дословно). Пакеты: `@supabase/supabase-js`, `@supabase/ssr`, `leaflet` (без `react-leaflet` — Leaflet рулится императивно, как в прототипе), `@tanstack/react-query`.

**Next.js 16 (новее тренировочных данных модели)**: `web/AGENTS.md` (сам файл кладёт `next dev`) явно предупредил свериться с `node_modules/next/dist/docs/` перед тем как писать код. Ключевое отличие — `middleware.ts` переименован в `proxy.ts` (`export function proxy` вместо `export function middleware`), механика та же. Использован `proxy.ts` сразу, без набивания шишек.

**База данных** (Supabase проект `yhgdcdkfkerzuhnzjzrz`, уже был подготовлен в сессии, схема была пустой): через MCP `apply_migration`/`execute_sql` созданы `profiles`, `territories` (тонкая — id/kind/lat/lng/owner_id, без геометрии), `catches`, `activity_log`, вью `territories_with_stats` (агрегация catch_count/last_catch_at), RLS (публичное чтение везде, запись только через RPC), RPC `confirm_catch` (SECURITY DEFINER, атомарно: улов → смена владельца → лента, с блокировкой строки территории от гонки при параллельном захвате), триггер `handle_new_user` (создаёт `profiles` при регистрации). Просеяны все 703 территории из `tools/fishing-hex/sectors.json` — **все свободны**, никаких demo-владельцев (в отличие от прототипа с захардкоженными `B1127`/`B1126`/`B1079` — фиктивные люди неуместны при настоящих аккаунтах).

`get_advisors` после первого прохода нашёл 2 security warning (обе SECURITY DEFINER-функции были случайно исполняемы ролью `anon`, включая `handle_new_user`, который вообще не должен быть вызываем напрямую) — поправлено отдельной миграцией (`revoke`/`grant` только нужным ролям), после чего остался один ожидаемый warning (сам факт того, что `confirm_catch` доступна `authenticated` — так и задумано).

**Приложение**: 7 экранов перенесены как клиентские React-компоненты внутри одного app-shell (`FishZoneApp.tsx`, стейт-машина экранов — аналог `goTo()`/`currentScreen` из прототипа, не отдельные Next.js-роуты — см. [[Указатель решений|DECISIONS.md]]). Карта (`LeafletMap.tsx`) — прямой перенос `initMap`/`drawTerritories` с тем же `preferCanvas:true` и зум-гейтингом подписей. Данные — через `@tanstack/react-query` хуки (`lib/supabase/queries.ts`): геометрия секторов фетчится статикой из `public/data/sectors.json` и мёржится на клиенте с владением из `territories_with_stats`. `/auth` — форма входа/регистрации email+пароль, вне app-shell. Карта/территории/активность доступны без входа; запись (улов/захват) редиректит на `/auth`, если нет сессии.

**Баг, найденный и починенный в этой же сессии**: `lib/supabase/client.ts` изначально создавал новый Supabase-клиент на каждый вызов `createClient()` — из-за этого `AuthProvider` (подписан на один экземпляр) не узнавал о входе, выполненном через другой экземпляр (форма на `/auth`), пока страница не перезагружалась полностью. Первый сквозной тест («поймать рыбу» сразу после регистрации) провалился именно на этом — `startCatchFlow` считал пользователя неавторизованным. Починено переводом `createClient()` на модуль-левel синглтон.

**Проверено вручную** через `next dev` (порт 3300, добавлен как конфигурация `fishzone-web` в `.claude/launch.json`) с реальным Supabase: регистрация → (подтверждение email через прямой SQL, т.к. тестовое письмо шло на несуществующий адрес) → вход → карта (703 сектора, публичный список/фильтры) → открыть территорию → камера → подтверждение улова → RPC `confirm_catch` → сектор стал «моя территория», записи появились в `catches`/`activity_log`, профиль/достижения/лента обновились — все проверено прямыми SQL-запросами к БД, не только по UI. Тестовый аккаунт и его данные удалены после проверки (`delete from auth.users` — каскадом почистило всё, включая владение территорией).

**Не сделано в этом заходе** (см. «Открытые вопросы» в [[Указатель решений|DECISIONS.md]]): деплой на Vercel (MCP-коннектор не авторизован, нужен явный шаг пользователя), Realtime-подписки (пока refetch-on-focus через react-query), файловые миграции `web/supabase/` (схема живёт в истории миграций Supabase, не в репозитории).

## Деплой на Vercel

MCP-коннектор Vercel не заработал ни разу за сессию — каждый вызов (`list_teams`, `create_git_project`, `get_deployment`) отдавал `403 Not authorized... re-authenticate to this scope`, независимо от переданного teamId (пробовал `personal`, `gamag`, реальный `team_...` id из тела ошибки). Штатного способа переподключить именно этот коннектор не нашлось. Весь деплой пользователь прошёл сам через веб-интерфейс Vercel по пошаговым инструкциям в чате, я диагностировал по присланным скриншотам и проверял результат через Browser-инструмент (публичные `*.vercel.app` URL не требуют моей авторизации в Vercel).

Первая попытка — проект `project-1`, который Vercel, похоже, создал сам через auto-detect сразу после пуша в GitHub (карточка «New repository detected»). У него на всех доменах (включая уникальный URL самого деплоя, не только кастомный алиас) стабильно был `404 NOT_FOUND` на уровне edge-сети — при этом сборка была зелёной, лог показывал корректный роут `/`, а в Runtime Logs не появлялось вообще ни одной записи (запросы не доходили до функции). Ни правка Root Directory (`web`), ни отключение Deployment Protection (`Require Log In`), ни повторные Redeploy (в т.ч. без билд-кэша) не помогли.

Решение — не чинить, а пересоздать: удалили `project-1` (Settings → Advanced → Delete Project) и импортировали репозиторий заново через обычный флоу Import, задав Root Directory и env-переменные (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) сразу на экране импорта. Новый проект (`web`) заработал с первого деплоя.

**Продакшен: https://web-flame-mu-44.vercel.app** — проверено вживую (карта, 703 сектора из реальной БД, без ошибок в консоли).

## Баг: карта на проде без гексагонов и обрезана

Пользователь открыл продакшен-URL в своём браузере — карта частично не показывалась, гексагонов не было вообще, только куски тайлов. Воспроизвёл в Browser-инструменте на локальном деве (баг был не только на проде — он был во всём переносе с самого начала, просто не проверялся в настоящем браузере вне превью-панели).

Причина — банальная: при переносе карты из `fishzone-app.html` (где `leaflet.min.css` подключался через `<link>` в `<head>`) забыл добавить эквивалент в Next.js-версию. Без стилей Leaflet у canvas-слоя с полигонами нет `position:absolute` (наследуется из `leaflet.css`, других источников для этого правила нет) — он рендерился как обычный `<canvas>` браузера по умолчанию (`display:inline; position:static`), поэтому visually улетал за пределы видимой области карты. Тайлы при этом выглядели более-менее нормально, потому что их позиционирование Leaflet делает через инлайновые `transform`, не только через CSS — из-за этого баг был не сразу очевиден на глаз (карта вроде рисовалась, просто без секторов и слегка криво).

Исправление: `import 'leaflet/dist/leaflet.css'` в начало `LeafletMap.tsx` (единственное место, где карта монтируется). Заодно на всякий случай добавлен `ResizeObserver` на контейнер карты, вызывающий `map.invalidateSize()` при изменении размера — не по этому багу, а как общая защита от рассинхронизации размера контейнера/карты в будущем (шрифты `next/font` могут дозагружаться и сдвигать вёрстку уже после инициализации Leaflet).

## Настоящая камера, обязательное фото, интро-экран

По запросу пользователя (скриншот с реальной геолокацией на его телефоне): убрать GPS-чип с экрана камеры и заменить симулированную камеру на настоящую (`getUserMedia`). Первый черновик плана предлагал мягкие фолбэки (пропуск фото при отказе, незаблокированный сабмит при неудачной загрузке) — пользователь их отклонил в рецензии плана, план переписан под «фото обязательно всегда» (см. [[Указатель решений|DECISIONS.md]]).

**БД** (миграция `catch_photos`): `catches.photo_url` — `text not null` (добавлена через safe default-и-drop, т.к. `ADD COLUMN NOT NULL` без дефолта падает на непустой таблице). Storage-бакет `catch-photos` (публичное чтение, запись только `authenticated` в свою папку `{userId}/...`). `confirm_catch` пересоздана: `p_photo_url text` — обязательный параметр (без дефолта, перед остальными опциональными — Postgres требует такой порядок).

**Камера** (`CameraScreen.tsx`, переписан): стейт-машина `intro→requesting→live→denied`. `intro` — объяснение + кнопка «Разрешить доступ к камере»; клик → настоящий `getUserMedia({video:{facingMode:'environment'}})`; успех → `<video>` с потоком + затвор; отказ/ошибка → `denied` — сообщение и только кнопка «Запросить доступ снова» (без обхода). Затвор рисует кадр в offscreen `<canvas>` (даунскейл до 1280px), сразу останавливает поток, кодирует JPEG (`toBlob`, качество 0.85). GPS-чип убран из UI целиком (геолокация как логика осталась, просто не показывается).

**Загрузка и форма** (`FishZoneApp.tsx`, `ConfirmScreen.tsx`, `lib/supabase/storage.ts` — новый): кадр сразу переключает на `screen-confirm` и запускает загрузку в фоне (`uploadCatchPhoto`), пока пользователь заполняет форму на том же экране — превью фото и поля вида рыбы/размера/веса/способа/наживки показываются вместе, не разными шагами. Поверх фото — статус: спиннер при загрузке, сообщение об ошибке + кнопка «Повторить попытку» (перезаливает тот же `Blob`) при неудаче. Кнопка «Подтвердить улов» задизейблена, пока не выбран вид **и** фото не загружено успешно — отправить улов без фото невозможно ни в UI, ни на уровне RPC/БД.

**Баг, найденный и исправленный при сквозной проверке**: `srcObject` присваивался `<video>` в обработчике клика сразу после `getUserMedia`, но элемент `<video>` рендерится в разметке только при `state==='live'` — в момент присвоения он ещё не существовал, поток молча терялся, экран оставался чёрным. Исправлено: `useEffect` по смене `state` подключает сохранённый в `streamRef` поток к `videoRef` уже после монтирования `<video>`.

**Второй баг, найденный при сквозной проверке**: `CameraScreen` — один и тот же React-компонент на всю сессию (экраны не размонтируются, только переключается CSS-класс `.active`), поэтому второй заход в камеру (новый улов или возврат кнопкой «назад» с экрана подтверждения) заставал компонент в состоянии `live` с уже остановленным потоком от предыдущего кадра — застывший чёрный экран вместо новой попытки. Исправлено: `FishZoneApp` держит счётчик `cameraSessionId`, инкрементирует его в каждом месте, откуда открывается камера, и передаёт как `key={cameraSessionId}` — форсирует полный ремаунт компонента с чистым состоянием `intro`.

Проверено вручную на локальном деве: `navigator.mediaDevices.getUserMedia` подменён на canvas-based `MediaStream` (`canvas.captureStream()`, рисующий видимый текст «MOCK CAM») — пройден полный путь интро→доступ→живое видео→кадр→фон-загрузка→форма→сабмит→БД (`photo_url` заполнен реальной ссылкой на Storage, файл открывается напрямую и показывает снятый кадр) → территория и достижения обновились, фото появилось в карточках уловов (`TerritoryScreen`/`ProfileScreen`) вместо градиента-плейсхолдера. Отдельно проверены оба защитных пути: отказ доступа → экран `denied` → «Запросить доступ снова» → повторный вызов `getUserMedia` (успешный) → живое видео; и неудачная загрузка (подменённый `fetch`, первый POST в Storage возвращает 500) → сообщение об ошибке + кнопка «Повторить попытку», сабмит задизейблен → повтор → загрузка проходит, сабмит разблокирован. Не проверено на реальном телефоне/камере (только эмуляцией) — см. открытый вопрос в [[Указатель решений|DECISIONS.md]].

## Метка геолокации на карте, «+» — единственный путь к камере

**Убрана ручная точка входа в камеру**: пользователь прямо указал, что вручную можно только посмотреть сектор, но не сфотографировать улов. `TerritoryScreen.tsx` лишился кнопки «Поймать и занять/переоформить территорию» и пропа `onStartCatchFlow`; `FishZoneApp.startCatchFlow()` удалена — «+» (геолокация) остался единственным путём к камере. ## Начальный зум карты, кнопки +/− и «моё местоположение»

По запросу пользователя: при заходе карта была слишком отдалена (`fitBounds` по всем 703 секторам всего побережья Аджарии), плюс не было кнопок ручного управления зумом/местоположением (`zoomControl:false` изначально, под кастомную карусель).

**`LeafletMap.tsx`**: начальный вид вместо `map.fitBounds(bounds, {padding:[36,36]})` — `map.getBoundsZoom(bounds, false, L.point(36,36))` (тот же зум, что вычислил бы `fitBounds`) плюс `Math.log2(3)` уровней (в Leaflet каждый уровень зума удваивает масштаб, значит `+log2(3)` — это ровно тройное приближение), тот же центр через `bounds.getCenter()`. `LeafletMapHandle` пополнился `zoomIn()`/`zoomOut()` (обёртки над встроенными `map.zoomIn()`/`map.zoomOut()`) и `flyToLocation(lat, lng)` (как `flyToTerritory`, но по сырым координатам, не по id сектора).

## Позиционирование лайтбокса на скролле, навигационный стек, бейдж непрочитанных уведомлений

По скриншоту пользователя с реального десктопного Chrome (фото улова открывалось «оторванным» от места, где был проскроллен экран) — три связанных запроса: починить позиционирование, сделать кнопку «назад» возвращающей на реальный экран-источник, добавить бейдж/точки непрочитанной активности с кнопкой «Прочитать все».

**Баг с лайтбоксом**: диагностирован через `getBoundingClientRect()` вживую в браузере — `top` оверлея точно равнялся `-scrollTop` содержащего его `.screen`. Причина: `PhotoLightbox`/`EditProfileModal` рендерились внутри самого экрана, чей `.screen-inner` и есть скроллящийся контейнер; `position:absolute; inset:0` внутри скроллящегося containing block считает `0` от верха контента, а не от видимой области. Исправление — оба компонента подняты на уровень `FishZoneApp.tsx` (соседи `.screens`, как уже было у модалки «Ты не на территории»); `ProfileScreen`/`TerritoryScreen`/`ActivityScreen`/`UserProfileScreen` больше не держат локальный стейт лайтбокса/модалки редактирования, получают `onOpenPhoto`/`onEditProfile` пропами.

**Навигационный стек**: `FishZoneApp.tsx` — `currentScreen` заменён на `stack: StackEntry[]` (размеченное объединение с параметрами — `{screen:'screen-territory', territoryId}`, `{screen:'screen-user-profile', userId}` и т.п.). `push()`/`pop()` вместо прямого `goTo()`; переход по вкладке нижней навигации по-прежнему сбрасывает стек (`resetTo`) — вкладки не часть истории «назад». Побочно найден и исправлен баг: общее поле `activeTerritoryId` обслуживало и поток фиксации улова, и просмотр территории — «+» поверх `TerritoryScreen` мог тихо подменить его геолоцированной территорией. Разделено на `catchTerritoryId` (только поток улова) и `viewingTerritoryId`/`viewingUserId` (управляются стеком).

**Бейдж уведомлений**: новый `lib/activityRead.ts` (`useActivityReadState`) — `lastReadAt` в `localStorage` (`fishzone:lastReadActivity:{userId}`), без изменений схемы БД (чисто косметическое, привязанное к устройству состояние). Первый визит на устройство выставляет `lastReadAt` в текущий момент (не в начало времён) — иначе вся существующая история сразу показалась бы непрочитанной. `BottomNav.tsx` — кружок с числом (`9+` при переполнении) на иконке «Активность»; `ActivityScreen.tsx` — точка у каждой непрочитанной записи, кнопка «Прочитать все» справа от фильтров-чипов (видна только пока есть непрочитанное), `onMarkAllRead()` разом убирает и точки, и бейдж.

Проверено на локальном деве: лайтбокс на профиле реального пользователя (Magamed, продакшен-данные, read-only) после скролла вниз открывается ровно во весь текущий видимый вьюпорт (`getBoundingClientRect()` — `0,0` до `window.innerWidth/innerHeight`, без смещения на `scrollTop`), фото рендерится корректно. Цепочка навигации территория→профиль владельца→та же территория→назад→назад→назад проверена по `document.querySelector('.screen.active')?.id` на каждом шаге — каждый `pop()` возвращает именно тот экран, с которого был переход, включая повторный заход на одну и ту же территорию с разными предыдущими экранами в цепочке. Бейдж/точки/«Прочитать все» проверены свежим тестовым аккаунтом (`fishzone.social.test1@example.com`) — т.к. геолокация недоступна в браузер-инструменте (permissions API вернул `denied`), новая запись активности вставлена напрямую в БД поверх уже аутентифицированной сессии тестового аккаунта, что эквивалентно результату обычной фиксации улова через RPC для целей этой конкретной проверки (сам поток `confirm_catch` не менялся и не тестировался заново в этом заходе); бейдж «1» появился сразу, точка и кнопка отрисовались на экране активности, «Прочитать все» убрало и то, и другое. Тестовый аккаунт и вставленная запись удалены после проверки (`delete from auth.users` — каскадом очистило профиль).

## Окно «Достижение открыто» больше не всплывает при каждом запуске

Причина: список уже показанных достижений хранится на устройстве, а достижения считались по городу карты. Этот город берётся из памяти устройства и лишь через мгновение сменяется городом из профиля. Если профиль загружался последним (обычно в Telegram на телефоне), в это мгновение достижения считались для другого города. «Коллекционер видов» и «Три территории» тогда выглядели «потерянными», вычёркивались из списка и всплывали снова.

Исправление в `lib/achievementUnlock.ts`:
- достижения для окна считаются по городу аккаунта из профиля;
- смена города (например, супер-админ смотрит Москву и возвращается) больше ничего не вычёркивает и не вызывает окна: открытое в новом городе молча отмечается как показанное;
- новые достижения всплывают как раньше.

Проверено на localhost с искусственно замедленной загрузкой профиля: до правки окно всплывало, после — нет; настоящее новое достижение по-прежнему показывается.

## Быстрее запуск: сектора грузятся параллельно, редкие экраны — отдельно

По запросу пользователя 28.09 («если не повредит UI и UX»).

**Сектора на карте.** Раньше цепочка была последовательной: файл геометрии → 1-я страница секторов из базы → 2-я страница. Теперь геометрия и обе страницы запрашиваются одновременно, как только прочитана сохранённая сессия (`sessionReady` в `AuthProvider`). Проверку входа на сервере запросы не ждут. Замер на localhost: данные карты готовы через ~0,33 с после старта запросов вместо ~0,72 с. Лишней загрузки «для гостя», пока сессия не прочитана, нет. Если секторов станет больше 2000, остальные страницы догрузятся по очереди, как раньше.

**Редкие экраны вынесены из стартового бандла** (`lazyScreens.tsx`):
- админские экраны и модалки;
- сброс пароля и привязка почты;
- чат, редактор и экран битвы кланов;
- «Прошлая неделя» и достижения;
- окна недели и церемонии.

Стартовый JS уменьшился на ~70 КБ (−15 КБ в gzip). Когда карта загрузилась и браузер свободен, эти куски подгружаются заранее (админские — только админам). Поэтому первое открытие такое же мгновенное, как раньше, без пустого кадра. Если кусок не загрузился (плохая сеть), загрузка повторяется ещё дважды, а потом экран предлагает «Обновить» вместо падения приложения.

**Мелкий баг заодно:** на экране сектора, пока грузились уловы, на миг показывалось «Пока нет уловов в этом секторе», хотя рядом было «30 уловов». Теперь в это время написано «Загрузка…».

## Баг: счётчик на вкладке «Активность» не сбрасывался

Точка у уведомления и счётчик на вкладке оставались после прочтения. Причина — правка под линтер 28.09. Флаг «уже отметили прочитанным» лежал в ref, а сброс при новом заходе на экран перенесли в рендер, и этот ref больше не очищался. Поэтому уведомления помечались прочитанными только при первом заходе за сессию, при следующих отметка не уходила на сервер.

Исправлено: отметка привязана к счётчику «раундов», по раунду на каждый показ непрочитанного. Заодно уведомление, пришедшее, пока экран открыт, тоже получает точку и сразу помечается прочитанным, а не висит в счётчике до следующего захода. Проверено в браузере: повторный заход и уведомление при открытом экране — по одной отметке на сервер.

## Приложение само переходит на новую версию

Запрос пользователя 28.09. Ссылка главы BFC пришла без кода приглашения, потому что у него была открыта версия до выкладки: Telegram держит мини-приложение в памяти, пока его не закрыть полностью.

Теперь приложение само проверяет версию, когда игрок возвращается в него после 30 секунд и больше в фоне. Если на сервере вышла новая версия, оно тихо перезагружается и открывает тот же экран: сектор, улов, профиль, клан, чат клана, битву, итоги недели или челленджи. Вкладки открываются с карты, как при обычном запуске. Перезагрузки не будет:
- на камере и при подтверждении улова;
- пока сохраняется улов;
- в редакторе клана;
- при входе и регистрации;
- если в видимом поле набран текст.

Проверка — один запрос `/api/version` при возвращении. Если после перезагрузки версия не сменилась (кэш), повторной перезагрузки нет.

- **Пригласи друзей.** В профиле под карточкой клана появилась карточка «Пригласи друзей». Она делится ссылкой `/?ref=<свой ID>`: в Telegram через меню «Поделиться», в браузере копирует. Раньше пригласившего запоминала только ссылка на экран (сектор, профиль…), теперь любая ссылка с `ref`. Новичок на приветственном экране видит «Друг пригласил тебя · +100 монет на старт». Начисление прежнее: +100 новичку после регистрации, +100 пригласившему после первого улова друга.
- **Баг: упоминание в чате клана считалось ссылкой.** «@Ruslan» с латинским именем быстрая проверка в приложении принимала за Telegram-ник и не давала отправить. Сервер такие упоминания и так пропускал: `post_clan_message` убирает «@» у имён участников перед фильтром. Теперь приложение делает то же самое.
- **Баг: «Поделиться» в обычном браузере уводил на t.me.** Скрипт Telegram загружается на всех страницах, поэтому `openTelegramLink` существовал и вне Telegram и просто переводил вкладку на t.me. Меню Telegram теперь открывается только внутри мини-приложения (`insideTelegram()`), в браузере ссылка копируется. Касается ссылок на клан, приглашения и подключения бота.
- **Кольцо наград вокруг аватарки.** Верхний отступ аватарки (14 px) смещал её вниз от центра кольца. Верхняя награда висела далеко, нижняя почти касалась аватарки. Внутри кольца этот отступ убран, радиус чуть больше (96), «плавание» наград уменьшено до ±3 px. Теперь отступ одинаковый со всех сторон.
- **Автообновление для гостя.** Гость на экране по ссылке после автоперезагрузки возвращается на ту же ссылку, а не на приветствие.

## Telegram: без второго аккаунта, привязка к своему аккаунту, вход в правильный аккаунт

Жалоба Руслана 29.09: «Подключить Telegram» отвечало «Этот Telegram уже привязан к другому аккаунту RANGE», хотя аккаунт у него один. Оказалось, 14.09 мини-приложение, открытое без входа, само создало ему второй, пустой аккаунт (0 уловов, онбординг не пройден) и привязало Telegram к нему. Потом Руслан вошёл по почте в свой основной аккаунт, а Telegram остался занят пустым.

Что изменилось:
- **Мини-приложение больше не создаёт аккаунт само.** При запуске оно только ищет аккаунт, привязанный к этому Telegram (`/api/auth/telegram` с `create:false`). Если такого нет, открывается приветствие с двумя кнопками:
  - «Захватить первую территорию» — новый аккаунт через Telegram;
  - «У меня уже есть аккаунт» — вход по почте.

  Кнопка «Создать аккаунт» на экране по ссылке внутри Telegram ведёт туда же.
- **Вход по почте внутри Telegram привязывает Telegram к этому аккаунту** (`/api/auth/telegram/link`). Со следующего запуска мини-приложение сразу открывает этот аккаунт. Если Telegram был занят пустым автоаккаунтом (без уловов и клана), привязка переносится. Аккаунт с игрой и аккаунт, уже привязанный к другому Telegram, не трогаются.
- **Бот («Подключить Telegram») тоже переносит привязку с пустого автоаккаунта.** Если чужой аккаунт с игрой, бот называет его имя и советует войти в него или написать администратору.
- **Баг: вход через Telegram в аккаунт с почтой.** Если к аккаунту с почтой привязан Telegram, вход в мини-приложении всё равно выпускал токен на служебный адрес `tg_…@telegram.catchrange.com`. Человека заносило в пустой аккаунт, а если такого не было, вход ломался. Теперь токен выпускается на адрес аккаунта, к которому Telegram привязан на самом деле.

Старые версии приложения, открытые до выкладки, запрашивают вход без флага и по-прежнему создают аккаунт. Так ничего не ломается, пока они не обновятся.

## Поле ввода в чате клана висело над клавиатурой (Telegram на iOS)
- Причина: в новых версиях Telegram окно приложения само сжимается над клавиатурой, а `window.innerHeight` остаётся прежним. Старая формула `innerHeight − visualViewport.height` поднимала поле второй раз, и под ним оставалась пустота высотой с клавиатуру.
- Исправление: `lib/useKeyboardInset.ts` меряет низ рамки приложения (`.app-shell`, ближайший `position:fixed` предок) против видимой области. Если окно уже сжалось, подъём нулевой, если нет — ровно высота клавиатуры. Мерится рамка, а не сам экран, потому что экран въезжает с `transform` и на старте давал лишние 10px. Тот же хук в шторке комментариев.

## Логи Supabase: превышен лимит 1 ГБ — убраны лишние запросы
- **Что было.** В панели Supabase «Log Ingestion» 1,34 ГБ из 1 ГБ бесплатного тарифа. Около 80% логов — записи о запросах к API (~2 КБ каждая), ещё ~4 МБ в сутки — строки планировщика о каждом запуске задач.
- **Telegram.** Две задачи pg_cron раз в минуту звали Vercel, а тот спрашивал базу, даже когда отправлять нечего: ~2 700 запросов к Supabase и ~2 900 вызовов Vercel в сутки. Теперь одна задача `telegram-send` зовёт маршрут только при непустой очереди (миграция `telegram_send_gated`, прогнана в откатываемой транзакции; старые задачи выключены, не удалены). Строк планировщика в логах вдвое меньше.
- **Возврат в приложение.** `staleTime` по умолчанию 15 секунд → 2 минуты (`QueryProvider.tsx`). Сектора, уловы и уведомления и так приходят по каналу реального времени, а каждый возврат из чата Telegram перезапрашивал ~15 запросов. В превью возврат через 25 секунд больше не даёт ни одного запроса.
- **Ожидание.** ~0,7–0,8 ГБ логов в месяц вместо ~1,1 ГБ, и на треть меньше вызовов функций Vercel. Если при росте снова подойдём к лимиту, следующий шаг — убрать служебные запросы браузера `OPTIONS` (~11% логов), пустив запросы к Supabase через свой домен.
