# Полноразмерное фото, аватар/имя, публичные профили и подписки, персонализированная лента

Четыре связанных запроса пользователя за один заход: лайтбокс для фото уловов, редактирование имени/аватара (без email), публичные страницы других рыбаков с подпиской, и лента активности, показывающая либо только своё (+ уведомления о потере территории), либо ещё и подписки.

**Решение: `followers_count` (статичная колонка-заглушка) заменена на вью `profiles_with_stats`, не превращена в триггер-поддерживаемый счётчик**
Тот же паттерн, что уже был выбран для `territories_with_stats` (см. решение выше в этом файле) — агрегация `count(*) from follows` дешева при разумном числе подписчиков, триггер на каждый `insert`/`delete` в `follows` добавил бы риск рассинхронизации ради экономии, которая не нужна на этом масштабе. Старая колонка `profiles.followers_count` удалена полностью (не переименована/не оставлена как deprecated) — она была буквально всегда 0, ничего не хранила, оставлять её рядом с работающим счётчиком было бы просто мёртвым полем.

**Решение: подписка/отписка — прямой `insert`/`delete` в `follows` с клиента, без RPC**
В отличие от `confirm_catch` (три таблицы, атомарность, блокировка строки от гонки), подписка — одна строка в одной таблице под RLS «можешь писать только свою». Оборачивать в `SECURITY DEFINER` RPC ради этого — не по делу; политики `insert ... with check (auth.uid() = follower_id)` / `delete ... using (auth.uid() = follower_id)` полностью достаточны.

**Решение: подписка не ретроактивна — в ленте только то, что подписанный сделал ПОСЛЕ подписки**
Первая реализация фильтровала `activity_log` только по `user_id in (подписки)`, без учёта времени — при проверке (два тестовых аккаунта, улов сделан ДО подписки) пользователь уточнил текстом: ожидание — уведомления только на новые уловы после подписки, не ретроактивная загрузка всей истории подписанного. Так и для реальных соцсетей интуитивнее: подписка — это «показывай мне, что будет дальше», не «вывали всю историю разом». Технически: `follows.created_at` сравнивается построчно с `activity_log.created_at` для каждого автора — PostgREST не может выразить разный порог для разных `user_id` в одном фильтре, поэтому это отдельный проход на клиенте поверх уже полученных (и уже суженных сервером до «моё + подписки + отняли территорию») строк, не полный клиентский фильтр с нуля — так не теряется защита от вытеснения топ-100 глобальной активностью.

**Решение: «увели территорию» — новая колонка `activity_log.previous_owner_id`, не вью с window-функцией**
Нужно было понять, что данный `'claim'` — это территория, которая раньше принадлежала текущему пользователю. Рассматривался вариант с `LAG()` по истории `claim`-строк на территорию (посчитать «предыдущего владельца» постфактум из истории). Отклонён: `confirm_catch` RPC уже вычисляет `v_prev_owner` в момент захвата (нужен для решения, писать ли `'claim'` вообще) — сохранить уже известное значение в новую колонку на порядок проще и надёжнее, чем восстанавливать его позже оконной функцией по всей таблице. Побочный эффект, на который наступили при первой реализации: у `activity_log` теперь два FK на `profiles` (`user_id`, `previous_owner_id`) — старый select с `profiles(display_name)` стал неоднозначным для PostgREST (300 «ambiguous relationship»), пришлось явно указать `profiles!activity_log_user_id_fkey(display_name)`. Ловушка была тем незаметнее, что `ActivityScreen` не проверяет `isError` — ошибка запроса тихо превращалась в пустую ленту («Пока нет активности»), а не в видимую ошибку; сам факт бага нашёлся только потому, что лента была ПУСТОЙ там, где заведомо не должна была быть.

**Решение: имя/аватар — модалка на экране профиля, не отдельный роут/экран**
Тот же принцип, что уже применён для входа (встроен в `screen-profile`, не отдельная `/auth`) — маленькая, самодостаточная форма не заслуживает собственного места в стейт-машине экранов `FishZoneApp`. Аватар грузится сразу по выбору файла (без промежуточного шага подтверждения) — решение сразу применяется (`useUpdateProfile({avatarUrl})`), как и с фото улова, ждать нажатия отдельной кнопки незачем.

**Решение: email — `<input disabled>` с явной подписью, а не просто отсутствующее поле**
По запросу пользователя («нельзя менять почту»). RLS и так не позволяет менять `auth.users.email` через `profiles` (это разные таблицы), так что можно было бы просто не показывать email в форме вообще — но явное «Email нельзя изменить» рядом с видимым (но неактивным) значением понятнее, чем молчаливое отсутствие поля, которое выглядело бы как недоделанная форма.

**Решение: список территорий/уловов чужого профиля — фильтрация уже загрученных данных, не новые запросы (кроме уловов)**
`FishZoneApp` уже держит в памяти полный массив `territories` (не про сектор — про ВСЕ 658, с `ownerId`) для карты; чужие территории — просто `territories.filter(t => t.ownerId === viewedUserId)`, без похода в БД. Уловы так не переиспользовать (нет глобального списка «все уловы всех» в памяти) — `useCatchesByUser(userId)` стал параметризованной версией того, что раньше было только `useMyCatches()` (теперь однострочная обёртка над ней).

**Решение: точки входа на чужой профиль — имя в ленте активности и владелец в карточке территории, отдельного поиска/каталога рыбаков нет**
Пользователь попросил «заходить на страницы других рыбаков», не «искать рыбаков» — этого достаточно для органического обнаружения (увидел чужой улов в ленте или на территории — зашёл к автору), отдельный экран поиска/каталога никто не просил, и создавать его сейчас — угадывать нереализованное требование.
