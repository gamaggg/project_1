# Уведомление о подписке, жалобы на фото + админ-модерация, админ-улов на любой сектор, био профиля

Четыре запроса за один заход: уведомление в ленте при новой подписке, кнопка «Пожаловаться на фото» на занятой территории с фиксированными причинами и админ-очередью модерации, право одного конкретного аккаунта (`m.alimetov@mail.ru`) добавлять улов на любой сектор без привязки к геолокации, и описание профиля («био»).

**Решение: «подписался на тебя» — синтетическая запись на клиенте из `follows`, не строка в `activity_log`**
Хранить это в `activity_log` потребовало бы делать `territory_id` nullable (у подписки нет территории) ради единственного нового вида записи, плюс завести триггер на `insert` в `follows`, дублирующий то, что и так делает клиентский `useSetFollowing()`. Вместо этого `useActivity()` при наличии сессии отдельно тянет последние строки `follows` (`followee_id = я`) и подмешивает их в общий список, пересортированный по времени — та же идея, что уже применялась для персонализации ленты (клиентский пост-обработка поверх серверной выборки), не новый архитектурный паттерн.

**Решение: `ActivityEntry.id` — строка с префиксом источника (`log:123` / `follow:<uid>`), не сырой bigint**
Как только появился второй источник данных для одного списка (`activity_log` и `follows`), встал риск коллизии id между ними (bigint `activity_log.id` и uuid `follower_id` — разные пространства, но раньше тип был `number`, что технически не позволило бы `follow`-записи иметь строковый id вообще). Простая типизация «с префиксом» устраняет и коллизию, и несовместимость типов разом, не заводя отдельного параллельного набора «непрочитанных подписок» в `lib/activityRead.ts`.

**Решение: admin — колонка `profiles.is_admin`, захардкоженная под конкретный email в `handle_new_user()`, а не отдельная таблица ролей**
На один известный аккаунт (`m.alimetov@mail.ru`, уже существующий реальный пользователь «Magamed») городить таблицу `roles`/`admins` с полноценным RBAC — оверинжиниринг; булева колонка ровно отвечает на единственный вопрос, который приложению сейчас нужен («может ли этот профиль модерировать»). `handle_new_user()` проверяет `new.email = 'm.alimetov@mail.ru'` при каждой новой регистрации — не только текущий (уже существующий и обновлённый вручную через `update`) аккаунт, но и гипотетическое пересоздание того же email в будущем сразу получит права, без повторного ручного вмешательства.

**Решение: `is_admin` публично читаем через `profiles_with_stats`, а не скрыт**
Сам факт «этот профиль — админ» не даёт никаких прав через клиентское чтение — все реальные действия (`admin_delete_catch`, `admin_dismiss_report`) перепроверяют `is_admin` внутри `SECURITY DEFINER` функции по `auth.uid()`, не доверяя тому, что прислал клиент. Прятать колонку не даёт защиты (её всё равно легко проверить, просто попытавшись выполнить админское действие), а публичность упрощает код (`useIsAdmin()` — просто поле уже загруженного профиля, не отдельный защищённый эндпоинт).

**Решение: жалобы — отдельная таблица `catch_reports` с фиксированными причинами в TS, не enum в БД**
4 причины ровно как `METHODS`/`BAITS` — короткий список для `<select>`, не растущий каталог вроде `species`, так что не нужна отдельная таблица-справочник; но и `check`-constraint на `reason` не заведён (по той же причине, по которой его нет и на `catches.method`/`catches.bait` — см. решение выше в этом файле про способ/наживку) — это не enum уровня БД, а подсказки клиента, менять список — это правка одного файла, не миграция.

**Решение: «Удалить улов» пересчитывает владельца территории из оставшихся уловов, а не просто освобождает сектор**
Первая мысль — раз улов был поддельный, всегда снимать владение с territories. Но если поддельный улов перехватил территорию поверх чужого РЕАЛЬНОГО более раннего улова (обычный сценарий модели «последний улов побеждает», см. `confirm_catch`), после удаления фейка сектор должен вернуться прежнему владельцу, а не встать свободным — иначе модерация сама создаёт вторичный баг (без вины отобранная территория). `admin_delete_catch` явно смотрит, есть ли ещё уловы на этот `territory_id` после удаления, и либо переносит владение на автора самого нового оставшегося, либо (если не осталось ни одного) освобождает сектор.

**Решение: `admin_delete_catch` полагается на уже существующий `on delete cascade` (`activity_log.catch_id` → `catches.id`, `catch_reports.catch_id` → `catches.id`), не на ручную последовательность DELETE**
`activity_log.catch_id` каскадно удалялся и раньше (проверено через `pg_constraint` перед тем, как писать функцию) — в отличие от более ранней ручной чистки сирот при удалении сектора `B1313` (см. CHANGELOG), здесь достаточно одного `delete from catches`, обе зависимые таблицы почистятся сами. `catch_reports.catch_id` заведён с тем же `on delete cascade` намеренно — жалоба существует, чтобы админ принял решение; после решения (улов удалён) сама жалоба не несёт дальнейшей ценности как отдельная запись.

**Решение: «Отклонить» — отдельная RPC `admin_dismiss_report`, хотя пользователь явно просил только «удалить улов»**
Без способа закрыть необоснованную жалобу без действия над уловом очередь модерации была бы тупиковой — каждая жалоба либо приводит к удалению чужого (возможно, настоящего) улова, либо вечно висит в списке. Это не запрошенная пользователем функция сама по себе, а необходимое следствие того, что у очереди вообще есть кнопки, а не только один нож.

**Решение: обход геолокации для админа — только клиентский UI-путь в камеру, без изменений в `confirm_catch`/RLS**
Проверено перед реализацией: RPC `confirm_catch` никогда не принимала и не проверяла координаты — «сектор должен быть рядом» всегда было проверкой на клиенте (`handlePlus()` → `nearestTerritory()`), не на сервере. Значит для «админ может добавить улов куда угодно» не нужно ослаблять никакую серверную защиту — только дать админу кнопку, которая пропускает вызов геолокации и сразу открывает камеру для выбранного вручную сектора (`TerritoryScreen` → `FishZoneApp.startAdminCatch`), используя тот же самый камера→форма→RPC пайплайн, что и обычный улов.

**Решение: био — `text` без ограничения на уровне БД, `maxLength=280` только в UI**
Как и с именем (`maxLength=40` в `EditProfileModal`, тоже не задан в БД) — ограничение длины здесь чисто UX-декоративное (не даёт разрастись карточке профиля), а не требование целостности данных, так что constraint на колонке был бы лишним.
