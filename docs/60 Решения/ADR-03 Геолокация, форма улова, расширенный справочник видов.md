# Геолокация, форма улова, расширенный справочник видов

По прямому запросу пользователя: реалистичный поток «встал на секторе → «+» → сразу камера → фото → форма (вид рыбы обязателен, остальное по желанию) → подтвердить», плюс расширение списка рыб с 3 до 36 (с разделением на морских/пресноводных). Первое изменение с момента переноса в веб-сервис, которое трогает схему БД — сделано через план (`EnterPlanMode`), не итеративно.

**Решение: список видов — то, что пользователь прислал текстом, а не то, что распознал голосовой ввод**
Первая попытка (голосом) дала нечёткий список с нераспознанными названиями («Zubar», «Testava») — переспросил, пользователь прислал точный список текстом: 23 морских (Ставрида, Барабуля, Кефаль, Морской бычок, Морская собачка, Сарган, Луфарь, Морской карась, Скорпена, Смарида, Горбыль, Каменный окунь, Пеламида, Морской дракон, Звездочёт, Скат, Катран, Чёрноморская сельдь, Мармир, Зубарь, Морской петух, Радужная форель, Черноморская форель) + 13 пресноводных (Речная форель, Кумжа, Голавль, Усач, Сазан, Карп, Карась, Щука, Судак, Окунь, Сом, Амур, Толстолобик). Старый enum (`stavrida`/`skorpena`/`laskir`) заменён целиком — `laskir` в новый список не попал (пользователь не включил), `stavrida`/`skorpena` сохранили те же ключи по смыслу.

**Решение: справочник видов — таблица `species` в БД, а не хардкод в TS**
36 записей с категорией (`marine`/`freshwater`) — это уже не маленький фиксированный список вроде `METHODS`/`BAITS` (которые остались в TS как были), а полноценный справочник, который может расшириться позже без передеплоя фронтенда. `catches.species` стал текстовым FK на `species.key` (раньше был Postgres enum `catch_species` — enum пришлось бы менять миграцией `ALTER TYPE ... ADD VALUE` на каждое добавление вида, что и негибко, и нельзя откатить в одной транзакции; текстовый FK такого ограничения не имеет).

**Решение: категория вида по умолчанию — от типа территории (`kind`), но переключаема**
`sea` → сразу «Морская», `river`/`stream`/`lake` → «Пресноводная» (`categoryForKind()`). Меньше кликов в типичном случае (рыбак почти всегда ловит то, что водится в этом типе воды), но не жёстко — вдруг он поймал что-то нетипичное или геолокация ошиблась с сектором.

**Решение: геолокация запрашивается только по нажатию «+», не автоматически на карте**
Карта публична и не требует входа (более раннее решение) — запрашивать разрешение на геолокацию у анонимного посетителя, который просто листает карту, было бы навязчиво и не нужно для этого действия. «+» уже требует вход, так что момент запроса геолокации совпадает с моментом, когда она реально нужна. Порог «человек на этой соте» — 400м от центра (сота 600м шириной, запас на неточность GPS); `getCurrentPosition` разовый на каждое нажатие, не фоновый `watchPosition` (проще, не жжёт батарею фона, свежие координаты важнее в момент фиксации улова, чем постоянное слежение).

**Решение: при неудачной геолокации — fallback на вручную открытую территорию, потом тост с ошибкой**
Не блокирует поток совсем: если геолокация отказала/недоступна/слишком далеко от всех секторов, но пользователь до этого сам открыл территорию (карта/список) — используем её. Только если вообще ничего не выбрано — тост «выбери территорию на карте».

**Решение: карта долетает до найденной по геолокации территории сразу, ещё до открытия камеры**
`MapScreen` стал `forwardRef`, прокидывает `flyToTerritory` от внутреннего `LeafletMap` наверх в `FishZoneApp` — тот же паттерн, что уже применялся для карусели (`LeafletMap`→`MapView`). Карта не размонтируется при переходе на другие экраны (только визуально скрыта через `.screen`), поэтому `flyTo` можно вызвать, даже когда в этот момент показана камера — когда пользователь потом вернётся на карту, она уже там.

**Решение: размер/вес/способ/наживка — необязательные (в форме и в БД), обязателен только вид рыбы**
Соответствует тому, как реально фиксируют улов на бегу — не всегда есть время/желание взвешивать и измерять рыбу. `catches.length_cm`/`weight_kg`/`method`/`bait` переведены в nullable (`alter column ... drop not null`), RPC `confirm_catch` — параметры с `default null`. Клиент передаёт `null`, но сгенерированные TS-типы для RPC-аргументов ожидают `undefined` для необязательных полей — на вызове `?? undefined` (иначе TS-ошибка `null` не назначается в `T | undefined`).

**Решение: «Коллекционер видов» пересчитан под новый список — 5 морских видов вместо «поймать все»**
Старая ачивка требовала поймать все 3 (из 3) видов — со старым списком это было «поймать вообще всё». С 23 морскими видами требовать «все» — нереалистичная планка для геймификационной вехи; вместо этого — фиксированный таргет (5 разных морских видов), учитываются только `category:'marine'` уловы (пресноводные виды не считаются — ачивка описана именно как «рыба Чёрного моря»).

**Решение: `personalRecord()` учитывает только уловы с указанным размером**
Раз размер необязателен, `reduce` по всем уловам (включая без размера) был бы некорректен — фильтруем на `lengthCm !== null` перед сравнением; если ни разу не указали размер — рекорда нет вообще (секция «Личный рекорд» на профиле не показывается), а не берётся случайный/нулевой улов.
