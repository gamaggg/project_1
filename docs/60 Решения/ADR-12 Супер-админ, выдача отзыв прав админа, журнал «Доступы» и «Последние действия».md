# Супер-админ, выдача/отзыв прав админа, журнал «Доступы» и «Последние действия»

Доп. запрос сразу после трёх предыдущих блоков: единственный текущий админ становится «супер-админом» с правом раздавать/забирать обычные права админа и видеть журнал действий всех админов.

**Решение: `is_super_admin` — отдельный флаг, не «уровень» поверх `is_admin`**
Простая булева колонка, а не enum ролей (`admin`/`super_admin`) — при ровно двух уровнях доступа, где верхний уровень уже подразумевает нижний (`is_super_admin=true` всегда идёт вместе с `is_admin=true`, выставляется в одном месте в `handle_new_user()`), enum добавил бы сравнения по строкам вместо простой проверки boolean без какой-либо гибкости, которая была бы использована. Та же логика, что уже применена к `is_admin`/`is_blocked` в этом проекте.

**Решение: `admin_set_admin` проверяет `is_super_admin` вызывающего, а не `is_admin`**
Прямое требование пользователя («учти что только супер админ может повышать пользователей до админа»). Это не тот случай, где два уровня прав естественно образуют иерархию для ЭТОГО конкретного действия — обычный админ, выданный супер-админом, не должен получать возможность плодить новых админов самостоятельно (иначе исходная гарантия «только я решаю, кто админ» ломается на втором шаге). Проверено вживую: прямой вызов RPC от обычного (не супер) админа отклоняется с `not authorized`.

**Решение: `details` в `admin_actions` — готовый текст, собранный в момент действия, не поля для пересборки при чтении**
Рассматривался вариант хранить только `action`/`target_user_id`/`territory_id` и собирать читаемый текст на клиенте по этим полям (JOIN'ом на лету). Отклонён: имя цели или вид пойманной рыбы на момент удаления улова — это факт того самого момента, который должен остаться в истории неизменным, даже если пользователь позже сменит имя или улов давно удалён (сам `catches`/`species`-join после `delete` уже невозможен). Готовый текст, вычисленный один раз внутри `SECURITY DEFINER`-функции (которая и так уже там же читает нужные имена для самого действия), проще и надёжнее, чем денормализованный snapshot полей + логика сборки текста, продублированная на клиенте.

**Решение: «Доступы» и «Последние действия» — один компонент (`AdminActionsScreen`) с разным фильтром, не два отдельных**
Обе разницы между экранами — заголовок и список `actionTypes` для `.in()` — не оправдывают дублирования разметки списка карточек (имя админа/детали/время), которая идентична для обеих. Тот же принцип, что уже применялся в проекте (например, `ReportPhotoModal`/`EditProfileModal` через общий `.modal-*` паттерн, а не копипаст вёрстки).

**Решение: кнопка «Выдать/забрать права админа» скрыта на профиле другого супер-админа (клиентская проверка задваивает серверный guard)**
Сейчас это единственный практический случай (один супер-админ), но проверка на клиенте не полагается на это допущение — если в будущем появится второй супер-админ, UI не будет показывать кнопку, которая всё равно была бы отклонена сервером; тот же принцип defense-in-depth, что уже применён к кнопке «Заблокировать» (тоже скрыта для чужих админов, хотя сервер и так отклонил бы).
