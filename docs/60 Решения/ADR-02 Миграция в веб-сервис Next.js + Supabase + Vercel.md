# Миграция в веб-сервис: Next.js + Supabase + Vercel

Пользователь решил делать не прототип, а настоящий веб-сервис — многопользовательский, с реальными аккаунтами. Ниже — решения, зафиксированные при переходе (все — явный выбор пользователя через вопросы в чате, не решены за него).

**Решение: стек — Next.js + Supabase (Postgres/Auth) + Vercel**
Причина: в сессии уже были подключены MCP-инструменты обоих сервисов — прямой намёк на связку, и она же самая быстрая для этого масштаба (React-фреймворк с бэкендом на одном языке, БД+Auth из коробки, деплой в один клик). Другие стеки не оценивались.

**Решение: `web/` — соседняя папка в том же репозитории (монорепо), `fishzone-app.html`/`tools/fishing-hex/` не трогаются**
Причина: `tools/fishing-hex` — общий источник геометрии для обоих поколений (прототип и веб-сервис), логично держать их рядом. Прототип оставлен как есть — исторический референс дизайна, из которого `web/` был перенесён, не удалён и не обновляется дальше.

**Решение: дизайн/экраны переносятся 1:1, кроме фейковой рамки телефона/статус-бара — их убрали**
`.device`/`.statusbar`/`.notch` в прототипе существовали только для превью в браузере на десктопе (эмуляция экрана iPhone 390×844). В реальном вебе, открытом на настоящем телефоне, это стало бы вторым статус-баром поверх настоящего — решили убрать, заменив на честную адаптивную вёрстку (`.app-shell{max-width:480px;margin:0 auto}` — full-bleed на мобильном, по центру на десктопе). Все цвета/радиусы/тени/шрифт/компонентные классы (`.card`, `.btn-primary`, `.badge-*`, и т.д.) перенесены из `fishzone-app.html` практически дословно — см. `web/app/globals.css`.

**Решение: авторизация сразу и по-настоящему — Supabase Auth, email+пароль**
Причина: территории должны принадлежать реальным людям, не одному демо-юзеру — иначе «веб-сервис» не отличался бы от прототипа по сути. Email+пароль выбран для v1 вместо magic link/OAuth — не требует настройки внешних OAuth-приложений или зависимости от доставки писем для самого входа (регистрация всё равно требует подтверждения email — это дефолт Supabase, не отдельная настройка, см. [[00 Главная|DOCS.md]]).

**Решение: карта/территории/лента активности публичны без входа; вход нужен только для записи (улов/захват территории)**
Strava-style: смотреть чужие уловы и карту может кто угодно, вход — только когда хочешь сам что-то сделать. Реализовано через RLS `select using (true)` на всех таблицах + проверку сессии в `FishZoneApp.startCatchFlow` (редирект на `/auth`, а не тихий no-op).

**Решение: все 703 территории стартуют свободными — никаких demo-аккаунтов вместо старых `B1127`/`B1126`/`B1079`**
Причина: раз территории теперь принадлежат настоящим людям, подсовывать фиктивных «Алексея»/«Марину» как реальные аккаунты — обман; создавать реальные тестовые аккаунты только ради демо-заполненности карты тоже не имеет смысла для только что запущенного сервиса. Карта просто пустая (все свободны), пока реальные пользователи её не заполнят.

**Решение: геометрия секторов — статический JSON-ассет (`web/public/data/sectors.json`), не строки в Postgres**
Причина: 6 вершин × 703 сектора никогда не меняются в рантайме и не нужны для RLS/агрегаций — гонять их через БД на каждый запрос бессмысленно. В Postgres — только «тонкая» `territories` (id/kind/lat/lng/owner_id) для целостности FK (`catches`/`activity_log` ссылаются на неё) и владения. См. [[00 Главная|DOCS.md]], раздел «База данных».

**Решение: тип водоёма сектора — из `territories.kind`, `sectors.json` только запасной вариант; у каждого сектора из файла есть строка в БД**
Раньше клиент брал `kind` из `sectors.json`, а серверные челленджи («Картограф», «Разведка», «Коллекционер вод») и достижение «Обошёл всё побережье» — из `territories.kind`. Расхождения: 675 московских секторов вообще не имели строки (просмотры и уловы там не засчитывались), `confirm_catch` создавал строки без `kind`, а слияние ручьёв в реки в БД не было видно в приложении. Теперь все сектора из файла дозаполнены в `territories` (id/kind/lat/lng, без `corners`, геометрия по-прежнему из файла), клиент берёт `kind` из БД, а супер-админ меняет его на экране сектора (`admin_set_territory_kind`, заодно пересчитывает цель открытых «Картографов» города). Ручьёв больше нет: Батуми — море/река/озеро/пруд, Москва — река/озеро/пруд (`WATER_KINDS_BY_CITY`); значение `stream` осталось в enum только ради старых строк. **Вывод на будущее**: при перегенерации сетки (`tools/fishing-hex`) новые сектора нужно сразу завести в `territories` с типом, а скрипты по-прежнему размечают ручьи — их надо переводить в реки.

**Решение: `catch_count`/`last_catch_at` — вью с агрегацией (`territories_with_stats`), не денормализованные колонки**
Причина: 703 территории — агрегация по `catches` дешёвая при любом разумном трафике; денормализация потребовала бы триггеров и создала риск рассинхронизации ради экономии, которая тут не нужна.

**Решение: запись только через RPC (`confirm_catch`), не прямые INSERT/UPDATE от клиента**
Причина: `confirmCatch()` в прототипе атомарно делает три вещи (улов, смена владельца, запись в ленту) — RPC с `SECURITY DEFINER` и `select … for update` на строке территории повторяет то же самое атомарно и безопасно при параллельном заходе двух пользователей на одну свободную территорию (кто первый — тот и получил). Прямые insert/update-политики клиентам не выданы: без RPC создать улов без реального `auth.uid()` или подделать владение нельзя.

**Решение: единый клиентский app-shell со стейт-машиной экранов, а не отдельные Next.js-роуты на каждый экран**
Причина: переходы-кроссфейды между 7 экранами и эфемерный `pendingCatch` (камера→подтверждение) проще и надёжнее перенести как React-стейт в одном компоненте (`FishZoneApp.tsx`), как это было устроено в прототипе (`goTo()`/`currentScreen`), чем резать на роуты — ни один экран сейчас не должен быть шаримой ссылкой, а настоящая навигация браузера рисковала бы потерять `pendingCatch` между камерой и подтверждением.
> **Уточнение**: изначально `/auth` был единственным отдельным роутом вне shell — позже убран целиком (см. «Форма входа встроена в профиль» ниже), теперь весь app-shell — один роут (`/`), без исключений.

**Решение: Realtime-подписки Supabase — не в v1, обновление на фокусе вкладки (`@tanstack/react-query`, `refetchOnWindowFocus`)**
Причина: проще для первой версии; переход на Realtime позже — локальное добавление (инвалидация query на `postgres_changes`), не переписывание архитектуры данных.

**Решение: `lib/supabase/client.ts` — синглтон, не фабрика нового клиента на каждый вызов**
Наступили на грабли в этой же сессии: с фабрикой (`createBrowserClient()` при каждом `createClient()`) форма входа создавала СВОЙ экземпляр Supabase-клиента, отдельный от того, на который подписан `AuthProvider` — `onAuthStateChange` срабатывает только на экземпляре, который сам выполнил вход/выход, поэтому после логина `AuthProvider` не узнавал о новой сессии без полной перезагрузки страницы (первый прогон end-to-end теста «поймать рыбу» упал именно на этом — `startCatchFlow` считал пользователя неавторизованным сразу после успешного входа). Починено модуль-левел синглтоном. **Вывод на будущее**: Supabase-клиент в браузере должен быть один на вкладку, если где-то в приложении есть больше одного места, которое его создаёт и на него подписывается.

**Решение: Next.js 16 — используем `proxy.ts` вместо `middleware.ts`**
В установленной версии (16.3.4, новее тренировочных данных модели — увидели явное предупреждение в `web/AGENTS.md`, которое Next.js сам кладёт в свежий проект) файл-конвенция `middleware.ts`/`export function middleware` переименована в `proxy.ts`/`export function proxy`; механика (cookies, matcher, `NextResponse`) не изменилась. Узнали из `node_modules/next/dist/docs/` перед тем как писать код, а не через ошибку компиляции постфактум.

**Решение: `proxy.ts` удалён — сессию обновляет только браузерный клиент**
Стандартный для Supabase SSR middleware (`getUser()` на каждый запрос, чтобы «освежить» cookie) оказался причиной того, что пользователей постоянно выбрасывало из аккаунта и приложение возвращалось на экран входа — и в браузере, и в Telegram Mini App. Механика: refresh-токены Supabase одноразовые с ротацией, а matcher ловил вообще все запросы, так что один заход в приложение порождал десяток параллельных вызовов middleware, каждый из которых пытался провернуть ротацию тем же самым токеном. В логах Auth это видно как пачка `refresh_token_not_found` на `/token` в пределах одной-двух секунд с полутора десятков IP Vercel (плюс `session_not_found` 403 на `/user`); проигравшие гонку — в том числе сам браузер — получали отказ, `supabase-js` считал сессию невалидной и разлогинивал, после чего Mini App уходил на повторный вход через `admin/generate_link` → `/verify` и часто ловил там `otp_expired`. Предыдущая попытка починки (буферизовать cookie и записывать их только при успешном `getUser()`) убрала лишь propagation чужой ошибки, но не саму ротацию токена middleware'ом, поэтому гонка осталась.
Сервер-сайду сессия здесь не нужна вообще: серверных компонентов, читающих `auth`, в проекте нет, а два роут-хендлера (`/api/auth/complete-email-link`, `/api/telegram/link-token`) создают свой клиент и работают с cookie сами, по одному запросу за раз. Браузерный `createBrowserClient` (`lib/supabase/client.ts`, синглтон) хранит сессию в cookie и обновляет её сам, последовательно и с внутренней блокировкой. **Вывод на будущее**: для SPA-приложения без серверного чтения сессии middleware из гайдов Supabase — чистый минус (лишний round-trip на каждый запрос плюс гонка за одноразовый refresh-токен). Не возвращать.

**Решение: Node.js скачан локально в `.tools/node/` (не установлен системно, не через nvm/Homebrew — их тоже не было)**
В среде разработки не оказалось вообще никакого JS-тулчейна (ни `node`, ни `npm`, ни менеджера версий, ни Homebrew). Вместо системной установки (нет sudo/доступа к системным путям от инструмента) — скачан официальный tar.gz с nodejs.org (v24 LTS, «Krypton», arm64) и распакован в `.tools/node/` внутри репозитория, добавлен в корневой `.gitignore`. Все npm/node-команды в этой и будущих сессиях требуют `export PATH=".../.tools/node/bin:$PATH"` перед запуском — шелл-стейт инструмента не персистится между вызовами, окружение задаётся заново каждый раз (это не изменение системы пользователя, никакие системные файлы/PATH не тронуты за пределами репозитория).

**Решение: первый Vercel-проект удалён и создан заново через обычный Import, а не починен на месте**
При первом подключении (через MCP `create_git_project`, упавший на 403 из-за нерабочей авторизации коннектора) в аккаунте пользователя откуда-то появился проект `project-1`, автоматически привязанный к `gamaggg/project_1` — по всей видимости, сработал стандартный auto-detect Vercel для только что запушенного репозитория, независимо от наших действий. У этого проекта на всех проверенных доменах (включая собственный уникальный URL конкретного деплоя, не только кастомный алиас) стабильно был 404 `NOT_FOUND` на уровне Vercel edge — при этом сборка была полностью успешной (логи показывали корректный роут `/`), а в Runtime Logs не было вообще ни одного request-лога, то есть запросы не доходили до функции вообще, останавливаясь на маршрутизации домена. Ни смена Root Directory, ни отключение Deployment Protection, ни повторные Redeploy (в т.ч. без билд-кэша) это не поправили. Решили не разбираться дальше в природе поломки — удалили проект (Settings → Advanced → Delete Project) и создали новый через обычный флоу Import (карточка «New repository detected» → Root Directory/env переменные выставлены сразу при импорте). Новый проект заработал с первого деплоя. **Вывод на будущее**: если у только что созданного/auto-detected Vercel-проекта домен стабильно 404-ит на пустых Runtime Logs при зелёной сборке — это, похоже, дешевле починить пересозданием проекта через Import, чем разбираться, в каком именно внутреннем состоянии Vercel он застрял.

**Решение: деплой в итоге сделан руками пользователя через веб-интерфейс Vercel, не через MCP**
MCP-коннектор Vercel был доступен по имени инструментов, но каждый вызов (`list_teams`, `create_git_project`, `get_deployment`, …) отдавал `403 Not authorized: ... re-authenticate to this scope` независимо от того, какой teamId передавался (`personal`, `gamag`, реальный `team_...` id из тела ошибки) — то есть сам токен коннектора был нерабочим, а не просто неверно указан scope. Штатных инструментов «переподключить коннектор»/получить ссылку авторизации в рамках этой сессии не нашлось (`suggest_connectors`/`list_connectors` не видели Vercel как переключаемый коннектор вообще — судя по всему, это отдельная интеграция уровня Claude Code/аккаунта, не обычный MCP-коннектор). Пользователь прошёл весь путь (создание env-переменных, Root Directory, Deployment Protection, удаление и пересоздание проекта) вручную по скриншотам, я только читал логи/статусы через Browser-инструмент (у которого доступ к самим *.vercel.app URL не требует авторизации Vercel API) и давал следующий шаг.

**Решение: Confirm email временно выключен в Supabase Auth**
При первой же попытке пользователя зарегистрироваться на проде словили `email rate limit exceeded` — дефолтный (не настроенный отдельно) email-сервис Supabase имеет очень маленький лимит писем, аккаунт при этом не создаётся вообще (падает до записи в БД, подтверждать через SQL было нечего, в отличие от более раннего теста в этой же сессии). Чтобы не блокировать тестирование, выключили Confirm email (Dashboard → Authentication → Sign In / Providers) — регистрация теперь сразу даёт активную сессию. **Это временно**: без подтверждения email любой человек может зарегистрироваться на чужой email без проверки владения им — приемлемо, пока сервис не публичный, но перед реальным запуском нужно либо вернуть подтверждение вместе со своим SMTP-провайдером (снимет лимит), либо осознанно решить, что подтверждение почты вообще не нужно для этого продукта.

**Решение: форма входа встроена в screen-profile, отдельного роута `/auth` больше нет**
По прямому запросу пользователя после первого раунда тестирования на проде: раньше «+» без сессии редиректил на `/auth`, а вкладка «Профиль» без входа показывала пустую заглушку (плейсхолдеры вместо имени/статистики) — два разных места для одного и того же «нужен вход», нелогично. Теперь `AuthForm.tsx` (вынесена из бывшего `app/auth/page.tsx` в переиспользуемый компонент, без `router.push`) рендерится прямо в `ProfileScreen`, когда `user` пуст — и «+», и сама вкладка «Профиль» ведут в одно и то же место. Успешный вход/регистрация ничего никуда не редиректит: `AuthProvider` реактивно обновляет `user`, `ProfileScreen` сам переключается с формы на настоящий профиль. По той же причине «Выйти» сразу возвращает форму входа на этом же экране — это просто следствие того, что рендер экрана целиком зависит от `user`, а не отдельное поведение кнопки.
`app/auth/` (папка) удалена; `.auth-wrap` (CSS для полноэкранной раскладки формы) убран как мёртвый, `.auth-card` получил `margin:0 auto` для центрирования внутри `.screen-inner`.
