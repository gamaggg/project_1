# Открытые вопросы / не решено

- Приложение задумано и называется как «береговая морская рыбалка», а с переходом на инструмент друга фактически стало «рыбалка у любой воды (море/река/ручей/озеро) по всей Аджарии» — не решено, стоит ли переименовать/перепозиционировать продукт под новый охват, или в будущем сузить данные обратно до только моря / только части побережья (инструмент это поддерживает — правка `PRIORITY`/фильтра в `build_hex.mjs` и BBOX).
- 703 сектора отрисовываются и рендерятся в список/карусель без кластеризации или виртуализации (см. [[00 Главная|DOCS.md]], «Известные ограничения») — пока быстро при демо-нагрузке, не проверено при реальном многопользовательском трафике.
- MCP-коннектор Vercel не заработал за всю сессию (постоянный 403, см. решение выше) — деплой сделан вручную через веб-интерфейс. Если он остаётся сломанным и в следующей сессии — не тратить время на повторные попытки `list_teams`/`create_git_project`, сразу вести пользователя по UI (Vercel Dashboard: Root Directory `web`, env-переменные `NEXT_PUBLIC_SUPABASE_*`, см. [[00 Главная|DOCS.md]] «Деплой»).
- Realtime не подключён (см. решение выше) — если многопользовательский сценарий окажется активным (несколько рыбаков одновременно смотрят карту), стоит переоценить, достаточно ли refetch-on-focus.
- `web/supabase/` как каталог файловых миграций не заведён — схема применена напрямую через Supabase MCP в разговоре (см. [[00 Главная|DOCS.md]]). Стоит выгрузить в файлы, если появится локальная разработка через Supabase CLI или понадобится история миграций в git.
- Фото и аватары из Storage в ночную копию базы не входят (см. «Резервные копии базы»). Их можно копировать отдельно, но для этого GitHub понадобится служебный ключ Supabase. Пока решено обойтись без этого.
- Названия видов рыб в ленте активности не склоняются падежно («поймал скорпена») — полноценное русское склонение 36 существительных не стали строить (нужен был бы словарь форм или библиотека морфологии), не критично для читаемости.
- Порог геолокации (400м) и выбор «разовый getCurrentPosition вместо watchPosition» не проверялись в реальных полевых условиях (только эмуляцией координат в браузере) — точность GPS на телефоне у воды, скорость получения фикса и поведение при плохом сигнале не протестированы.
- Настоящая камера (`getUserMedia`) проверена только эмуляцией `MediaStream` (canvas → `captureStream()`) — весь цикл интро→доступ→кадр→загрузка→БД пройден так, но не на реальном телефоне/браузере. Стоит попросить пользователя пройти поток на своём устройстве (он именно там впервые увидел GPS-координаты, есть под рукой) и проверить: реальное качество/ориентацию фото с задней камеры, поведение `facingMode:'environment'` на разных телефонах, и что происходит при повторном отказе после явного запрета доступа (браузер может не показывать системный диалог повторно — тогда кнопка «Запросить доступ снова» будет молча не срабатывать, у пользователя останется только подсказка проверить настройки сайта).
