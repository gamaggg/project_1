# Убраны сектора над «микро-ручьями» (порог длины водотока)

Пользователь прислал скриншот с продакшена: кластер соседних `stream`-секторов над лесистым/горным участком без видимой воды на тайле — технически касаются OSM-линии `waterway=stream`, но по факту незначительные ручьи/канавы, не места для рыбалки. Попросил убрать подобные.

**Решение: фильтр по суммарной длине связного водотока (порог 800м), не по отдельному OSM-way и не по тегу**
У 587 линий-ручьёв в bbox почти нет метаданных о размере — именованы только 8. Единственный доступный сигнал — геометрическая длина. Но считать по отдельному OSM-`way` нельзя: мапперы часто режут один и тот же физический ручей на много мелких сегментов (пересечения дорог, административные границы и т.п.) — наивная длина одного фрагмента ничего не говорит о размере настоящего ручья. Решение: склеить связанные `waterway`-way (кроме `river`) в целые водотоки union-find'ом по общим id узлов OSM, считать суммарную длину каждого водотока, и уже её сравнивать с порогом (`STREAM_MIN_LENGTH_M = 800` в `build_hex.mjs`). River-сегменты в склейку не включаются намеренно: иначе крошечный приток, впадающий в большую реку через общий узел, унаследовал бы длину всей реки, и порог перестал бы что-либо отличать.

**Порог подобран экспериментально, не теоретически**: прогнали симуляцию на реальных данных при разных порогах (100–1000м) и посмотрели, что реально удаляется. 400м — безопасно (не задевает ни одной уже занятой территории), но не убирает ни одного сектора со скриншота пользователя. 800м — убирает ровно те сектора со скриншота (6 из 8) и ещё 39 похожих по всему bbox (итого 45 из 703, все `kind:'stream'`, 320→275); выбран пользователем явно, после того как ему показали оба варианта с count'ами.

**Решение: сектор `B1313` (единственный из 45 с реальным уловом) удалён вместе с остальными, не защищён отдельно**
Изначально предполагалась защита уже занятых секторов от удаления геометрическим фильтром (чтобы не терять реальные данные пользователей). Пользователь уточнил текстом: улов на `B1313` — тест его друга, никакой ценности как реальные данные не несёт, защищать не нужно. Перед удалением строки `territories` вручную почищены зависимые `activity_log` (id 13, 14) и `catches` (id 7) — иначе упал бы FK. Фото в Storage осталось сиротой (прямой `delete` в `storage.objects` заблокирован Supabase, `storage.protect_delete()`) — не мешает, как и два похожих осиротевших файла из более ранней сессии тестирования камеры.

**Вывод на будущее** (см. также обновлённый раздел в [[00 Главная|DOCS.md]] «tools/fishing-hex»): теперь, когда территориями реально владеют живые пользователи, регенерация сетки — больше не безобидная операция «переисполнить один скрипт». Перед удалением любого id из `sectors.json`/`territories` нужно проверять, нет ли на нём реальных `catches`/`owner_id`, и осознанно решать (сохранить/расчистить), а не полагаться на автоматическое исчезновение строки, как было до запуска в прод.
