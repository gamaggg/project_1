## Что это

FishZone — приложение для рыбалки у воды в Аджарии (море, реки, ручьи, озёра — весь берег от Сарпи до Чакви). В проекте сейчас два поколения:

- **`web/`** — действующий продукт: настоящий веб-сервис (Next.js + Supabase + Vercel), многопользовательский, с реальными аккаунтами. Разработка идёт здесь. См. раздел «Веб-сервис (web/)» ниже.
- **`fishzone-app.html`** — исходный однофайловый прототип (без сборки, без бэкенда, один захардкоженный демо-пользователь, данные в памяти браузера). Дальше не развивается, оставлен как референс дизайна/логики, из которого `web/` был перенесён почти один-в-один. См. раздел «Прототип (fishzone-app.html)» ниже.

Оба используют одну и ту же геометрию секторов из `tools/fishing-hex/` (гексагональная сетка 600м по реальным данным OpenStreetMap — море/река/ручей/озеро, см. раздел «Сектора»).

## Веб-сервис (web/)

Next.js (App Router, TypeScript) + Supabase (Postgres, Auth) + Vercel (деплой). Дизайн и экраны перенесены из `fishzone-app.html` почти один-в-один (см. DECISIONS.md) — те же 7 экранов, те же CSS-токены/классы, та же логика достижений/статистики. Отличие — не выдумка/редизайн, а следствие смены платформы: настоящие аккаунты вместо одного демо-юзера, данные в Postgres вместо памяти браузера, публичная карта без входа (Strava-style), убрана декоративная рамка телефона/статус-бар (незачем рисовать второй поверх настоящего в реальном браузере на телефоне).

### База данных (Supabase Postgres)
Проект `yhgdcdkfkerzuhnzjzrz` («Project 1», см. `mcp__…__list_projects`). Схема применена через Supabase MCP (`apply_migration`), не через файлы в репозитории — если нужно посмотреть точный DDL, он в истории миграций проекта в Supabase, а актуальная схема получается через `list_tables`/`generate_typescript_types`.

Таблицы:
- **`profiles`** — `id` (=`auth.users.id`), `display_name`, `location`, `avatar_url` (nullable), `bio` (nullable), `is_admin` (`boolean not null default false`, см. «Админ: `profiles.is_admin`» ниже), `is_super_admin` (`boolean not null default false`, см. «Супер-админ» ниже), `is_blocked` (`boolean not null default false`, см. «Блокировка пользователя» ниже), `public_id` (`text not null unique`, 5 цифр, см. «Публичный ID пользователя» ниже). Создаётся автоматически триггером `handle_new_user()` при регистрации.
- **`admin_actions`** — журнал действий админов: `admin_id` (FK `profiles`, `on delete cascade`), `action` (`grant_admin`/`revoke_admin`/`delete_catch`/`dismiss_report`/`block_user`/`unblock_user`), `target_user_id`/`territory_id` (nullable, контекст действия), `details` (готовый человекочитаемый текст, собранный внутри RPC в момент действия — не пересобирается при чтении), `created_at`. `select` — только `is_super_admin`. См. «Супер-админ» ниже. Читать/писать `followers_count`/`following_count` напрямую нельзя — это не колонки, см. `profiles_with_stats` ниже.
- **`follows`** — подписки: `follower_id`, `followee_id` (оба FK на `profiles`, составной PK, `check (follower_id <> followee_id)`). Публично читаема; `insert`/`delete` — только своя строка (`auth.uid() = follower_id`), без RPC (простая одно-табличная операция, RPC тут не нужен, в отличие от `confirm_catch`).
- **`catch_reports`** — жалобы на фото: `catch_id` (FK `catches`, `on delete cascade`), `reporter_id` (FK `profiles`, `on delete cascade`), `reason` (text, один из `REPORT_REASONS`, не enum), `created_at`. `insert` — любой `authenticated` на свою `reporter_id`; `select` — только `is_admin`-профили. См. «Жалобы на фото и модерация» ниже.
- **`territories`** — «тонкая» таблица только для владения: `id` (текст вида `"B0144"`, совпадает с `public/data/sectors.json`), `kind`, `lat`, `lng`, `owner_id` (nullable FK на `profiles`), `claimed_at`. Геометрия (`corners`) сюда намеренно не входит — она статична и живёт в `public/data/sectors.json` (см. DECISIONS.md, почему не денормализовали в БД).
- **`species`** — справочник видов рыб: `key` (текстовый slug, PK), `name`, `category` (`'marine'`|`'freshwater'`). 36 записей (23 морских + 13 пресноводных, список — в DECISIONS.md), читается публично, пишется только вручную через миграции (не UI). Таблица, а не хардкод в TS — в отличие от `METHODS`/`BAITS` (маленькие фиксированные списки), 36+ видов с категорией — уже полноценный справочник, который может расти без передеплоя.
- **`catches`** — один улов: `territory_id`, `user_id`, `species` (текст, FK на `species.key`), `length_cm`/`weight_kg`/`method`/`bait` (все **nullable** — обязателен только вид рыбы, остальное по желанию рыбака, см. DECISIONS.md), `photo_url` (**text, NOT NULL** — без загруженного фото улов не создаётся вообще, см. DECISIONS.md), `caught_at`.
- **`activity_log`** — лента активности: `user_id`, `territory_id`, `kind` (`'catch'`|`'claim'`), `catch_id`, `previous_owner_id` (nullable FK на `profiles`, заполняется только у `'claim'`-строк — кто владел территорией до захвата, см. «Персонализированная лента активности» ниже). Пишется атомарно вместе с уловом внутри RPC (не отдельным клиентским запросом).
- **`territories_with_stats`** (view, `security_invoker`) — `territories` + `catch_count`/`last_catch_at`, агрегированные из `catches`. Не денормализовано в саму таблицу — 658 территорий, агрегация дешёвая, лишний триггер/риск рассинхронизации не нужен.
- **`profiles_with_stats`** (view, `security_invoker`) — `profiles` + реальные `followers_count`/`following_count` (агрегация из `follows`, тот же паттерн, что `territories_with_stats`). Заменила прежнюю статичную колонку-заглушку `profiles.followers_count` (она удалена). Все чтения профиля (`useProfile`) идут через эту view, не через `profiles` напрямую; запись (`useUpdateProfile`) — по-прежнему в `profiles` (обновлять вью нельзя).

RLS: все таблицы читаются публично (`select using (true)`) — карта, список территорий, лента активности, справочник видов и подписки видны без входа (см. решение «Карта публична» в DECISIONS.md). Прямых `insert`/`update` политик для клиентов нет, кроме `follows` (своя строка) и `profiles` (своя строка, `update using (auth.uid() = id)` — уже была на момент создания таблицы, использована для редактирования имени/аватара без новых миграций RLS). Вся остальная запись — через RPC.

RPC `admin_delete_catch(p_catch_id)`/`admin_dismiss_report(p_report_id)`/`admin_set_blocked(p_user_id, p_blocked)` — все `SECURITY DEFINER`, доступны роли `authenticated` (явный `revoke ... from anon`, та же необходимость, что была у `confirm_catch`/`handle_new_user` — Supabase по умолчанию даёт `anon` выполнять новые функции), но сами проверяют `is_admin` внутри и бросают исключение, если вызвавший не админ — грант на `authenticated` тут не является границей авторизации, ей является проверка внутри тела функции. `confirm_catch` дополнительно проверяет `is_blocked` вызывающего. См. «Жалобы на фото и модерация» и «Блокировка пользователя» ниже.

RPC `confirm_catch(p_territory_id, p_species, p_photo_url, p_length_cm default null, p_weight_kg default null, p_method default null, p_bait default null)` — `SECURITY DEFINER`, доступна только роли `authenticated`. `p_photo_url` — обязательный параметр (не `default null`), стоит перед необязательными (Postgres требует параметры с дефолтом последними). Атомарно (с `select … for update` на строке территории, чтобы не ловить гонку при одновременном захвате): вставляет улов → переводит `owner_id` территории на текущего пользователя (последний улов побеждает — так же, как в прототипе) → пишет `activity_log` (запись `'catch'`, и `'claim'` дополнительно с `previous_owner_id` = прежним владельцем, если территория поменяла владельца). Клиент вызывает её через `supabase.rpc('confirm_catch', {...})` в `lib/supabase/queries.ts` (`useConfirmCatch`), передавая `null` вместо `undefined` для необязательных полей (сгенерированные типы RPC хотят `undefined` — конвертация через `?? undefined` на вызове, см. код).

**Storage**: два публичных на чтение бакета. `catch-photos` — `insert` только `authenticated`, только в свою папку (`(storage.foldername(name))[1] = auth.uid()::text`), путь `{userId}/{timestamp}.jpg`, см. `lib/supabase/storage.ts` (`uploadCatchPhoto`). `avatars` — тот же паттерн политик и путей, `uploadAvatar`. Оба бакета не поддерживают `update`/`delete` объектов с клиента — новый аватар/фото всегда грузится под новым именем файла (`Date.now()`), старый файл остаётся сиротой в бакете (безвредно, см. CHANGELOG.md).

### Авторизация
Supabase Auth, email+пароль (см. DECISIONS.md почему не magic link/OAuth в v1). Формы входа/регистрации отдельного роута `/auth` больше нет — `AuthForm.tsx` встроена прямо в `screen-profile` (см. DECISIONS.md, «форма входа встроена в профиль»). **Confirm email выключен** (Supabase Dashboard → Authentication → Sign In / Providers → Confirm email) — регистрация сразу даёт активную сессию, без письма. Это временно, ради тестирования (дефолтный email-сервис Supabase уткнулся в rate limit почти сразу — см. DECISIONS.md); перед реальным публичным запуском стоит вернуть подтверждение (и/или подключить свой SMTP, чтобы rate limit не мешал живым пользователям).

`components/providers/AuthProvider.tsx` держит текущую сессию (`supabase.auth.onAuthStateChange`) в React-контексте, используется всем app-shell'ом. **Важно**: `lib/supabase/client.ts` — синглтон (`createClient()` возвращает один и тот же экземпляр на вкладку). Отдельный `createBrowserClient()` на каждый вызов — частая ошибка: `onAuthStateChange` срабатывает только на том экземпляре, который выполнил вход/выход, поэтому форма логина и `AuthProvider` с разными инстансами друг друга не видят без полной перезагрузки страницы. Наступили на эти грабли и в этой сессии — см. запись в CHANGELOG.md.

Карта/территории/активность/профиль доступны без входа (просмотр). Попытка нажать «+» без сессии переключает на вкладку «Профиль» (не молча ничего не делает) — а там без сессии сразу форма входа/регистрации, а не пустая заглушка.

### Карта
`LeafletMap.tsx` — прямой перенос `initMap()`/`drawTerritories()` из прототипа: `preferCanvas:true`, `labelsLayer` (id-подписи секторов) показывается только при `zoom >= 14`, перерисовка полигонов (при смене статуса владения) намеренно не связана с перерисовкой карусели/зумом — те же причины, что в прототипе (см. DECISIONS.md, баг `flyTo`↔`zoomend`↔сброс карусели). Геометрия (`public/data/sectors.json`) фетчится один раз и кешируется навсегда (`staleTime: Infinity` в `useTerritories`/`useSectorsGeometry`), статус владения — через `territories_with_stats`, объединяются по `id` на клиенте.

`import 'leaflet/dist/leaflet.css'` — в начале `LeafletMap.tsx` (единственное место монтирования карты). Без этого импорта у canvas-слоя нет `position:absolute` (это правило только из leaflet.css) — сектора рендерятся, но улетают за пределы видимой области. Забыли при переносе из прототипа (там подключался через `<link>`), поймали только когда посмотрели живой прод в настоящем браузере — см. CHANGELOG.md. Помимо этого — `ResizeObserver` на контейнер карты, вызывает `map.invalidateSize()` при изменении размера (шрифт `next/font` может дозагрузиться и сдвинуть вёрстку уже после инициализации Leaflet).

`LeafletMapHandle.showUserLocation(lat, lng)` — маркер реальной позиции пользователя (синяя точка с CSS-пульсацией, `.user-location-icon`/`.user-location-dot`/`.user-location-pulse` в `globals.css`), отдельный `L.marker`, не в `markersLayer` — чтобы не пропадал при перерисовке полигонов секторов. Ставится/двигается по нажатию «+» (см. «Геолокация» ниже) или кнопки «моё местоположение», не убирается сам по себе.

Начальный вид карты — не просто `fitBounds` по всем секторам (это оставляло вид сильно отдалённым, весь берег Аджарии целиком): зум считается через `map.getBoundsZoom(bounds, false, L.point(36,36))` (то же значение, что дал бы `fitBounds`), к нему прибавляется `Math.log2(3)` уровней — в Leaflet каждый уровень зума удваивает масштаб, значит такая прибавка утраивает его, при том же центре (`bounds.getCenter()`). Кнопки ручного управления (`.map-controls` в `MapScreen.tsx`, справа от карты, между легендой и каруселью): «+»/«−» — обёртки над `map.zoomIn()`/`map.zoomOut()` (карта создаётся с `zoomControl:false`, встроенного контрола нет), «моё местоположение» — `LeafletMapHandle.flyToLocation(lat, lng)` (как `flyToTerritory`, но по сырым координатам). Кнопка местоположения не связана с потоком улова («+» в нижнем меню) — просто `getCurrentCoords()` → маркер → перелёт, без проверки попадания в сектор и без камеры.

### Поток данных / react-query
`lib/supabase/queries.ts` — все хуки читают напрямую из Supabase JS SDK на клиенте (`'use client'`), кешируются `@tanstack/react-query` с `refetchOnWindowFocus`. Realtime-подписок нет (см. DECISIONS.md) — карта/лента обновляются на фокусе вкладки и после `useConfirmCatch` (инвалидирует `territories`/`catches`/`activity`).

### Геолокация и быстрая фиксация улова
`lib/geolocation.ts` — две отдельные функции: `getCurrentCoords()` оборачивает `navigator.geolocation.getCurrentPosition` в промис и возвращает `{lat, lng} | null` (при отказе/таймауте/отсутствии API — `null`, никогда не бросает исключение); `nearestTerritory(lat, lng, territories)` — чистая функция, считает ближайшую территорию (haversine) и возвращает её, только если расстояние ≤ 400 м от центра соты, иначе `null`. Разделены намеренно — координаты нужны и для маркера на карте (показывается независимо от того, попал ли пользователь на сектор), и для поиска сектора отдельно.

**«+» — единственный путь к камере.** Выбор сектора вручную (клик по полигону на карте, карточка в карусели, список территорий, «Мои территории» в профиле) открывает только `TerritoryScreen` — экран статистики/уловов, без кнопки, ведущей к камере (см. DECISIONS.md, «вручную — только просмотр»). Запрашивается геолокация **только по нажатию «+»**, не автоматически при заходе на карту — карта публична (см. решение выше), не хотим просить геолокацию у анонимных посетителей, которые просто смотрят карту.

`FishZoneApp.handlePlus()`: не залогинен → вкладка «Профиль»; залогинен → тост «Определяем твоё местоположение…», `await getCurrentCoords()`. Геолокация не удалась технически (отказ/таймаут/нет API) → тост с ошибкой, ничего больше. Координаты получены → **маркер на карте ставится в любом случае** (`mapHandleRef.current?.showUserLocation(lat, lng)`, синяя точка с пульсацией, `LeafletMapHandle.showUserLocation`) — затем ищем сектор (`nearestTerritory`): нашли → карта долетает до него (`flyToTerritory`) и сразу открывается камера; не нашли (человек не на воде — например, в центре города) → модальное окно «Ты не на территории» (`.modal-overlay`/`.modal-card` в `globals.css`, новый переиспользуемый паттерн; сверху — `.modal-icon`, круглый градиент с SVG «геометка перечёркнута»), сообщающее коротким текстом, что зафиксировать улов не получится, без каких-либо вариантов обойти это вручную.

После геолокации/выбора территории открывается `CameraScreen.tsx` — **настоящий доступ к камере** (`getUserMedia`, не имитация, см. DECISIONS.md), без экрана-обхода:
- `intro` — объяснение «Быстрое добавление» + кнопка «Разрешить доступ к камере».
- клик → `requesting` → `getUserMedia({video:{facingMode:'environment'}, audio:false})`. Успех → `live`: `<video>` с потоком, `srcObject` подключается через `useEffect` по смене состояния (не сразу в обработчике клика — в момент, когда промис резолвится, элемент `<video>` ещё не смонтирован, т.к. рендерится только при `state==='live'`).
- затвор → кадр рисуется в offscreen `<canvas>` (даунскейл до 1280px по ширине), поток немедленно останавливается (`track.stop()`), `canvas.toBlob('image/jpeg', 0.85)` → `onCapture(blob)`.
- отказ/ошибка → `denied` — сообщение «Без доступа к камере нельзя сфотографировать улов и занять территорию» + кнопка **«Запросить доступ снова»** (тот же обработчик, что у intro). Нет пути пропустить фото — только повтор или × (назад на карту).
- `FishZoneApp` передаёт `CameraScreen` с `key={cameraSessionId}` (счётчик, инкрементируется при каждом новом заходе в камеру) — экран камеры никогда не размонтируется сам по себе (все экраны держатся в DOM, переключается только CSS `.active`), поэтому без явного `key` state оставался бы `live` со уже остановленным потоком при следующей попытке снять улов (застывший кадр). `key` форсирует полный ремаунт → чистое состояние `intro` на каждый новый заход.

Кадр сразу передаётся в `FishZoneApp.handleCapture(blob)`, который переключает на `screen-confirm` и **в фоне запускает загрузку** (`uploadCatchPhoto`, `lib/supabase/storage.ts`) — не дожидаясь заполнения формы. `ConfirmScreen.tsx` показывает **фото и форму на одном экране** одновременно: превью через `URL.createObjectURL(capturedPhoto)`, переключатель категории «Морская/Пресноводная» (по умолчанию — от `territory.kind`), `<select>` вида рыбы (обязателен, список — из `useSpecies()`, отфильтрован по категории), необязательные размер/вес/способ ловли/приманка. Поверх фото — статус загрузки: спиннер, пока `photoStatus==='uploading'`; при `'error'` — сообщение «Не удалось загрузить фото. Без фото улов сохранить нельзя.» + кнопка **«Повторить попытку»** (грузит тот же `Blob` заново, без возврата к камере). Кнопка «Подтвердить улов» задизейблена, пока не выбран вид рыбы **и** `photoStatus !== 'success'` — без успешно загруженного фото улов физически нельзя отправить (см. DECISIONS.md).

### Позиционирование модалок: почему `PhotoLightbox`/`EditProfileModal` рендерятся в `FishZoneApp`, а не внутри экрана
Изначально оба (`.lightbox-overlay`, `.modal-overlay` редактирования профиля — оба `position:absolute; inset:0`) рендерились внутри самого экрана (`.screen-inner`, который и есть `overflow-y:auto`-контейнер со скроллом контента). На практике это давало баг: если открыть фото/редактирование, промотав экран вниз, оверлей появлялся не на видимом месте, а «оторванным» — прибитым к верху, будто отрисован в исходной (непрокрученной) точке. Причина — не баг React/CSS-свойств самого оверлея, а стандартное (хоть и неочевидное) поведение: если containing block для `position:absolute` — сам является скроллящимся элементом, то `top:0/inset:0` считается от верха его *контента*, а не от видимой области, и смещение потомка на экране физически равно `-scrollTop` контейнера (проверено вживую через `getBoundingClientRect()`: `top` оверлея точно совпадал с `-scrollTop` `.screen`). Исправление — оверлей вынесен за пределы любого скроллящегося `.screen`, на верхний уровень `FishZoneApp` (`.app-shell`, не скроллится сам), как и уже существовавшая модалка «Ты не на территории». **Вывод на будущее**: любой full-screen оверлей (`inset:0`/`position:fixed`-имитация через `absolute`) в этом приложении должен рендериться только на уровне `FishZoneApp`, никогда внутри `.screen-inner` — иначе баг вернётся с любым новым модальным окном.

### Публичные профили и подписки
`components/app-shell/screens/UserProfileScreen.tsx` — read-only версия `ProfileScreen`: аватар/имя/локация без редактирования, статистика/достижения/уловы/территории **чужого** пользователя, кнопка «Подписаться»/«Отписаться» вместо «Выйти». Территории и уловы этого пользователя — не отдельные запросы: территории фильтруются из уже загруженного в `FishZoneApp` массива `territories` по `ownerId`, уловы — через параметризованный `useCatchesByUser(userId)` (`useMyCatches` теперь однострочная обёртка над ним).

Точки входа на чужой профиль: клик по имени в `ActivityScreen` (когда запись не своя) и по владельцу занятой территории в `TerritoryScreen` (`OwnerRow`, подгружает `useProfile(ownerId)` для аватара/имени). Обе идут через `FishZoneApp.openUserProfile(id)`: если `id === user.id` — просто переключает на вкладку «Профиль» (свой, редактируемый), иначе открывает `screen-user-profile` с этим `userId`. Экран не в `NAV_SCREENS` (как и `screen-territory`) — нижняя навигация продолжает подсвечивать вкладку, с которой пришли.

Подписка/отписка — `useIsFollowing(followeeId)` + `useSetFollowing()` (прямой `insert`/`delete` в `follows`, без RPC — простая одно-табличная операция под RLS «своя строка», в отличие от `confirm_catch`, где нужна атомарность нескольких таблиц). `useProfile` теперь читает `profiles_with_stats`, так что счётчик подписчиков обновляется сразу у всех, кто в этот момент смотрит профиль (после инвалидации `['profile', followeeId]`).

### Персонализированная лента активности
`useActivity()` (`lib/supabase/queries.ts`) без сессии — публичная нефильтрованная лента (как раньше, доступна анонимным посетителям). С сессией — сервер отдаёт только: свои записи, записи тех, на кого подписан, и записи, где `previous_owner_id` = твой id (кто-то захватил территорию, которой раньше владел ты). Фильтр строится через `.or('user_id.eq...,previous_owner_id.eq...,user_id.in.(...)')` **до** `.limit(100)` — иначе редкая, но релевантная запись могла бы вытесниться чужой глобальной активностью до применения фильтра.

**Важно**: подписка не ретроактивна — активность подписки считается только с момента, когда ты на неё подписался (`follows.created_at`), а не вся её история уловов. Это нельзя выразить одним PostgREST-фильтром (порог свой для каждого подписанного), поэтому после серверной выборки есть ещё один проход на клиенте: строка отфильтрованного участника остаётся, только если `created_at` записи позже, чем `follows.created_at` для этого автора; свои записи и «увели территорию» — без ограничения по времени. Подтверждено вручную (два тестовых аккаунта): улов, сделанный ДО подписки, в ленте не появляется; сделанный ПОСЛЕ — появляется сразу.

`activity_log.previous_owner_id` ссылается на `profiles`, как и `activity_log.user_id` — из-за этого embed в select обязательно указывает конкретный FK (`profiles!activity_log_user_id_fkey(display_name)`), иначе PostgREST отвечает 300 «ambiguous relationship» (наступили на это при первой реализации — запрос падал с ошибкой, но `ActivityScreen` тихо показывал «Пока нет активности», т.к. `data` по умолчанию `[]`, а на `isError` экран не смотрит).

**Уведомление «подписался на тебя»** не хранится в `activity_log` (пришлось бы делать `territory_id` nullable ради одной строки без территории, плюс триггер на `follows`) — вместо этого `useActivity()` при наличии сессии отдельно запрашивает последние строки `follows` (`followee_id = я`, embed `profiles!follows_follower_id_fkey(display_name)`, до 50 штук) и подмешивает их как записи `ActivityEntry` с `kind:'follow'` (без `territoryId`/`territoryKind` — они опциональны в типе именно из-за этого), объединяя с обычными записями и пересортировывая по `createdAt`. Из-за двух независимых источников `ActivityEntry.id` — не сырой `bigint` из `activity_log`, а строка с префиксом (`` `log:${id}` `` / `` `follow:${followerId}` ``), чтобы гарантированно не пересечься; это же id используется бейджем непрочитанного (`lib/activityRead.ts`, см. ниже).

### Навигация: стек экранов, кнопка «назад» возвращает на реальный источник перехода
`FishZoneApp.tsx` хранит `stack: StackEntry[]` (не просто `currentScreen: ScreenId`) — каждый переход между «просмотровыми» экранами (`screen-territory`, `screen-user-profile`) добавляет запись в стек через `push()`, кнопка «назад» (`pop()`) снимает верхнюю и восстанавливает предыдущую, включая её параметры (`territoryId`/`userId`), а не просто переключает на какой-то один фиксированный «предыдущий» экран. Переход по вкладке нижней навигации (`navClick`) сбрасывает стек целиком (`resetTo`) — вкладки не участвуют в истории «назад», это разные оси навигации (как в большинстве мобильных приложений: таб-бар не то же самое, что кнопка «назад»).

`StackEntry` — размеченное объединение (`{screen:'screen-territory', territoryId}`, `{screen:'screen-user-profile', userId}` и т.д.), не просто список `ScreenId` — иначе `pop()` не знал бы, какую именно территорию/профиль показать при возврате, если один и тот же тип экрана встречается в стеке дважды подряд с разными id (например: территория A → профиль владельца → территория B из его списка → назад → назад — должно попасть обратно на профиль владельца, а не потерять, какой именно профиль это был).

**Побочный баг, найденный и исправленный по пути** (не то, что просил пользователь напрямую, а следствие корректной реализации стека): раньше `activeTerritoryId` был одним общим полем и для потока фиксации улова (геолокация → камера → подтверждение), и для вручную открытой `TerritoryScreen`. Поскольку нижняя навигация (и кнопка «+») остаётся видна поверх `screen-territory`, нажатие «+» во время просмотра территории A могло молча подменить `activeTerritoryId` найденной по геолокации территорией B, ломая то, что должна была показать кнопка «назад» на экране территории. Разделено на `viewingTerritoryId`/`viewingUserId` (управляются стеком, только для чтения) и `catchTerritoryId` (независимое поле только для потока улова).

### Уведомления: бейдж непрочитанной активности
`lib/activityRead.ts` (`useActivityReadState()`) — отслеживание «прочитано/не прочитано» для ленты активности целиком на клиенте (`localStorage`, ключ `fishzone:lastReadActivity:{userId}`), без изменений схемы БД: это чисто косметическое, привязанное к устройству состояние (как непрочитанные в почтовом клиенте), которому не нужна синхронизация между устройствами или переживание очистки браузера. Хук хранит `lastReadAt` (ISO-таймстамп), считает `unreadIds` — `Set` id записей `activity_log`, у которых `createdAt > lastReadAt`, из уже загруженных `useActivity()`.

**При первом заходе на устройство** (`localStorage` пуст для этого `userId`) — `lastReadAt` сразу выставляется в текущий момент, а не в начало времён: иначе вся история активности пользователя выглядела бы как гора непрочитанных уведомлений в первую же секунду после того, как он открыл вкладку в новом браузере/после очистки данных.

Бейдж (`BottomNav.tsx`, `.nav-badge` — кружок с числом, `9+` при переполнении) показывает `unreadCount` на иконке вкладки «Активность»; сама вкладка (`ActivityScreen.tsx`) отмечает каждую непрочитанную запись точкой (`.unread-dot`) рядом с датой и показывает кнопку «Прочитать все» (`.mark-read-btn`, справа от фильтров-чипов) только пока `unreadIds.size > 0` — `onMarkAllRead()` переставляет `lastReadAt` на текущий момент, разом убирая и точки, и бейдж.

### Админ: `profiles.is_admin`
Одна колонка `boolean not null default false` на `profiles`, читается публично (как и остальные поля профиля — не секрет, кто админ, реальные права проверяются не на клиенте). `handle_new_user()` выставляет её в `true` автоматически, если `new.email = 'm.alimetov@mail.ru'` — захардкожено под конкретный существующий аккаунт (см. DECISIONS.md, почему не отдельная таблица/роль). `useIsAdmin()` (`lib/supabase/queries.ts`) — тонкая обёртка над уже закешированным `useProfile(user.id)`, не отдельный запрос. Все действия админа (`admin_delete_catch`, `admin_dismiss_report`) сами перепроверяют `is_admin` через `exists(select … from profiles where id=auth.uid() and is_admin)` внутри `SECURITY DEFINER`-функции — фронтенд только скрывает/показывает кнопки, не является границей безопасности.

### Жалобы на фото и модерация
Таблица `catch_reports` (`catch_id`, `reporter_id`, `reason`, `created_at`) — `insert` доступен любому `authenticated` на свою же `reporter_id` (RLS), `select` — только `is_admin`-профилям. Причины — фиксированный список `REPORT_REASONS` (`lib/data/reportReasons.ts`, 4 варианта), тот же паттерн, что `METHODS`/`BAITS` в `species.ts` — маленький список для `<select>`, не справочник в БД.

Кнопка «Пожаловаться» — в `TerritoryScreen.tsx`, на каждой строке «Последние уловы», где улов не свой (`!c.mine`) и есть сессия; открывает `ReportPhotoModal.tsx` (`useReportCatch()` → `insert` в `catch_reports`). Как и `PhotoLightbox`/`EditProfileModal`, модалка рендерится на уровне `FishZoneApp` (стейт `reportingCatchId`), а не внутри `TerritoryScreen` — та же причина, что в «Позиционирование модалок» выше.

Админ видит очередь на отдельном `screen-admin-reports` (`AdminReportsScreen.tsx`, вход — кнопка «Жалобы на фото» в `ProfileScreen`, видна только при `useIsAdmin()`; экран не в `NAV_SCREENS`, назад — обычный `pop()`). `useReports()` тянет `catch_reports` с embed `catches(...)`/`profiles!catch_reports_reporter_id_fkey(display_name)` — одна FK на `profiles`, без неоднозначности, в отличие от `activity_log`. Две кнопки на жалобу:
- **«Удалить улов»** (`useAdminDeleteCatch` → RPC `admin_delete_catch(p_catch_id)`) — удаляет `catches` (каскадом чистит `activity_log` и все `catch_reports` на этот улов, обе FK уже `on delete cascade`), затем пересчитывает `territories.owner_id`/`claimed_at` территории из того, что осталось: если на ней ещё есть чужие уловы — владение переходит к автору самого свежего оставшегося (`order by caught_at desc limit 1`), если не осталось ни одного — территория освобождается (`null`/`null`). Не «всегда освобождать» — если правонарушитель перехватил территорию поверх чужого более раннего улова, после удаления фейка сектор должен вернуться к тому, у кого его увели, а не просто опустеть.
- **«Отклонить»** (`useDismissReport` → RPC `admin_dismiss_report(p_report_id)`) — просто удаляет строку `catch_reports`, улов не трогает. Без неё очередь модерации была бы тупиковой для жалоб, которые админ счёл необоснованными.

Кнопка «Жалобы на фото» в `ProfileScreen.tsx` показывает бейдж-счётчик (`.btn-wrap`/`.btn-badge` в `globals.css`, тот же визуальный приём, что `.nav-badge`) с `reports.length` — тот же кэш `useReports()`, что и у `AdminReportsScreen` (оба вызова используют один и тот же `queryKey:['reports']`, второго запроса не происходит). `useReports()` получил `enabled: isAdmin` — раньше отправлялся при каждой загрузке приложения для любого посетителя (`AdminReportsScreen` всегда смонтирован, как и любой другой экран в этом app-shell), RLS просто возвращал пустой список; теперь запрос вообще не летит, если профиль не админ.

**Уведомление об удалении улова**: `admin_delete_catch` перед удалением дополнительно достаёт `user_id` владельца и пишет строку в `activity_log` (`kind:'moderation'`, `catch_id: null` — улов уже удалён, `territory_id` — территория остаётся). `activity_log_kind_check` расширен до `('catch','claim','moderation')`. Строка автоматически появляется в личной ленте владельца — `useActivity()` уже показывает всё, где `user_id` совпадает с текущим пользователем, без изменений в фильтрации. `ActivityScreen.tsx` рендерит `kind==='moderation'` отдельной веткой (не через шаблон «{кто} {действие}», это не чьё-то действие, а системное уведомление): «Улов на территории {id} удалён модератором» + «Нарушены правила площадки. При повторных нарушениях аккаунт будет заблокирован.» — красный аватар-восклицание вместо инициалов. Бейдж/точка непрочитанного работают уже существующей логикой (`lib/activityRead.ts` не менялся).

### Блокировка пользователя
`profiles.is_blocked` (`boolean not null default false`), публично читаема, как `is_admin`/`bio`. RPC `admin_set_blocked(p_user_id, p_blocked)` — `SECURITY DEFINER`, проверяет `is_admin` вызывающего, плюс два защитных guard'а: нельзя заблокировать самого себя и нельзя заблокировать другого админа (оба — явные `raise exception`, проверено вживую прямым вызовом RPC). Реальный эффект блокировки — не бан на уровне Supabase Auth (это требует service-role Admin API, недоступного клиентской `SECURITY DEFINER`-функции на анон-ключе), а отказ в `confirm_catch`: `if exists(... is_blocked) then raise exception 'account blocked'` в самом начале функции, до всех остальных проверок — заблокированный пользователь не может зафиксировать новый улов/захватить территорию, но по-прежнему может входить и просматривать приложение.

Кнопка «Заблокировать»/«Разблокировать» — в `UserProfileScreen.tsx`, рядом с кнопкой подписки, видна только при `useIsAdmin()` (`useSetBlocked()` → RPC). Бейдж «Заблокирован» рядом с именем показывается всем посетителям профиля, не только админу — как и с `is_admin`, публичность статуса не даёт никаких прав через клиент, а сокрытие бейджа только запутало бы обычных пользователей, почему у кого-то вдруг перестали появляться новые уловы.

### Админ: добавление улова на любой сектор
`confirm_catch` не проверяет местоположение вообще (гейт «сектор рядом» — чисто клиентский, в `handlePlus()`) — значит для обхода не нужны ни RPC, ни RLS-правки, только альтернативный UI-путь в камеру. В `TerritoryScreen.tsx`, если `useIsAdmin()`, показывается кнопка «Добавить улов (админ)» рядом с `OwnerRow`; она вызывает `FishZoneApp.startAdminCatch(territoryId)` — тот же хвост, что у `handlePlus()` после успешного `nearestTerritory()` (выставить `catchTerritoryId`, поднять `cameraSessionId`, открыть `screen-camera`), но без единого вызова геолокации. Дальше — тот же камера→форма→`confirm_catch` пайплайн, что у обычного улова; для админа не заведено отдельного пути отправки данных.

### Супер-админ: выдача/отзыв прав админа, журнал действий
`profiles.is_super_admin` — тот же паттерн, что `is_admin` (email-чек в `handle_new_user()`, только для `m.alimetov@mail.ru`), но это отдельный флаг, не производный от `is_admin` — супер-админ обладает всеми правами обычного админа (`is_admin` у него тоже `true`), но не наоборот: обычный админ (выданный супер-админом) не может ни выдавать/забирать права другим, ни видеть журнал действий.

RPC `admin_set_admin(p_user_id, p_is_admin)` проверяет именно `is_super_admin` вызывающего (не `is_admin`) — попытка обычного админа вызвать её напрямую отклоняется с `not authorized` (проверено вживую прямым вызовом RPC). Guard'ы: нельзя менять свой собственный статус, нельзя менять другого супер-админа (сейчас это в принципе один аккаунт, но защита не завязана на это допущение).

Каждое админ-действие (`admin_set_admin`, `admin_delete_catch`, `admin_dismiss_report`, `admin_set_blocked`) пишет строку в `admin_actions` с уже готовым текстом на русском (`details`), собранным внутри самой функции в момент действия — это осознанно не денормализация ради денормализации: имя цели/вид рыбы на момент действия сохраняются именно такими, какими были тогда, а не пересчитываются при каждом просмотре журнала (если пользователь сменит имя позже — старая запись в журнале не должна задним числом поменяться).

`useAdminActions(actionTypes?)` (`lib/supabase/queries.ts`) — один хук на оба экрана: «Доступы» (`ProfileScreen` → `AdminActionsScreen`, `actionTypes:['grant_admin','revoke_admin']`) показывает, кому и когда супер-админ выдавал/забирал права; «Последние действия» (без фильтра) — полный журнал всех админов. Обе кнопки в `ProfileScreen` видны только при `useIsSuperAdmin()`. Кнопка «Выдать права админа»/«Забрать права админа» — в `UserProfileScreen`, тоже только для супер-админа, скрыта на профиле другого супер-админа.

### Публичный ID пользователя
`profiles.public_id` — 5-значная строка (`text`, с ведущими нулями — поэтому `text`, не `int`: `int` потерял бы `'00042'` → `42`), генерируется случайно в `handle_new_user()` при регистрации с проверкой уникальности (цикл `loop … exit when not exists`, коллизии практически исключены при текущем масштабе пользовательской базы). Единственное исключение — `m.alimetov@mail.ru` получает фиксированный `'00000'` (тот же email-чек, что уже используется для `is_admin`). Существовавшие на момент миграции два реальных профиля были обработаны вручную: Magamed → `00000`, остальным (Ruslan) — одноразовый backfill-скрипт со случайным уникальным кодом.

Читается публично через `profiles_with_stats`, показывается небольшой строкой под локацией и в `ProfileScreen` (свой профиль), и в `UserProfileScreen` (чужой) — без этого поле поиска ниже было бы бесполезно (пользователю негде увидеть свой ID, чтобы сообщить его админу).

На вкладке «Территории» (`TerritoriesListScreen.tsx`), если `useIsAdmin()`, сверху — форма поиска (только цифры, ровно 5 символов): `useFindUserByPublicId()` (`lib/supabase/queries.ts`, `useMutation`, а не `useQuery` — это разовое действие по сабмиту, а не реактивный кэшированный запрос) ищет `profiles.public_id` точным совпадением; найден → `onOpenUser(id)` (та же функция `openUserProfile`, что уже используется во всём приложении, теперь проброшена и сюда новым пропом); не найден → инлайн-сообщение «Пользователь с таким ID не найден».

### Профиль: био
`profiles.bio` — nullable `text`, читается публично через `profiles_with_stats`. Редактируется в `EditProfileModal` (та же форма, что имя) — `<textarea maxLength={280}>`, сохраняется вместе с именем по «Сохранить» (`useUpdateProfile({displayName, bio})`). Показывается под локацией и в `ProfileScreen` (свой профиль), и в `UserProfileScreen` (чужой, read-only) — только если непусто, отдельного «нет описания» плейсхолдера нет.

## Прототип (fishzone-app.html)

Однофайловый MVP-прототип (HTML/CSS/JS, без сборки и зависимостей, кроме Leaflet и Google Fonts через CDN, эмулирует экран iPhone 390×844) — из него перенесён `web/`. Дальше не развивается; ниже — как он устроен, для справки при переносе оставшейся логики или сверке поведения.

Данные секторов (гексагональная сетка по воде) генерируются отдельным офлайн-инструментом `tools/fishing-hex/` и вшиты в `fishzone-app.html` как статический массив — сам инструмент в рантайме приложения не участвует и не нужен, чтобы просто открыть файл. См. раздел «Сектора» ниже.

### Структура файла
- `<head>` — подключение шрифта Manrope и Leaflet (JS+CSS).
- `<style>` — все стили, дизайн-токены в `:root` (цвета, радиусы, тени, переходы).
- `<body>` — разметка «телефона» (`.device`) со статус-баром, контейнером экранов (`.screens`) и нижней навигацией (`.bottomnav`).
- `<script>` — вся логика: данные (включая вшитый `HEX_SECTORS`), рендер экранов, обработчики.

## Экраны (в `.screens`, переключаются через `goTo(id)`)
| id | Назначение |
|---|---|
| `screen-map` | Карта Батуми (Leaflet), шестиугольные сектора, карусель карточек снизу |
| `screen-territory` | Детальная карточка одного сектора |
| `screen-territories` | Список всех секторов с фильтром (Все / Мои / Свободные) |

## Модель данных

### Сектора (`HEX_SECTORS` → `territories`)
Сектора больше не задаются вручную. `HEX_SECTORS` — статический массив, вшитый в `fishzone-app.html`, сгенерированный инструментом `tools/fishing-hex/` из реальных данных OpenStreetMap (береговая линия моря, реки, ручьи, озёра Аджарии). Каждый элемент — одна реально существующая гексагональная сота 600 м, которая касается воды:
```js
{ id:'B0144', kind:'sea', lat:41.48129, lng:41.515646, corners:[[lat,lng] × 6] }
```
- `id` — стабильный номер соты в сетке инструмента (не переиспользуется вручную).
- `kind` — тип воды: `sea` (море) / `river` (река) / `stream` (ручей) / `lake` (озеро). Показывается на UI через `KIND_LABEL`.
- `lat/lng` — центр соты (среднее шести вершин), используется для GPS-чипа камеры, метки на карте, `flyTo`.
- `corners` — 6 вершин в `[lat,lng]`, готовые для `L.polygon`.

Как это получено (см. tools/fishing-hex/README.md и DECISIONS.md):
```
fetch_osm.sh (Overpass API) → build_hex.mjs (гекс-сетка 600м, фильтр «касается воды») → hex.geojson
  → extract_sectors.mjs (только core-соты, [lon,lat]→[lat,lng], центроид) → sectors.json
  → вручную вставлено в fishzone-app.html как значение HEX_SECTORS
```
Если `hex.geojson` перегенерирован (другой BBOX/район) — надо заново прогнать `extract_sectors.mjs` и вставить новый `sectors.json` в `fishzone-app.html`; это ручной шаг, отдельного build-пайплайна для самого приложения нет (см. «Что это»).

Сейчас вшито 703 сектора (море 61, река 303, ручей 320, озеро 19) — весь берег Аджарии от Сарпи до Чакви.

`territories = HEX_SECTORS.map(...)` строится на старте: у каждого сектора `status:'free'`, `owner:null`, `catchCount:0`. Дальше явный список из трёх id (`B1127`/`B1126`/`B1079`) переводит их в `mine`/`other` — это ближайшие морские соты к тем же ориентирам набережной, что были в старой ручной версии (Пирс у Дельфинария / Marriott / порт). Подробности и риски при регенерации сетки — см. DECISIONS.md.

**Статусы**: `mine` (зелёный), `other` (синий), `free` (серый) — логика статусов и цвета не изменились, изменился только способ получить список секторов и их id.

### Виды рыб (`SPECIES`)
Только черноморские виды: ставрида, скорпена, ласкирь (с латинскими названиями). У каждого — свой цветовой градиент (`SPECIES_GRADIENT`) для карточек «фото» улова (реальных фото нет — используется иллюстративный градиент + SVG-силуэт рыбы, см. `fishIcon()`).

### Уловы (`catches`) и активность (`activityFeed`)
Массивы в памяти, дополняются при подтверждении улова (`confirmCatch()`). Данные не сохраняются между перезагрузками страницы (нет localStorage — оно явно запрещено в среде артефактов; здесь это просто in-memory JS).

### Пользователь (`user`)
Статичный объект (имя, локация, подписчики). Статистика на экране профиля считается «на лету» из `territories`/`catches` (`myTerritories()`, `myCatches()`, `speciesCountMine()`, `personalRecord()`), а не хранится отдельно.

### Достижения (`computeAchievements()`)
Реальные вехи, не игровые очки: первый улов, три территории, все 3 вида рыб, улов до 8 утра, личный рекорд 40+ см, десять уловов. Считаются каждый раз заново из текущего состояния — разблокировка происходит органически по ходу использования (например, «Ранний рыбак» уже разблокирован в стартовых данных, «10 уловов» — нет).

## Карта (Leaflet)
- Тайлы: стандартный OpenStreetMap (`{s}.tile.openstreetmap.org`), без API-ключа. Приглушены CSS-фильтром (`grayscale/contrast/saturate`) для более «премиального» вида.
- `initMap()` — один раз при загрузке: карта создаётся с `preferCanvas:true` (703 сектора через SVG заметно тормозили бы — canvas держит всё на одном холсте, замер перерисовки ≈5мс), `fitBounds` по вершинам всех `territories` (весь берег Аджарии, а не только точки одного отрезка набережной), отрисовка секторов, первичный рендер карусели.
- `drawTerritories()` — очищает и перерисовывает полигоны секторов + слой подписей (вызывается при инициализации; **не** триггерит перерисовку карусели карточек — это разделено намеренно, см. журнал изменений).
- Подписи id секторов (`labelsLayer`) показываются только при `zoom >= LABEL_MIN_ZOOM` (14) — при 703 секторах на весь берег все подписи разом на далёком зуме превращаются в нечитаемое месиво текста; сами шестиугольники со статусом видны на любом зуме. Переключение — на `map.on('zoomend', updateLabelVisibility)`, без пересборки полигонов.
- `renderMapSheet()` — строит карусель карточек снизу (по одной на сектор, все 703), навешивает синхронизацию скролла.
- `attachSheetScrollSync()` + `panToTerritory()` — при свайпе карточки карта делает `flyTo` на соответствующий сектор.

## Поток фиксации улова
```
Карта/Территория → кнопка «Поймать территорию» / «+» в меню
  → screen-camera (имитация камеры, GPS-чип с реальными координатами сектора)
  → нажатие затвора (takePhoto()) — рандомный вид рыбы + правдоподобные размер/вес/способ/наживка
  → screen-confirm (карточка улова) → «Подтвердить улов» (confirmCatch())
      — сектор помечается status:'mine', catchCount++, добавляются записи в catches/activityFeed
  → экран успеха («Теперь это твоя территория») → «Готово» (finishCatchFlow()) → назад на карту
```

## tools/fishing-hex — генератор сетки секторов

Отдельный офлайн-инструмент (написан не для `fishzone-app.html`, а как самостоятельная утилита; вторая половина README нацелена на его собственный демо-`map.html`, который в проект не копировался). Живёт в `tools/fishing-hex/`, требует Node 18+ (в среде разработки узла не было вообще — при переходе на `web/` скачан локально в `.tools/node/` (не коммитится, см. корневой `.gitignore`), см. DECISIONS.md; при первом прогоне `extract_sectors.mjs` узла ещё не было и шаг был выполнен эквивалентным Python-скриптом).

| Файл | Назначение |
|---|---|
| `fetch_osm.sh` | Overpass API → береговая линия, реки, ручьи, каналы, полигоны воды в bbox → `osm.json` (не коммитится, см. `.gitignore`) |
| `build_hex.mjs` | Гекс-сетка 600м по bbox, оставляет соты, касающиеся воды → `hex.geojson` + `water.geojson`. Ручьи/каналы короче `STREAM_MIN_LENGTH_M` (800м, суммарно после склейки связных OSM-way — см. DECISIONS.md) не считаются водой — отсекает незначительные притоки/канавы, реки/море/озёра не затронуты |
| `extract_sectors.mjs` | **Добавлен для FishZone** (не было у друга). Фильтрует `hex.geojson` до core-сот, конвертирует `[lon,lat]→[lat,lng]`, считает центроид → `sectors.json`, который вручную вставляется в `fishzone-app.html` как `HEX_SECTORS` |
| `assemble.mjs`, `tiles.py` | Из инструмента друга, для его собственного демо-`map.html` (не используются приложением FishZone) |

Перегенерация при смене района/шага сетки:
```bash
cd tools/fishing-hex
export PATH="$(git rev-parse --show-toplevel)/.tools/node/bin:$PATH"  # если узел не установлен системно
npm install
npm run fetch   # bash fetch_osm.sh — правки BBOX смотри в самом файле
npm run build   # node build_hex.mjs — правки WIDTH_M/PRIORITY/RING_AROUND/STREAM_MIN_LENGTH_M смотри в самом файле
node extract_sectors.mjs
```
Дальше геометрию нужно разнести в оба места, которые её используют (независимы друг от друга):
- **Прототип**: вставить содержимое `sectors.json` в `fishzone-app.html` как значение `const HEX_SECTORS` (вручную, файл однофайловый).
- **Веб-сервис**: скопировать `sectors.json` в `web/public/data/sectors.json`, и пересеять таблицу `territories` в Supabase (id/kind/lat/lng — без `corners`, geometry там не хранится, см. раздел «Веб-сервис» выше) через `execute_sql`/`apply_migration` MCP. Для новых id `owner_id` будет `null` (свободны) — это ожидаемо. **Пока в БД не было реальных владений/уловов**, удаление ушедших из сетки id было тривиальным (строка территории просто не существует). **Теперь, когда есть реальные пользователи** — если у удаляемого id уже есть `catches`/`activity_log` (`owner_id is not null`), прямой `delete from territories` упадёт на FK; сперва нужно решить, сохранять эти данные (тогда не удалять id из сетки/данных вообще) или чистить (тогда явно удалить зависимые `activity_log`→`catches`→саму территорию в этом порядке) — это осознанное решение, не автоматика. Фото уловов в Storage при этом не удаляются (`storage.protect_delete()` не даёт удалить объект напрямую SQL-ем) — остаются сиротами, что безвредно.

В прототипе после этого нужно заново подобрать id для стартовых `mine`/`other` секторов (см. DECISIONS.md) — старые id могут не существовать в новой сетке. В веб-сервисе такой перепрошивки не требуется — там нет захардкоженных demo-владельцев (все территории стартуют свободными, см. DECISIONS.md).

## Известные ограничения прототипа (осознанные, не баги)
- 703 сектора рендерятся все разом, без кластеризации и без виртуализации списка: `screen-territories` и карусель карты строят все карточки одним `innerHTML` за раз. Замеры в этой сессии показали это быстрым (карусель ≈54мс, список ≈9мс, отрисовка полигонов ≈5мс) — но если сетка вырастет ещё на порядок или список обрастёт более тяжёлой разметкой на карточку, стоит вернуться к виртуализации/пагинации. Актуально и для веб-сервиса (тот же паттерн рендера списков), но там это уже настоящая многопользовательская нагрузка, а не демо — стоит перепроверить при реальном трафике.
- Стартовые id `mine`/`other` (`B1127`/`B1126`/`B1079`) захардкожены и завязаны на конкретную сборку `hex.geojson` — при регенерации сетки другим BBOX/шагом эти id могут исчезнуть (seed молча пропустит несуществующий id, все сектора останутся `free`). См. DECISIONS.md. Не актуально для веб-сервиса.
- Нет сохранения состояния между перезагрузками (in-memory only). Не актуально для веб-сервиса — там Postgres.
- Фото рыбы — не настоящие снимки, а стилизованные градиентные карточки с SVG-иконкой рыбы. **Не актуально для веб-сервиса** — там камера настоящая (`getUserMedia`, см. раздел «Веб-сервис» выше и DECISIONS.md); ограничение осталось только в прототипе.

## Известные ограничения веб-сервиса
- Realtime не подключён — карта/лента/территории обновляются на фокусе вкладки (react-query `refetchOnWindowFocus`) и сразу после своего собственного улова, но не увидят чужой улов вживую без переключения вкладки/навигации. См. открытый вопрос в DECISIONS.md.
- Email-подтверждение регистрации сейчас выключено (см. раздел «Авторизация» выше) — временно, из-за rate limit дефолтного email-сервиса Supabase. Значит пока что любой email проходит без проверки владения им — приемлемо для теста, не для публичного запуска.
- MCP-коннектор Vercel в этой сессии так и не авторизовался (постоянный 403 «Not authorized... re-authenticate to this scope» на любой запрошенный teamId/scope) — весь деплой сделан руками пользователя через веб-интерфейс Vercel, я только диагностировал по скриншотам и логам. См. DECISIONS.md.
- `web/supabase/` (миграции как файлы) не заведён — схема применена напрямую через Supabase MCP `apply_migration` в разговоре, а не через файлы в репозитории. Если разработка перейдёт на локальный Supabase CLI (`supabase db`), эти миграции стоит выгрузить в файлы для истории/повторяемости.
- Название пойманного вида в ленте активности не склоняется («поймал скорпена», а не «скорпену») — с 36 видами полноценное русское склонение по падежам не стали делать (было и в прототипе для части видов, просто менее заметно при 3 видах). Не блокирует использование, просто не идеально грамматически.
- Геолокация просит разрешение браузера при каждом нажатии «+» (не спрашивает заранее) — если пользователь один раз откажет, браузер обычно предложит снова только вручную через настройки сайта; это стандартное поведение браузера, приложение не пытается обойти отказ повторными попытками.
- Камера (`getUserMedia`) проверена в этой сессии через подменённый `MediaStream` (canvas → `captureStream()`, эмуляция без реального устройства) — весь путь до записи в БД и Storage пройден именно так. На настоящем железе (реальная камера телефона) поведение не проверялось моей стороной — см. открытый вопрос в DECISIONS.md, стоит попросить пользователя пройти поток на своём телефоне.
